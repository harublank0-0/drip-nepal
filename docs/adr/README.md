# Architecture decision records

Status: Draft v1 (2026-09-25)

This folder records the architecture decisions for DripNepal: one file per decision, with the context, the choice, the alternatives rejected, and how the decision is verified. The specification documents (docs/00–12) hold the detail. An ADR records _why_, and links to them.

## How ADRs are written and changed

The rules are in [ADR-0001](0001-record-architecture-decisions.md). In short:

- **Naming.** `NNNN-kebab-title.md`, numbered sequentially. Numbers are never reused, even for a rejected ADR. Every ADR is listed in the index below.
- **Sections**, in this order: Status, Context, Decision, Alternatives considered, Consequences, When to revisit, Verification, Related. Under the title is the line `Status: Draft v1 (<date>)`. A CI docs check fails if a heading is missing, a number is duplicated, or an ADR is missing from this index.
- **Status values:**
  - `Proposed`: blocked on a named OD-xx or VX-xx in the [risk register](../risks-and-open-decisions.md);
  - `Accepted`: the team builds against it;
  - `Deprecated`;
  - `Superseded by ADR-NNNN`.
- **Immutability.** An Accepted ADR's Context, Decision and Alternatives are not rewritten. A changed decision gets a new ADR that supersedes it, and both Status tables are updated. In-place edits are limited to typos, links, status changes and new Verification entries.
- **Evidence labels.** ADRs use the labels defined in [docs/00](../00-context-assumptions-and-questions.md): [Confirmed], [Verified-repo], [Verified-doc] (with URL and access date), [Assumption], [Open] OD-xx and [Verify-external] VX-xx. Prices are always written "as published on <date>".
- **When one is required.** A PR needs a new or superseding ADR when it changes any of these:
  - money or ledger rules;
  - tenancy, authorization or authentication;
  - stateful infrastructure;
  - external providers, hosting included;
  - the public URL scheme, API versioning or error contract;
  - the migration policy;
  - UI component sources.

  It also needs one when it weakens a security control.

- **Workflow.** An ADR arrives as Proposed with, or before, the first dependent code, and is reviewed by the other developer or acknowledged by the product owner. It moves to Accepted once its blocking items close. Each milestone exit checks that ADR statuses match the register.
