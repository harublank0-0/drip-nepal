Part of the [research digests](README.md) (digest name `nepal_payments`). Compiled on 2026-09-25; repository paths refer to the code at commit `0282605`. This is a dated snapshot: re-check a fact against its source before relying on it.

Status: verified-official = primary source read. Fact-check verdicts included where a skeptic re-checked.

- [verified-official] eSewa ePay v2 is an HTML form POST (browser redirect) to https://rc-epay.esewa.com.np/api/epay/main/v2/form (UAT) or https://epay.esewa.com.np/api/epay/main/v2/form (production).
  - Sources: eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>
  - Implication: Checkout must render an auto-submitting server-built form (works with Inertia SSR). The server computes all field values and the signature so the client cannot change them. Keep the form endpoint in per-environment config.
- [verified-official] The ePay form requires amount, tax_amount, total_amount, transaction_uuid, product_code, product_service_charge, product_delivery_charge, success_url, failure_url, signed_field_names and signature. None may be null or empty, and unused tax, service or delivery charges must be sent as zero.
  - Sources: eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>
  - Implication: The payment-attempt record must keep the exact amount breakdown that was sent, including zeros, so it can be compared with the callback and status API later.
- [verified-official] The eSewa request signature is HMAC-SHA256 with Base64 output. It is computed over the string 'total_amount=<v>,transaction_uuid=<v>,product_code=<v>', and those three fields are mandatory and must be signed in that order. The UAT secret key published in the docs is 8gBm/:&EnhH.1/q with product_code EPAYTEST.
  - Sources: eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>; eSewa Developer Docs - Test Credentials <https://developer.esewa.com.np/pages/Test-credentials>
  - Implication: Sign on the server only and keep the production secret in env or a secret manager, never in the Inertia props. Use a constant-time comparison when verifying. The UAT key is public, so it must never be used outside the sandbox.
- [verified-official] After a successful payment eSewa redirects the user to success_url with a Base64-encoded response. It contains transaction_code, status, total_amount, transaction_uuid, product_code, signed_field_names and signature, and the docs tell merchants to verify its integrity by recomputing the signature. The docs do not name the query parameter that carries the payload.
  - Sources: eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>
  - Implication: The redirect is signed but is still only a browser hop: it can be lost if the tab closes or the network drops. Treat it as a hint. Verify the signature, then confirm with the status API before marking the order paid. Confirm the query parameter name in UAT; third-party integrations commonly use 'data'.
- [verified-official] eSewa redirects to failure_url after a FAILURE or PENDING transaction, and user cancellation counts as a failure. The docs define no response parameters for the failure redirect.
  - Sources: eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>
  - Implication: A failure redirect does not mean the payment definitely failed, because PENDING also lands there. Move the order to 'payment_pending_verification' and let the status API decide. Never auto-cancel an order and release its stock based on this redirect alone.
- [verified-official] The eSewa status check is GET https://rc.esewa.com.np/api/epay/transaction/status/?product_code=&total_amount=&transaction_uuid= (UAT) or https://esewa.com.np/api/epay/transaction/status/?... (production). It returns product_code, transaction_uuid, total_amount, status and ref_id, where ref_id is null for pending payments.
  - Sources: eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>
  - Implication: This API is the source of truth for eSewa. Run it from the callback handler and from a background reconciliation job (Redis-backed queue). Store ref_id as the provider reference. Note that a third-party WooCommerce plugin calls epay.esewa.com.np for production status, so confirm the production host with eSewa.
- [verified-official] The eSewa status API can return COMPLETE, PENDING, FULL_REFUND, PARTIAL_REFUND, AMBIGUOUS ('Payment is at hult state'), NOT_FOUND ('Payment terminated at eSewa: Session expired') and CANCELED ('Canceled/Reversed from eSewa side'). It can also return the error {"code":0,"error_message":"Service is currently unavailable"}.
  - Sources: eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>
  - Implication: Map each value to an internal payment state. Only COMPLETE plus an amount match counts as paid. PENDING and AMBIGUOUS keep being polled with backoff and eventually go to manual review. NOT_FOUND and CANCELED mean failed. FULL_REFUND and PARTIAL_REFUND mean refunded. Treat the error response as retryable.
- [verified-official] The ePay v2 docs describe no server-to-server webhook. Merchants are 'notified via email/SMS' of each successful transaction, and if no response arrives within five minutes they should use the status check API.
  - Sources: eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>
  - Implication: No push confirmation exists for ePay, so DripNepal must run its own reconciliation poller for PENDING attempts. It should start about 5 minutes after initiation and continue on a schedule until the payment reaches a terminal state or goes to manual review.
- [verified-official] eSewa states that if payment is not made within 5 minutes of login, the transaction fails and the user must start it again.
  - Sources: eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>
  - Implication: The mobile UI on slow networks should warn about the short window. A retry must create a new payment attempt with a new transaction_uuid, and stock holds must last longer than the payment window.
- [verified-official] transaction_uuid must be unique on every request and may contain only alphanumeric characters and hyphens. The docs do not say what eSewa does with a duplicate transaction_uuid.
  - Sources: eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>
  - Implication: Generate a UUID or ULID (hyphen or alphanumeric) per payment attempt, not per order, and put a unique DB constraint on (provider, transaction_uuid). Make callback and poller handlers idempotent on this key.
- [verified-official] The eSewa developer docs (Epay, Intent, Token, Test credentials) document no refund API. Refunds show up only as FULL_REFUND or PARTIAL_REFUND in the ePay status API, and as REVERTED in the Intent status API.
  - Sources: eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>; eSewa Developer Docs - Intent <https://developer.esewa.com.np/pages/Intent>
  - Implication: eSewa refunds must be an ops workflow (merchant portal or eSewa support) with a manual 'refund recorded' step in DripNepal admin. Reconciliation should then confirm it through the status API.
- [contradicted] The published eSewa test credentials disagree. The Epay page lists password 'Nepal@123' and the Test Credentials page lists 'Test@123'. Both give eSewa IDs 9711111111-9711111114 (the Test Credentials page writes 9711111111/2/3), MPIN 1122 and token/OTP 123456.
  - Sources: eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>; eSewa Developer Docs - Test Credentials <https://developer.esewa.com.np/pages/Test-credentials>
  - Implication: Do not hard-code test credentials in docs or tests. Keep them in a testing runbook and re-check them against eSewa UAT before E2E runs.
- [verified-official] eSewa says live credentials are provided 'after successful test transactions'.
  - Sources: eSewa Developer Docs - Test Credentials <https://developer.esewa.com.np/pages/Test-credentials>
  - Implication: Launch planning needs a UAT sign-off step with eSewa before go-live. Environments must switch cleanly between UAT and production keys and hosts.
  - Fact-check: supported — Quote: 'For production environment we will provide live credentials after successful test transactions.'
- [verified-official] eSewa's Intent integration is an API flow. The merchant POSTs to https://rc-checkout.esewa.com.np/api/client/intent/payment/book with product_code ('INTENT'), amount, transaction_uuid, signed_field_names, signature, callback_url, redirect_url and properties, and receives booking_id, a deeplink and correlation_id. Mobile browsers use the deeplink to open the eSewa app, and desktop web browsers are sent to ePay web payment. Only development URLs are published.
  - Sources: eSewa Developer Docs - Intent <https://developer.esewa.com.np/pages/Intent>
  - Implication: This fits a mobile-first audience, and eSewa marks it 'Recommended'. It needs a server-to-server initiate call like Khalti. Production endpoints must come from eSewa, so the Intent flow is a Phase-2 option until they are available.
- [verified-official] For the Intent flow, eSewa POSTs a server notification to the merchant's callback_url containing product_code, amount, reference_code, correlation_id, status, signed_field_names and signature. The signature is HMAC-SHA256 over 'product_code,amount,reference_code,correlation_id,status' with the access key. If no callback arrives within five minutes, the merchant should call POST .../intent/payment/status.
  - Sources: eSewa Developer Docs - Intent <https://developer.esewa.com.np/pages/Intent>
  - Implication: Of the four candidates, this is the only documented HTTP server-to-server callback. The webhook route must skip CSRF (Shield) and session, verify the HMAC, check the amount against the stored attempt, and be idempotent on correlation_id. It must still fall back to the status API.
- [verified-official] eSewa Intent statuses are BOOKED, SUCCESS, PENDING, FAILED, CANCELED and REVERTED ('refunded back to the user'). A cancel endpoint exists at POST https://rc-checkout.esewa.com.np/api/client/intent/payment/cancel. The docs give no expiry period for a booking or deeplink.
  - Sources: eSewa Developer Docs - Intent <https://developer.esewa.com.np/pages/Intent>
  - Implication: Call the cancel endpoint when a user abandons checkout or stock expires. Store BOOKED as 'initiated'. Because expiry is undocumented, set DripNepal's own expiry and reconcile after it passes.
- [verified-official] eSewa's 'Token' integration is a model where the customer enters a merchant-generated token inside eSewa, and eSewa calls the merchant's /inquiry/{request_id}, /payment and /status endpoints (Basic or Bearer auth). request_id identifies the transaction. It is not a web checkout flow.
  - Sources: eSewa Developer Docs - Token <https://developer.esewa.com.np/pages/Token>
  - Implication: Not suitable for storefront checkout. It could suit a later 'pay by reference code' option, for example paying for a COD-converted order inside the eSewa app. Out of scope for the MVP.
- [verified-official] eSewa lists documents for merchant API integration by entity type. A private or public limited company needs a Certificate of Incorporation, PAN/VAT certificate, MOA/AOA, a board minute on signatories, signatories' citizenship, the latest tax clearance certificate, any applicable industry or business licence, and a completed KYM document. Sole proprietors below NPR 1 lakh annual transactions have a lighter set.
  - Sources: Documents Required for eSewa Merchant API Integration - eSewa Blogs (11 Aug 2026) <https://blog.esewa.com.np/documents-required-esewa-merchant-api-integration>
  - Implication: DripNepal (the platform entity) needs company registration, PAN/VAT and tax clearance before going live on eSewa. This is a launch dependency for the ops plan. Vendors do not onboard with eSewa if the platform collects centrally, which is subject to the legal item on aggregation.
- [verified-official] eSewa's consumer terms say cancellations and refunds 'will be governed as per the terms and conditions of the Merchant'. 'Cancelled' means the amount was reverted to the eSewa account, and 'Pending' means the transaction is not yet complete because of technical or other issues at eSewa, the merchant or the bank.
  - Sources: eSewa Terms and Conditions <https://blog.esewa.com.np/terms-and-conditions>
  - Implication: DripNepal must publish its own refund and cancellation policy (the E-Commerce Act also requires this) and show it at checkout.
- [verified-official] No split payment, sub-merchant or marketplace settlement feature appears in eSewa's public developer documentation.
  - Sources: eSewa Developer Docs - Introduction <https://developer.esewa.com.np/>; eSewa Developer Docs - Epay <https://developer.esewa.com.np/pages/Epay>
  - Implication: If the platform collects, funds land in DripNepal's single merchant account and vendor payouts are off-gateway, which carries legal risk (see NRB items). Model vendor payables in an internal ledger either way.
- [verified-official] Khalti web checkout (KPG-2) starts with a server-side POST to https://dev.khalti.com/api/v2/epayment/initiate/ (sandbox) or https://khalti.com/api/v2/epayment/initiate/ (production) with header 'Authorization: Key <live_secret_key>'. It returns pidx, payment_url, expires_at and expires_in, and the user is redirected to payment_url.
  - Sources: Web Checkout - Khalti Payment Gateway <https://docs.khalti.com/khalti-epayment/>
  - Implication: Initiate from an AdonisJS service with a timeout and retry-safe design. Persist pidx before redirecting. Use an Inertia external redirect (location visit) to payment_url.
- [verified-official] Khalti initiate requires return_url, website_url, amount (in paisa), purchase_order_id and purchase_order_name. customer_info, amount_breakdown (whose amounts must sum to amount), product_details, merchant_username and merchant_extra are optional.
  - Sources: Web Checkout - Khalti Payment Gateway <https://docs.khalti.com/khalti-epayment/>; khalti/docs.khalti.com - khalti-epayment.md <https://github.com/khalti/docs.khalti.com/blob/master/content/khalti-epayment.md>
  - Implication: Store money as integer paisa (bigint) across the data model to match Khalti and connectIPS and to avoid float errors. Convert to rupee decimals only for eSewa's fields.
- [verified-official] Khalti requires the amount to be greater than Rs. 10 (1000 paisa).
  - Sources: Web Checkout - Khalti Payment Gateway <https://docs.khalti.com/khalti-epayment/>
  - Implication: Validate the minimum with Vine before initiating, and hide Khalti for orders below the threshold.
- [verified-official] Khalti redirects the user by GET to return_url with the query parameters pidx, status (Completed / Pending / User canceled), transaction_id, tidx, amount, mobile, purchase_order_id, purchase_order_name and total_amount. The redirect carries no signature, and the docs say to 'use the lookup API for the final validation of the transaction'.
  - Sources: khalti/docs.khalti.com - khalti-epayment.md <https://github.com/khalti/docs.khalti.com/blob/master/content/khalti-epayment.md>; Web Checkout - Khalti Payment Gateway <https://docs.khalti.com/khalti-epayment/>
  - Implication: The unsigned query parameters can be forged by anyone. The return handler may only look up the pidx it already stored and call the lookup API. It must never trust status or amount from the URL. Record this as a threat-model item.
- [verified-official] Khalti's lookup is POST https://dev.khalti.com/api/v2/epayment/lookup/ (sandbox) or https://khalti.com/api/v2/epayment/lookup/ (production) with body {"pidx": ...}. It returns pidx, total_amount, status, transaction_id, fee and refunded. The docs state 'Only the status with Completed must be treated as success.'
  - Sources: Web Checkout - Khalti Payment Gateway <https://docs.khalti.com/khalti-epayment/>
  - Implication: Mark an order paid only when lookup status is Completed and total_amount equals the stored amount in paisa. Store fee and transaction_id, which the refund API needs.
- [verified-official] Khalti lookup statuses are Completed, Pending ('Hold, do not provide service. And contact Khalti team.'), Initiated, Refunded, Expired, User canceled and Partially refunded. The source docs also describe Pending as 'Transaction is failed or is in pending state'.
  - Sources: Web Checkout - Khalti Payment Gateway <https://docs.khalti.com/khalti-epayment/>; khalti/docs.khalti.com - khalti-epayment.md <https://github.com/khalti/docs.khalti.com/blob/master/content/khalti-epayment.md>
  - Implication: Pending must not trigger fulfilment. Send it to a manual-review queue with an ops alert, and keep polling until expiry.
- [verified-official] Khalti's KPG-2 web checkout docs describe no server-to-server webhook. Confirmation comes only from the return_url browser redirect plus the merchant-initiated lookup API. A third-party Drupal module describes the pattern the same way: redirect, then lookup, never trusting callback parameters.
  - Sources: Web Checkout - Khalti Payment Gateway <https://docs.khalti.com/khalti-epayment/>; Khalti | Drupal.org <https://www.drupal.org/project/khalti>
  - Implication: When users drop off on slow mobile networks, the only recovery is a background job that looks up every non-terminal pidx until Completed, Expired or User canceled. That job is required, not optional.
- [contradicted] Khalti's docs contradict themselves on link expiry. They say the payment link 'expires in 60 minutes in production (default)', but the sample initiate response shows expires_in 1800 (30 minutes). The sample expires_at uses a +05:45 offset.

  - Sources: Web Checkout - Khalti Payment Gateway <https://docs.khalti.com/khalti-epayment/>
  - Implication: Use a unique purchase_order_id per payment attempt, guarded by a DB unique constraint. If the initiate call times out, look up or recreate an attempt rather than blindly re-POSTing, and treat pidx as the provider key.

- [verified-official] connectIPS e-payment is a browser form POST (x-www-form-urlencoded) to https://{base_url}/connectipswebgw/loginpage. Fields are MERCHANTID, APPID, APPNAME, TXNID (max 20), TXNDATE (DD-MM-YYYY), TXNCRNCY (NPR), TXNAMT (in paisa), REFERENCEID, REMARKS, PARTICULARS and TOKEN (max 512).

  - Implication: connectIPS is a bank-account payment method for higher-value orders. Enforce field length limits in Vine (TXNID at most 20 characters, so use a compact ID and not a 36-character UUID).
- [verified-official] The connectIPS TOKEN is built from the message 'MERCHANTID=..,APPID=..,APPNAME=..,TXNID=..,TXNDATE=..,TXNCRNCY=..,TXNAMT=..,REFERENCEID=..,REMARKS=..,PARTICULARS=..,TOKEN=TOKEN'. It is hashed with SHA-256, signed with SHA256withRSA using the merchant's private key from a .pfx certificate (CREDITOR.pfx for testing), then Base64-encoded.
  - Sources: 3. Merchant Interface Description | NCHL API Documentation <https://doc.connectips.com/docs/connectIPS-Gateway/merchant-interface>

- [verified-official] Section 8(1) of the Electronic Commerce Act, 2081 (2025) lets buyers pay the business entity, or a delivery service provider on its behalf, before, during or after purchase, and 'payment made to the delivery service provider shall be deemed as payment received by the business entity'.   - Sources: Electronic Commerce Act, 2081 (2025) - Law Commission English translation <https://giwmscdnone.gov.np/media/files/E-Commerce%20Act,%202081_yr7k9o5.pdf>

- [verified-official] Under the E-Commerce Act, the business must register a complaint, investigate and decide it within 15 days, reply in writing, and run an online redressal mechanism (Section 33). Goods that do not match their description may be returned, and if the buyer declines an exchange the amount paid must be refunded including taxes (Section 10).
