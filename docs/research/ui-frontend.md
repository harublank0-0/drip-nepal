Status: verified-official = primary source read. Fact-check verdicts included where a skeptic re-checked.

- [verified-official] The official components.json JSON Schema restricts 'style' to an enum of 'default', 'new-york', and {radix|base|aria}-{vega|nova|maia|lyra|mira|luma|sera|rhea} (e.g. 'radix-nova', 'base-nova', 'aria-nova').
  - Sources: shadcn/ui components.json JSON Schema <https://ui.shadcn.com/schema.json>
  - Implication: DripNepal's 'radix-nova' is a valid current style. The prefix picks the primitive library (Radix) and the suffix picks the visual style (Nova). Record both in the UI ADR.
- [verified-official] 'Nova' is one of the visual styles introduced with 'npx shadcn create' (December 2025). The docs describe it as 'Reduced padding and margins for compact layouts'. Vega is 'The classic shadcn/ui look', and Mira is 'Compact. Made for dense interfaces'.
  - Sources: December 2025 - npx shadcn create (shadcn/ui changelog) <https://ui.shadcn.com/docs/changelog/2025-12-shadcn-create>; shadcn/ui Component Styles: Vega, Nova, Maia, Lyra, and Mira - Shadcnblocks <https://www.shadcnblocks.com/blog/shadcn-component-styles-vega-nova-maia-lyra-mira>
  - Implication: Nova's compact density suits the vendor dashboard. On the mobile storefront and checkout, check touch-target sizes against WCAG 2.5.8 (see the target-size facts) and do not rely on the compact defaults.
- [verified-official] The official registry serves style-specific items at https://ui.shadcn.com/r/styles/radix-nova/{name}.json (for example button.json, file path 'registry/radix-nova/ui/button.tsx'). The repo's inertia/components/ui/button.tsx uses the same cva base class string as that item, with sizes default h-8, xs h-6, sm h-7, lg h-9, icon size-8, icon-xs size-6, icon-sm size-7 and icon-lg size-9.
  - Sources: shadcn registry item: radix-nova/button <https://ui.shadcn.com/r/styles/radix-nova/button.json>; drip-nepal repo: inertia/components/ui/button.tsx `inertia/components/ui/button.tsx`
  - Implication: The repo's primitives come from the official radix-nova registry. Use 'shadcn add <c> --diff' against this style when checking for upstream changes.
- [verified-official] The components.json docs say 'style' cannot be changed after initialization. They also say that for Tailwind CSS v4 'tailwind.config' should be left blank, and that baseColor and cssVariables cannot be changed after initialization.
  - Sources: components.json - shadcn/ui <https://ui.shadcn.com/docs/components-json>
  - Implication: Switching to base-nova later is a component migration, not a config edit. The repo's tailwind.config '' is correct for Tailwind 4.3.1.
- [verified-official] The schema defines iconLibrary (string), menuColor (enum default|inverted|default-translucent|inverted-translucent), menuAccent (enum subtle|bold) and rtl (boolean). The components.json docs page does not document these fields.
  - Sources: shadcn/ui components.json JSON Schema <https://ui.shadcn.com/schema.json>; components.json - shadcn/ui <https://ui.shadcn.com/docs/components-json>
  - Implication: The repo's menuColor 'default', menuAccent 'subtle' and rtl false are schema-valid. Nepali is LTR, so leave rtl false.
- [verified-official] In the 'registries' field, each key must start with '@'. The value is either a URL template string that contains '{name}', or an object with a required 'url' (containing '{name}') plus optional 'params' and 'headers'. '${VAR_NAME}' is expanded from process.env, and an optional '{style}' placeholder is replaced with the project's style.
  - Sources: shadcn/ui components.json JSON Schema <https://ui.shadcn.com/schema.json>; Namespaces - shadcn/ui registry docs <https://ui.shadcn.com/docs/registry/namespace>
  - Implication: '@commercn': 'https://commercn.com/r/{name}.json' is valid. Put any private registry token in env vars, never in components.json.
- [contradicted] The Registry Index docs say that 'shadcn add' and 'shadcn search' automatically check the open-source registry index (https://ui.shadcn.com/r/registries.json) and add the registry to components.json. The Namespaces page's trust model says 'No automatic registry discovery: The CLI never automatically adds registries'.
  - Sources: Registry Directory - shadcn/ui <https://ui.shadcn.com/docs/registry/registry-index>; shadcn/ui docs source: registry/namespace.mdx <https://github.com/shadcn-ui/ui/blob/main/apps/v4/content/docs/registry/namespace.mdx>
  - Implication: The two official pages disagree. Assume any indexed @namespace can be pulled in without an explicit config change, and review components.json diffs in PRs.
- [verified-official] @commercn is listed in the official shadcn registry index with url 'https://commercn.com/r/{name}.json'. On 2026-09-25 its Registry Health status was 'healthy', score 98.125, firstObservedAt 2026-08-24.
  - Sources: shadcn/ui open source registry index (registries.json) <https://ui.shadcn.com/r/registries.json>
  - Implication: The health score only measures availability and installability. It says nothing about code quality, accessibility or licence.
- [verified-official] shadcn's registry security model treats registry resources as data: they are validated against the item schema, and the CLI executes no code from them. The docs also state 'You trust what you install'. Index admission requires only that a registry be open source and publicly accessible, then be 'validated and reviewed by the team', and Registry Health 'does not delay or gate publication'.
  - Sources: shadcn/ui docs source: registry/namespace.mdx <https://github.com/shadcn-ui/ui/blob/main/apps/v4/content/docs/registry/namespace.mdx>; Registry Directory - shadcn/ui <https://ui.shadcn.com/docs/registry/registry-index>
  - Implication: Installed registry code ends up in DripNepal's bundle and runs in users' browsers, so it is a supply-chain input. The threat model should require code review of every added item. Prefer --dry-run or --view before writing.

- [verified-official] As of 2026-09-03, every shadcn registry component imports 'cn' from the npm package 'cn' instead of '@/lib/utils', and registry items declare it as a dependency. - [verified-official] Inertia deferred props are loaded 'after the initial page render' in a separate request. All deferred props share one request unless they are put in groups, which are fetched in parallel. On the client, <Deferred data=... fallback=...> renders the fallback until the props arrive.
  - Sources: Deferred Props - Inertia.js v2 <https://inertiajs.com/docs/v2/data-props/deferred-props>
  - Implication: Defer non-critical data such as reviews, recommendations, 'recently viewed' and dashboard charts. Keep SEO-critical product data (title, price, stock, images) out of deferred props so it appears in the SSR HTML.
