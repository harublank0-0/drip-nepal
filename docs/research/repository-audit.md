## Area: identity-authz

### IAM-01 [high; confirmed] Shop dashboard route group has authentication but no shop membership/ownership check (BOLA pattern); prefix is /shop/ not /shops/

- Evidence: start/routes/shops.ts:14-28 `.as('shop').prefix('/shop/:shopSlug').middleware(middleware.auth())` (only auth). app/controllers/shops/dashboard/shop*dashboard_controller.ts:4-6 `async create({ inertia }) { return inertia.render('shops/dashboard/index', {}) }` never reads params.shopSlug, never loads the Shop, never checks status. Generated pattern '/shop/:shopSlug/dashboard' (.adonisjs/client/registry/index.ts:23), while commit 0282605 is titled 'change url from /vendors/dashboard to /shops/:shopSlug/dashboard'. No @adonisjs/bouncer in package.json dependencies (lines 74-117) and no app/policies dir, although import aliases '#policies/*' and '#abilities/\_' exist (package.json:37-38). The page currently renders only `<h1>hello</h1>` (inertia/pages/shops/dashboard/index.tsx:5).
- Impact: Any logged-in customer can open /shop/<any-slug>/dashboard, including slugs that don't exist (no 404) and shops that are pending or suspended. No data leaks yet because the page is a placeholder. But the first settings, products, orders or payouts route added to this group will expose or modify another vendor's data (buyer PII on orders, bank/payout details, inventory) unless every controller re-implements the check.
- Recommendation: Add a named `shopContext` middleware applied to the whole /shop/:shopSlug group. It should resolve the shop by slug (excluding soft-deleted), return 404 unless the user is an active member (owner or staff), apply the status policy (e.g. pending shops get a limited view, suspended shops are read-only), and put ctx.shop and the member's permission set on the context. Scope every shop query by ctx.shop.id and never trust a shop_id from the body. Install @adonisjs/bouncer for per-permission abilities. Pick one prefix (/shop or /shops) and document it. Add functional tests showing that user A gets 404 on shop B's dashboard.

### IAM-02 [high; confirmed] Shop registration (vendor onboarding) is broken: stale route names after the last commit, and the success redirect targets a guest-only route

- Evidence: start/routes/shops.ts:11 `.as('shops.register')` (commit 0282605 changed it from `.as('shops')`). Generated names are 'shops.register.shop_registrations.create/store' (.adonisjs/server/routes.d.ts:7-8; .adonisjs/client/registry/index.ts:9-20). Server: app/controllers/shops/auth/shop_registrations_controller.ts:65-67 `response.redirect().toRoute('shops.shop_registrations.create', { data: { success: 1 } })`. Client: inertia/pages/shops/register/index.tsx:40-43 `router.visit({ route: 'shops.shop_registrations.store' }, …)`. The redirect target sits behind `.middleware(middleware.guest())` (shops.ts:12), but the controller has just logged the user in (controller:64), and app/middleware/guest_middleware.ts:24-26 redirects authenticated users to '/'. The success screen reads `?success=1` (register/index.tsx:19-24), but `{ data: {...} }` is passed where route params go, not a query string. .husky/pre-push only runs `pnpm lint` and tests/ has only bootstrap.ts, so `pnpm typecheck` (package.json:19) does not gate these names.
- Impact: The only way to create a shop fails. Either the client cannot resolve the route name, or the POST commits the user, shop, categories and address, logs the user in, and then throws on the redirect lookup, returning a 500. The user is left with a created account and shop and an error page, and a retry redirects them home. Even with the names fixed, the success screen can never be reached.
- Recommendation: Update both call sites to the generated names (or rename the group back). After a successful POST, redirect to an auth-only page (the new shop's dashboard, or a 'shop submitted, pending review' page), and pass query data through the redirect options, not params. Wire `pnpm typecheck` and functional tests into pre-push or CI so named-route drift fails the build.

### IAM-03 [high; confirmed] Catalogue, product, cart and checkout routes are guest-only, so logged-in users are bounced to '/'; a two-segment catch-all product route shadows future URLs

- Evidence: start/routes.ts:17-49: the group containing 'signup', 'login', 'men', 'women', 'categories/:slug' and ':attributeValue/:productSlug' ends with `.use(middleware.guest())` (line 49). start/routes.ts:52-64: '/cart' and '/checkout' use `.use(middleware.guest())` under a '// DEBUGS ROUTES' comment. start/routes.ts:66-71 exposes '/design-system' publicly. guest_middleware.ts:23-27 redirects any authenticated request to '/'. orders.user_id is NOT NULL (database/migrations/1780074257570_create_orders_table.ts:10), so checkout requires a logged-in buyer.
- Impact: Every logged-in customer or vendor who clicks Men, Women, a category, a product, the cart or checkout is redirected home. Checkout, which needs an authenticated buyer, is unreachable for authenticated users. The pattern `/:attributeValue/:productSlug` claims any two-segment path (e.g. a future `/shop/:slug` storefront or `/account/orders`) and applies guest-only semantics to it.
- Recommendation: Keep guest() only on signup, login and shop register. Make the catalogue public with no auth middleware, keep the cart public with a guest cart, and put checkout behind auth. Move product URLs under a static prefix (e.g. /p/:slug or /products/:slug). Remove the debug and design-system routes from production builds.

### IAM-04 [high; confirmed] Sessions cannot be revoked server-side (cookie store), and suspended or soft-deleted users can still log in and keep their sessions

- Evidence: .env.example:13 `SESSION_DRIVER=cookie`. config/session.ts:26 `age: '2h'`, :59 `store: env.get('SESSION_DRIVER')`, :65-75 only `cookie` and `database` stores are configured. No sessions-table migration exists in database/migrations/, and @adonisjs/redis is not a dependency (it is only an optional peer in pnpm-lock.yaml:547), although Redis 8.6 runs in docker-compose.yml. app/controllers/session_controller.ts:15-16 `User.verifyCredentials(email, password)` then `auth.use('web').login(user)` with no status or deletedAt check. The users table has status (migration 1761885935168:22-26) and deleted_at (:33), and UserStatus defines SUSPENDED/DELETED (app/constants/user_status.ts:1-6). app/middleware/auth_middleware.ts:22 and silent_auth_middleware.ts:12 only authenticate by id. config/auth.ts:19 `useRememberMeTokens: false`, yet inertia/pages/auth/login.tsx:129-132 renders a 'Remember me' checkbox that is ignored.
- Impact: Banning a fraudulent vendor or abusive buyer does not stop them: they can log in again and existing sessions keep working. With the cookie store there is no server-side session record, so 'log out all devices', killing sessions on password change and admin session termination are impossible, and a stolen session cookie stays usable until it expires. Switching SESSION_DRIVER to 'database' would fail because there is no sessions table.
- Recommendation: Move to a server-side store: Redis via @adonisjs/redis (already in compose), or the database store with its migration. Keep a per-user session index or an `auth_version` column checked on every request so sessions can be revoked. Reject non-active or soft-deleted users both at login and in auth/silent-auth (custom user provider or middleware). Regenerate and revoke sessions on password change. Either implement remember-me properly or remove the checkbox.

### IAM-05 [medium; corrected] Login has no rate limiting or lockout, swallows unexpected errors, and caps passwords at 32 characters

- Evidence: app/controllers/session_controller.ts:11-24 has no throttle. `} catch (e) { if (e instanceof errors.E_INVALID_CREDENTIALS) { return inertia.render('auth/login', { error: e.message }) } }` (lines 18-23) has no else/rethrow, so any other error returns undefined and is never reported. app/validators/shared.ts:7 `password = () => vine.string().minLength(8).maxLength(32)` is reused by loginValidator (app/validators/auth/user.ts:19-22), signupValidator and shopSignupValidator. package.json has no @adonisjs/limiter. config/app.ts sets no trustProxy (needed for correct request.ip() behind a proxy). scrypt cost is 16384 (config/hash.ts:31), so each attempt costs real CPU.
- Impact: Unlimited credential stuffing and password spraying are possible against buyer and vendor accounts. A vendor takeover allows listing or payout fraud. The login endpoint doubles as a CPU denial-of-service vector through scrypt. Database or hash failures produce a blank response with no log. The 32-character cap blocks passphrases and password-manager output.
- Recommendation: Add @adonisjs/limiter backed by Redis with limits on IP and on (email + IP), progressive backoff or temporary lockout, and a notification to the account owner. Rethrow non-credential errors so the handler reports them. Raise the password max to at least 64 (e.g. 128) and don't apply the policy's min length on login. Configure trustProxy for the deployment topology. Emit auth events (login success/failure, lockout) to logs.
- Verifier correction: The facts are accurate. session_controller.ts:11-24 has no throttle, and the catch at lines 18-23 swallows non-credential errors and returns undefined. shared.ts:7 caps passwords at 32 and is reused by loginValidator (user.ts:19-22). No limiter package is installed, config/app.ts has no trustProxy, and hash.ts:31 sets cost 16384. The severity is overstated for the rubric, though. Nothing is deployed, no core flow breaks, and 32 characters exceeds the defaults of common password managers. This is a missing pre-launch control, not a broken flow. Rate it medium and list it as a hard launch gate in the threat model. Minor note: trustProxy has a framework default (loopback), so the real issue is that it is unconfigured for the eventual proxy topology.

### IAM-07 [high; confirmed] Deleting a user or a saved address cascades to orders, order_items and payments

- Evidence: database/migrations/1780074257570_create_orders_table.ts:11 `table.foreign('user_id').references('users.id').onDelete('CASCADE')` and :14 `table.foreign('user_address_id').references('user_addresses.id').onDelete('CASCADE')`. 1780074815800_create_payments_table.ts:11 order_id CASCADE. 1780074567760_create_order_items_table.ts:11 order_id CASCADE and :14 shop_id CASCADE. 1780073825111_create_user_addresses_table.ts:11 user_id CASCADE. By contrast, shops.owner_id is RESTRICT (1780070540447:12).
- Impact: Account deletion and 'remove saved address' are obvious next profile features. With these FKs, deleting a buyer or one address book entry hard-deletes their orders, the vendors' order_items and the payment records. That destroys the financial and audit trail and the basis for vendor payouts and disputes. Deleting a shop also erases its sales history.
- Recommendation: Use RESTRICT (or SET NULL where appropriate) on orders.user_id, orders.user_address_id, payments.order_id and order_items.shop_id. Snapshot the shipping address into the order. Implement account deletion as anonymisation plus soft delete, and document retention rules in the data model and privacy docs.

### IAM-11 [medium; confirmed] Owner is modelled only as shops.owner_id: no owner membership or role, and the nav shares only owned shops, not staff shops

### IAM-12 [medium; confirmed] shop_roles has no unique(shop_id, slug), and shop roles share the global permissions table with no scope column

- Evidence: 1780070912722_create_shop_roles_table.ts:13-15 defines name and slug with no `unique(['shop_id','slug'])`. 1780071008418_create_shop_role_permissions_table.ts:11-12 references permissions.id. 1780070389008_create_global_role_permissions_table.ts:11-12 references the same table. 1780070239073_create_permissions_table.ts:7-16 has no scope, guard or is_system column. ### IAM-13 [medium; confirmed] Staff assignments allow multiple roles per user per shop and have no membership lifecycle (invite/active/removed) or audit fields

- Evidence: 1780071101792_create_shop_staff_assignments_table.ts:17 `table.unique(['shop_id', 'user_id', 'shop_role_id'])`, :19 `joined_at` is the only temporal column. There are no status, invited_by, invited_at, removed_at or updated_at columns and no primary key.

### IAM-14 [medium; confirmed] Emails are not normalised: uniqueness and login are case-sensitive, and the validator allows longer emails than the column

- Evidence: app/validators/shared.ts:6 `email = () => vine.string().email().maxLength(254)` has no trim or lowercase. app/models/user.ts:14-17 withAuthFinder `uids: ['email']` looks up by exact match. 1761885935168_create_users_table.ts:14 `table.string('email', 100).unique()` is a case-sensitive varchar unique in Postgres. The unique checks at app/validators/auth/user.ts:9 and app/validators/auth/shop.ts:7 use default (case-sensitive) comparison. The column is 100 characters but the validator allows 254.
- Impact: 'Ram@Gmail.com' and 'ram@gmail.com' can become two accounts. Users whose mobile keyboard capitalised the first letter at signup fail to log in with lowercase. ### IAM-15 [medium; confirmed] DB unique and length constraints are not mirrored in validators (500s instead of 422s); recipient_phone is globally unique

- Evidence: app/validators/auth/user.ts:8 `fullName: vine.string()` has no maxLength (column varchar(100), users migration :10). :10 `phone: vine.string().optional()` has no length, format or unique check (column varchar(15) unique, :18). app/validators/auth/shop.ts:8 phone has no unique check, although users.phone and shops.phone are unique (users :18, shops :26). shop.ts:14 shopName has no unique check although shops.name is unique (shops :14). 1780073825111_create_user_addresses_table.ts:17 `recipient_phone … unique()`.
- Impact: A duplicate phone or shop name at signup or registration raises an unhandled unique violation inside the transaction, so the user gets a 500 instead of a field error. Because recipient_phone is globally unique, a customer cannot save home and office addresses with their own number, and two customers cannot ship to the same household phone, which breaks checkout once addresses are built.
- Recommendation: Mirror every DB constraint in Vine: lengths, and uniqueness with normalised comparison. Normalise Nepali phone numbers to E.164 (+977, 98x/97x mobile). Map Postgres unique_violation (23505) to 422 in the exception handler. Drop the recipient_phone unique constraint.

### IAM-16 [medium; confirmed] shopSlug is not normalised or restricted: arbitrary characters, case variants and reserved words are accepted

- Evidence: app/validators/auth/shop.ts:15-20 `shopSlug: vine.string().trim().minLength(1).maxLength(100).unique({ table: 'shops', column: 'slug' })` has no regex, lowercase or reserved list. The shops migration :16 unique is case-sensitive. The slug is a URL segment in '/shop/:shopSlug' (start/routes/shops.ts:27) and in navbar links (inertia/components/navbar/index.tsx:203-205). inertia/pages/shops/register/form.ts:24-26 says the slug will be 'validate[d] or regenerate[d] on server side', but the server does neither. slugify is already a dependency (package.json).
- Impact: Slugs containing '/', '?', '#', spaces, Unicode homoglyphs or case variants ('UrbanDrip' vs 'urbandrip') are accepted. That produces broken URLs and lets a lookalike shop impersonate a real one to phish buyers. Reserved words ('admin', 'register', 'dashboard', 'settings') can collide with future routes.
- Recommendation: Slugify on the server. Enforce a pattern such as `^[a-z0-9](?:[a-z0-9-]{1,48}[a-z0-9])$` and a reserved-word list. Use a unique index on lower(slug). Keep a slug history table to redirect renamed shops.

### IAM-18 [low; corrected] The only ShopTransformer exposes ownerId and the owner's personal email/phone and includes non-active shops

### IAM-19 [low; corrected] Guest carts are keyed by raw session ID (carts.session_id)

- Evidence: database/migrations/1780074042695_create_carts_table.ts:10-13: user_id is nullable and `table.string('session_id', 255).nullable()`. database/README.md: '`session_id` + `user_id` supports guest shopping, login cart merging'. The session guard's login (session_controller.ts:16, new_account_controller.ts:14, shop_registrations_controller.ts:64) regenerates the session ID to prevent fixation.

- Impact: Noisy diffs and merge conflicts in generated files, and third-party scripts in the product repo that reviewers may not audit.
- Recommendation: Decide deliberately: either keep .adonisjs committed (it is needed by `#generated/*` imports before the first dev run) and document it, or regenerate it in CI. Move AI skills to a separate folder or repo, or document that they are tooling-only and excluded from builds.

### MISSED-tooling-ops [high] Catalog, product, cart and checkout routes are guest-only, so logged-in customers and vendors are bounced to '/'

- Evidence: start/routes.ts:17-49 wraps /signup, /login AND /men, /women, /categories/:slug and the product-detail route `/:attributeValue/:productSlug` in `.use(middleware.guest())`. :52-71 does the same for /cart and /checkout. guest_middleware.ts:16-27 redirects any authenticated user to '/'. After login (session_controller.ts:17 redirects home), every navbar link (navbar/index.tsx:104,107,285,288) and category card sends the user back to '/'. The two-segment GET catch-all `/:attributeValue/:productSlug` (routes.ts:43-47) also matches arbitrary two-segment URLs such as /shops/foo and applies the same guest redirect. Because http-server matches routes through @poppinss/matchit (define_config-\*.js:2619), later two-segment GET routes are at risk of being shadowed.
- Recommendation: Apply guest() only to the signup and login routes. Make browse routes public (silent auth is already global, kernel.ts:42). Put the product route under a static prefix (e.g. /p/:slug or /:gender/:productSlug with a matcher). Add a functional test that a logged-in user can GET /men and a product page.

### MISSED-tooling-ops [medium] Login ignores user status and soft-delete, and swallows non-credential errors

- Evidence: session_controller.ts:15 `User.verifyCredentials(email, password)` followed by login(user). There is no check of `status` (suspended or deleted) or `deletedAt`, and the User model (app/models/user.ts) has no soft-delete scope. The catch at :18-23 handles only E_INVALID_CREDENTIALS. Any other error (DB down, hash error) falls through and returns undefined, so the user gets an empty response instead of an error. Also, app/constants/user_status.ts lacks 'pending_verification', the DB default (users migration :25), which every signup receives (new_account_controller.ts:12).
- Recommendation: Reject logins where status is not 'active' (or an allowed set) or deletedAt is set, with a generic message. Rethrow unknown errors. Add 'pending_verification' to UserStatus or change the DB default, and record the user state machine in the data-model and auth design docs.

### MISSED-tooling-ops [low] Dev query logging prints every SQL statement with bindings (password hashes, emails, phones)

- Evidence: config/database.ts:10 `prettyPrintDebugQueries: true` and :60 `debug: app.inDev`. .env.example:5 defaults NODE_ENV=development, so any shared or staging box built from the template logs PII and scrypt hashes to stdout.
- Recommendation: Turn query debug on only through an explicit env flag (e.g. DB_DEBUG) and never on shared environments. Include this in the logging and redaction policy (A5-08).

### MISSED-tooling-ops [low] No production env template, and the only template boots in development mode

- Evidence: .env.example:4-5 has HOST=localhost and NODE_ENV=development. In development mode: handler.ts:10 enables Youch debug pages (stack traces and source), :17 disables status pages, config/session.ts:46 and config/app.ts:77 drop the Secure flag on cookies, and cors.ts:21 reflects any origin. Nothing in the repo documents the production env (APP_KEY rotation, NODE_ENV=production, HOST=0.0.0.0, DB TLS).
- Recommendation: Add a documented production env checklist or template to the ops runbook (NODE_ENV=production, HOST=0.0.0.0, APP_URL https, SESSION_DRIVER set to a server store, DB_SSL). Add a boot-time assertion that refuses to start with NODE_ENV!=production when APP_URL is not localhost.
