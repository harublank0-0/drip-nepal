Status: Draft v1 (2026-09-25)

Reviewed: 2026-09-25 · consistency review 2026-09-30 to 2026-10-04

## 1. Purpose and scope

This document describes the end-to-end journeys that DripNepal must support for customers, sellers and platform staff, and states the acceptance criteria (ACs) that decide whether each journey is done. It covers journeys J-01 to J-20 (ID scheme in [00 §1.3](00-context-assumptions-and-questions.md#13-id-schemes)). J-19 and J-20 are the two R1 journeys added so that every R1 legal obligation has a journey:

- **J-19 Support case / grievance (R1)**: the complaint register with a 15-day decision SLA (FR-ADM-009; E-Commerce Act 2081 s33).
- **J-20 Support-mediated return (R1)**: returns created by support on the customer's behalf (FR-RET-006; Consumer Protection Act 2075 s14, E-Commerce Act s10).

### 1.1 Labels

Every factual claim uses the evidence labels of [00 §1.2](00-context-assumptions-and-questions.md#12-evidence-labels): **[Confirmed]** (product owner, 2026-09-25), **[Verified-repo]** (file:line in this repository), **[Verified-doc]** (official documentation, accessed 2026-09-25), **[Assumption]** (proposed default, reversible), **[Open]** with an OD-xx, and **[Verify-external]** with a VX-xx. Durations, limits and thresholds in this document that do not name a platform setting or a source are **[Assumption]**. They are starting values, tuned in docs/12 and docs/11.

### 1.2 How each journey is written

Each journey has:

1. **A summary table**: actors, release, related FRs, entry points (page routes of [03 §6.1](03-system-architecture.md#61-surfaces-and-rendering-modes) and [06 §2.3](06-api-design.md#23-page-routes-this-document-adds); pages in [08 §2](08-ui-ux-and-design-system.md#2-route-map-and-information-architecture)), preconditions and permissions.
2. **Main success flow**: numbered steps. Each step names the page route and the API `operationId` it calls. Page reads come from Inertia props, which run the same query as the named read operation (ADR-0004). Mutations always go through `/api/v1`.
3. **State coverage**: one row per state class (see §1.3).
4. **Acceptance criteria**: IDs `AC-Jxx-nn`, in Given/When/Then form. Error codes come from [06 §5.2](06-api-design.md#52-codes) and are written `CODE (status)`. State names come from [05 §6](05-order-payment-and-inventory-lifecycles.md#6-state-machines) and are written in code font.
5. **Links**: FRs, operationIds, permissions, tests, milestone.

Test references use the IDs registered in [10 §6](10-testing-and-quality-gates.md#6-test-id-registry): the 14 base IDs (base (10 §6), for example T-INV-003, T-CHK-004, T-SEC-010) and the IDs that 10 added. Otherwise they say "docs/10 test catalogue, area X". This document does not create new numbered test IDs.

### 1.3 State-coverage classes

| Class                     | What the row must answer                                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Success                   | What the actor sees and what the system has stored when everything works.                                                             |
| Empty                     | What happens when there is nothing to show or act on (first use, no results, all filtered out).                                       |
| Validation                | Which inputs are rejected, with which code, and how the error reaches the field.                                                      |
| Permission                | Who is refused, with which code. Other tenants' resources return `NOT_FOUND (404)`, never 403 ([06 §5.2](06-api-design.md#52-codes)). |
| Concurrency               | What happens with two tabs, two staff members, a job racing a human, or a retried request.                                            |
| External-provider failure | Behaviour when email, object storage, the payment gateway or the courier (off-platform) is slow, down or ambiguous.                   |
| Recovery                  | How the actor gets back to a good state after a timeout, closed tab, expired link or partial failure, without creating duplicates.    |

### 4.2 Cross-cutting acceptance criteria (AC-J00)

These apply to every journey. They are tested once per mechanism and sampled per journey (docs/10 test catalogue, areas API, UI, A11Y, SEC).

- **AC-J00-01 Error display.** Given any `/api/v1` call fails, when the response is `application/problem+json`, then the UI shows `detail` in plain language and the `request_id` as "Reference: …", binds each `errors[].field` message to its input via `aria-describedby`, and never shows a stack trace or raw SQL (error contract: ADR-0018). Test: T-API-001 plus docs/10 area UI.
- **AC-J00-02 Session expiry.** Given a session that expired mid-journey, when the next mutation returns `UNAUTHENTICATED (401)`, then the page redirects to `/login?return_to=<path>`. The page never navigates to `return_to` itself: `logIn` receives it, the server validates it with the one helper of [07 TM-14](07-security-threat-model-and-permissions.md#tm-14-unsafe-redirects-and-return-urls) and returns `redirect_to` (default `/`), and the page navigates only to that value (fixes RF-37; T-SEC-017). After login the user returns to that path, and any unsaved form input for checkout, product edit and support case forms is restored from `sessionStorage`.
- **AC-J00-03 Suspension.** Given a user suspended while signed in, when any request arrives, then API calls return `ACCOUNT_SUSPENDED (403)` while the session exists, or `UNAUTHENTICATED (401)` once the `identity.revoke_sessions` job has revoked it, and never a 2xx; page requests redirect to `/login`, with a suspension notice while the session exists. A stamp-only mismatch (password changed or "sign out of all devices" elsewhere) is `UNAUTHENTICATED (401)` ([07 §3.3](07-security-threat-model-and-permissions.md#33-the-per-request-account-check-and-the-suspension-decision), AC-FR-IAM-006-2). Test: T-SEC-010.
- **AC-J00-04 Rate limits.** Given a rate limit is hit, when the API returns `RATE_LIMITED (429)` with `Retry-After`, then the UI disables the action and shows the wait time. It never retries automatically faster than `Retry-After`. Limits are those in [06 §9.1](06-api-design.md#91-rate-limits) [Assumption].
- **AC-J00-05 Formatting.** Given any money or time shown in the English UI, then money uses `Intl.NumberFormat('en-IN', { style: 'currency', currency: 'NPR', currencyDisplay: 'narrowSymbol' })` with Latin digits and lakh grouping (for example "Rs 7,250" or "Rs 12,34,567.50"), and times render in `Asia/Kathmandu` (UTC+05:45) on both the SSR and client passes with identical output. The exact symbol form is [Verify-external VX-12]. The API only ever carries `{amount_minor, currency}` and RFC 3339 UTC timestamps.
- **AC-J00-06 Mobile reach.** Given a 360 × 640 CSS px viewport, then every primary action of every journey is reachable without horizontal scrolling, interactive targets are at least 24 × 24 CSS px (WCAG 2.2 SC 2.5.8), and the header shows a cart entry with the item count. Test: T-A11Y-001 plus docs/10 area UI.
- **AC-J00-07 Double submit.** Given a mutation marked ⚷ in [06 §13](06-api-design.md#13-endpoint-catalogue), when the user taps the button twice or the network retries, then the client sends the same `Idempotency-Key` for the same logical action, disables the button while the request is in flight, and the server executes the action once ([06 §7](06-api-design.md#7-idempotency)).
- **AC-J00-08 Tenant isolation.** Given a customer or seller requests a resource that belongs to another customer or shop, then the response is `NOT_FOUND (404)` with a body identical to a truly missing resource. Tests: T-SEC-001, T-SEC-002.
- **AC-J00-09 Traceability of changes.** Given any state change by a shop member or platform staff member, then exactly one `audit_logs` row is written in the same transaction with `actor_role`, `action`, `subject`, `request_id` and a redacted before/after. Order-visible changes also write an `order_events` row with the right `visibility`.
- **AC-J00-10 No personal data in the client log.** Given any page render, then page props are never written to the browser console or SSR stdout (fixes RF-26), and seller pages receive customer contact only through the transformer allowed for that permission.
- **AC-J00-11 Kill switch.** Given `platform_settings.checkout_enabled = false` (breach response, E-Commerce Directive 2082 s8(2)), then within 60 seconds every storefront page shows the `maintenance_banner` text, and `quoteCheckout`, `placeOrder` and `startOrderPayment` return `PROVIDER_UNAVAILABLE (503)` (the current answer of [06 §5.2](06-api-design.md#52-codes) until the product owner adopts the proposed `CHECKOUT_DISABLED (503)`; see Consistency notes). Payouts (R1.1) are also blocked: `approvePayout`, `markPayoutPaid` and the proposed `revealPayoutAccount` return the same 503, while `markPayoutFailed` and the proposed `cancelPayout` stay available [Assumption, AC-FR-ADM-010-2]. Browsing, account pages and seller order processing keep working. No order, reservation or payment row is written while the switch is off.

2. The visitor opens `/men`. The navigation entry maps to filters `audience=men`. #### Main success flow

1. The server resolves `{publicId}` (8-character Crockford base32) to the product. If the slug part does not match the current slug, it returns 301 to the canonical URL (ADR-0017).
2. Page props (same data as `getProduct`) include: title, description, images grouped by colour, option axes (0 to 2, for example `apparel_size` and `color`), variants with `option_values` (axis code → value code; the `option_signature` column is internal and not sent), price, compare-at price, `in_stock` and `available_capped` (proposed: the available quantity capped at 10, [06 §13.2](06-api-design.md#132-public)); the shop summary; the delivery estimate per zone (`est_min_days`–`est_max_days` from `shop_shipping_rates`); accepted payment methods (COD in R1); and the listing disclosures required by E-Commerce Act s6 (FR-CAT-012).

4. The customer picks a size. The client resolves the variant from its `option_values` and shows its price and "Only 2 left" when `available_capped` is 3 or less [Assumption].
5. The customer picks a quantity from 1 to 10, capped at `available_capped`.
6. The customer taps "Add to cart". The client calls `addCartItem` with `{variant_id, quantity}`. For a guest, the server creates a guest cart and sets its token cookie. A live region announces "Added to cart", and the header count updates.

### J-03 Cart

| Field         | Value                                                                                                                   |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Actors        | Guest, customer                                                                                                         |
| Release       | R1 (M5)                                                                                                                 |
| Related FRs   | FR-CART-001, 002, 003; FR-PROMO-001                                                                                     |
| Entry points  | Header cart icon (visible at all widths), "Added to cart" notice, `/cart`                                               |
| Preconditions | None. A guest cart is created on first add.                                                                             |
| Permissions   | The cart is resolved only from the session user or the guest token cookie. No cart ID is ever accepted from the client. |

#### Main success flow

1. The customer opens `/cart`. Page props (same data as `getCart`) group lines by shop: shop name, lines (image, title, variant label, unit price, quantity, line total), shop subtotal, and a shipping estimate. The estimate uses the default address's district for signed-in customers; otherwise it says "Calculated at checkout".
2. The server revalidates every line on each load (FR-CART-002) and attaches notices: price changed since added (old and new price), only N left, out of stock, or no longer available (product not `published`, variant archived, shop not `active`).
3. The customer changes a quantity with the stepper (`updateCartItem`) or removes a line (`removeCartItem`). Totals are recomputed server-side in integer paisa and returned with the new `cart.version`.
4. A guest signs in or signs up (J-04). The guest cart merges into the user's active cart: lines for the same variant add their quantities, capped at 10; distinct lines are added up to 50 lines; the guest cart becomes `merged`. A notice lists any lines that could not be merged.
5. The customer taps "Checkout" and continues in J-05. If any line is unavailable, a dialog asks them to remove unavailable items first. One tap removes them all.

#### State coverage

| Class                     | Behaviour                                                                                                                                                                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Success                   | Lines grouped by shop, totals match the server, notices shown for changed lines.                                                                                                                                                                       |
| Empty                     | "Your cart is empty" with links to Men, Women and recently viewed items. After an order the old cart is `converted`, and the next add creates a new cart.                                                                                              |
| Validation                | `quantity` outside 1–10 → `VALIDATION_FAILED (422)` on `quantity`. A 51st line → `VALIDATION_FAILED (422)` with code `max_lines` [Assumption: code value owned by docs/06]. More than 60 adds per minute → `RATE_LIMITED (429)`.                       |
| Permission                | A `cartItemId` that is not in the caller's cart → `NOT_FOUND (404)` (T-SEC-006). Suspended user → `ACCOUNT_SUSPENDED (403)`.                                                                                                                           |
| Concurrency               | Two tabs: tab A removes a line while tab B changes its quantity → B gets `NOT_FOUND (404)` and reloads the cart. Every change increments `carts.version`, and checkout compares it (`CART_CHANGED (409)`, J-05). Quantity updates are last-write-wins. |
| External-provider failure | No external dependency. A database error returns 503. The optimistic UI rolls back and shows "Couldn't update your cart. Try again."                                                                                                                   |
| Recovery                  | The guest token is a random value in an httpOnly cookie; only its hash is stored (fixes RF-19). The guest cart survives browser restarts until `expires_at` (30 days [Assumption]). After login the merged cart is shown with the merge notice.        |

#### Acceptance criteria

- **AC-J03-01** Given a signed-in customer or a guest with items, when `/cart` is requested (SSR and client navigation), then it renders 200 with the server cart and no client exception (fixes RF-10).
- **AC-J03-02** Given a guest cart with variant V × 3 and a user cart with V × 8 and W × 1, when the guest signs in, then the user cart holds V × 10 and W × 1, the guest cart status is `merged`, and the notice says V was capped at 10.
- **AC-J03-03** Given a line added at Rs 1,500 whose variant is now Rs 1,650, when the cart loads, then the line shows "Price changed from Rs 1,500 to Rs 1,650", and the totals use Rs 1,650. Given a request that includes a `price` or `unit_price_minor` field, then it is rejected with `VALIDATION_FAILED (422)` and `errors[].code = unknown_field` ([06 §3.5](06-api-design.md#35-input-validators-are-allowlists)), and the cart is unchanged (T-SEC-003).
- **AC-J03-04** Given a line whose shop is `suspended`, when the cart loads, then the line is flagged "No longer available", excluded from totals, and "Checkout" first asks the user to remove it.
- **AC-J03-05** Given the stepper, when the user tries to go above 10, then the plus control is disabled. Given a direct API call with `quantity = 11`, then the response is `VALIDATION_FAILED (422)`.
- **AC-J03-06** Given lines with compare-at prices, then the cart total equals the sum of `unit price × quantity` plus shipping estimates, with savings shown for information only and never subtracted again (fixes RF-16).
- **AC-J03-07** Given a 360 px wide viewport, then the header cart control is visible, is at least 24 × 24 CSS px, and its accessible name includes the item count, for example "Cart, 3 items" (fixes RF-28).
- **AC-J03-08** Given a guest cart cookie and no cart activity since, when the browser is reopened 29 days later, then the cart and its lines are intact. Once 30 days pass after the last cart change (`carts.expires_at`, [04a §10.1](04a-data-dictionary-tables.md#101-carts)), the expiry job sets the cart to `abandoned` and a new empty cart is created on the next add.

### J-04 Sign up & verify

| Field         | Value                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------- |
| Actors        | Guest; system (email job)                                                                           |
| Release       | R1 (M1). Phone OTP is R2 (FR-IAM-010). Social login is R3.                                          |
| Related FRs   | FR-IAM-001, 002, 003, 013; FR-CART-001 (merge on login)                                             |
| Entry points  | `/signup`, `/login`, checkout gate (`/login?return_to=/checkout`), `/sell` gate, `/verify-email`    |
| Preconditions | Email provider configured (OD-08). Rate limiter uses the database store (OD-10 resolved).           |
| Permissions   | Guest only for `/signup` and `/login`. A signed-in user who opens them is redirected to `/account`. |

#### Main success flow

1. The guest opens `/signup` and enters full name, email, password (10–128 characters), and optionally a Nepal mobile number. The marketing-email checkbox is unchecked by default (FR-IAM-013; Advertisement (Regulation) Act 2076 s10). An age confirmation ("I am 18 or older") must be ticked (AC-FR-IAM-001-1 [Assumption A-26; Open OD-24]).
2. Submit calls `signUp`. The server normalises the email (trimmed, lower-cased, `citext`) and returns **202** with the same body whether or not the email already exists (enumeration defence for RF-38: AC-FR-IAM-001-2, [07 TM-09](07-security-threat-model-and-permissions.md#tm-09-account-recovery-abuse-and-enumeration)). Neither branch creates a session. For a new email it creates the user with status `pending_verification`, a fresh `security_stamp`, and a `user_tokens` row (`purpose = email_verification`, stored as a hash, expiring in 24 h [Assumption]). It then queues the verification email in the same transaction (ADR-0010). For an existing email it queues an "Someone tried to sign up with your email" notice instead.
3. The page moves to `/verify-email`: "We sent a link to r•••@gmail.com". A resend button calls `resendEmailVerification` (limit 3 per hour).
4. The user opens the link. `/verify-email?token=…` calls `confirmEmail`. The token is consumed, `email_verified_at` is set and the status becomes `active`.
5. The page redirects to `/login` with the email prefilled and the original `return_to` kept. Login calls `logIn`: the session ID is regenerated, the session is tagged with the user ID ([07 §3.1](07-security-threat-model-and-permissions.md#31-guard-store-and-cookie)), the `security_stamp` is stored in the session, and the guest cart merges (J-03 step 4).
6. Platform staff are sent to `/mfa` next (`verifyMfaChallenge`), because TOTP is mandatory for staff (FR-IAM-007).
7. If the account has no phone, the checkout page asks for one before placing an order (J-05). It is saved with `updateMe`.

| Validation                | Invalid email format, password shorter than 10 or longer than 128, or a mobile not matching `^9[678]\d{8}$` after stripping `+977`, `977`, spaces and hyphens → `VALIDATION_FAILED (422)` with field errors. | Permission                | Login by a `suspended` user with the correct password → `ACCOUNT_SUSPENDED (403)`. With a wrong password, the generic "Invalid email or password" is shown (no status leak). `anonymized` accounts cannot log in.                                                                                                                                                                                                                                                                   |
| Concurrency               | Two signups with the same email at once: the unique index on `users.email` lets one insert win; both callers get the same 202. Double-clicking the verification link: the second call finds the token consumed and the user already verified, and shows "Your email is already verified" (idempotent, no error).                                                                                                                                                                    |
| External-provider failure | Email provider down: the `notification_deliveries` row stays `queued` and the job retries with backoff; after the final attempt the job goes to the dead-letter queue and an alert fires, and the row is sent once the queue is redriven (a transport error never sets `failed`, [05 §8.14](05-order-payment-and-inventory-lifecycles.md#814-email-outage); docs/11). A user who logs in before verifying gets a session with a "Verify your email" banner; checkout and `/sell` are refused with `EMAIL_NOT_VERIFIED (403)` and link to resend.                                                                                                                                                                                                                                   |

- **AC-J04-10** Given 3 resend requests in an hour, when a 4th is made, then `RATE_LIMITED (429)` is returned and no email is queued.

The worked example used below: a customer in Lalitpur (zone `ktm_valley`) buys 2 × T-shirt at Rs 1,200 from shop A (shipping Rs 100) and 1 × sneakers at Rs 4,500 from shop B (shipping Rs 250). The grand total is Rs 7,250 (`725000` paisa), split into shop orders `DN-7Q4K2MX-1` (Rs 2,500) and `DN-7Q4K2MX-2` (Rs 4,750). Amounts are illustrative.

#### Main success flow

1. `/checkout` requires authentication. Unauthenticated → `/login?return_to=/checkout`. Page props carry the cart with its `version`, saved addresses (`listAddresses`) and an initial quote for the default address.
2. **Address.** The customer picks a saved address or adds one (`createAddress`): recipient name, recipient mobile, then Province → District → Local level → Ward → Area/tole → Landmark. The cascading selects use `listProvinces`, `listDistricts` and `listLocalLevels`. The ward must be between 1 and the local level's `ward_count` (up to 33, for example Pokhara). Nepal Post data, <https://giwmscdnone.gov.np/media/pdf_upload/Postal%20Code_wteggid.pdf>, accessed 2026-09-25; seeding source VX-10.
3. **Quote.** `quoteCheckout {address_id, payment_method: "cod"}` returns per-shop groups (lines, shipping fee for the address zone, delivery window, shop total), the grand total, COD eligibility, the `cart_version` that `placeOrder` echoes, and `problems[]` with any line or shop problems, such as `delivery_not_available` for a shop that does not deliver to the address district ([06 §13.4](06-api-design.md#134-customer)).
4. **Review** (WCAG 2.2 SC 3.3.4 error prevention for financial transactions). The page shows each shop group, the address, and "Cash on delivery: you will pay each shop's courier separately: Rs 2,500 to shop A and Rs 4,750 to shop B. No extra charge at the door." (E-Commerce Directive 2082 s8(3), [05 §3.3](05-order-payment-and-inventory-lifecycles.md#33-shipping-fee-per-shop-order)). It also links the return and refund policy. When the review renders, the client creates an `Idempotency-Key` (UUIDv4) and stores it in `sessionStorage` keyed by cart version and expected total.
5. **Place order.** `placeOrder` is sent with `Idempotency-Key` and `X-XSRF-TOKEN`, body `{address_id, payment_method: "cod", expected_grand_total_minor: 725000, cart_version, customer_note?}`. The server runs the checkout algorithm of [05 §4](05-order-payment-and-inventory-lifecycles.md#4-checkout-the-placeorder-algorithm): key row first, cart lock, availability, coverage, pricing, COD limits, reservations sorted by `variant_id`, then orders, shop orders, items with snapshots, payments, events and outbox jobs, all in one transaction.
6. Response **201** `{number: "DN-7Q4K2MX", status: "placed", shop_orders: [...], payment_id: null, next_action}` ([06 §14.4](06-api-design.md#144-checkout-quotecheckout-then-placeorder)). The parent order is `placed`. Each shop order is `awaiting_acceptance` with `acceptance_due_at = placed_at + vendor_acceptance_sla_hours` (default 48, 04a §15.1 [Assumption A-07; OD-19]), and the jobs `orders.acceptance_timeout` (at `acceptance_due_at`) and `orders.acceptance_reminder` (at `acceptance_due_at − least(24 h, vendor_acceptance_sla_hours / 2)`, which is 24 h before the deadline at the default) are sent in the same transaction ([05 §4.7](05-order-payment-and-inventory-lifecycles.md#47-what-runs-after-commit), [§6.1](05-order-payment-and-inventory-lifecycles.md#61-shoporder); AC-FR-ORD-004-2). Each shop order has a COD payment `awaiting_collection` for its total. Reservations are `committed`. The cart is `converted`.
7. The client navigates to `/checkout/complete/DN-7Q4K2MX` and shows both shop order numbers, the amount to pay each courier, delivery windows and a link to `/account/orders/DN-7Q4K2MX`.
8. After commit, jobs send the customer "Order placed" email and a "New order" email to each shop's owner and order fulfillers. The seller dashboard badge updates by polling (FR-NOT-003).

#### Acceptance criteria

- **AC-J05-01** Given the worked example and `vendor_acceptance_sla_hours` at its default of 48, when `placeOrder` succeeds, then: one `orders` row with `status = placed` and `grand_total_minor = 725000`; two `shop_orders` in `awaiting_acceptance` with `acceptance_due_at = placed_at + 48 h`; two COD `payments` in `awaiting_collection` with amounts 250000 and 475000; `inventory_reservations` `committed` for every line; `carts.status = converted`; and exactly one `order.placed` event. The page is reachable while signed in (fixes RF-02).
- **AC-J05-02** Given any placed order, then `grand_total_minor = items_subtotal_minor + shipping_total_minor - discount_total_minor` and equals the sum of shop order `total_minor`. Given a request body that contains `unit_price_minor`, `shop_id` or `commission_rate_bp`, then it is rejected with `VALIDATION_FAILED (422)` and `errors[].code = unknown_field` for each such field, and no order is written; the stored values always come from the server (AC-FR-CHK-002-3, [06 §3.5](06-api-design.md#35-input-validators-are-allowlists); T-SEC-003; fixes RF-16).
- **AC-J05-03** Given a 201 for key K, when the identical request with K is sent again within 72 h, then the response is byte-identical apart from `X-Request-Id`, and the order count is unchanged. Given 5 concurrent requests with K, then exactly one order exists and all 5 responses carry the same order `number` (T-CHK-004).
- **AC-J05-04** Given key K was used with body B1, when body B2 (different expected total) is sent with K after B1 committed, then `IDEMPOTENCY_KEY_REUSED (422)`. Given no key header, then `IDEMPOTENCY_KEY_REQUIRED (400)`.
- **AC-J05-05** Given a variant with `on_hand = 1, reserved = 0` in two carts, when both customers place orders concurrently, then exactly one succeeds, the other gets `OUT_OF_STOCK (409)` listing that variant with `available_quantity = 0`, and at no time is `reserved > on_hand` (T-INV-003).
- **AC-J05-06** Given the vendor raised the sneakers from Rs 4,500 to Rs 4,700 after the quote, when the customer places the order with `expected_grand_total_minor = 725000`, then `PRICE_CHANGED (409)` is returned with a new quote of `745000`, no rows are written, and the review step highlights the changed line and requires a new confirmation.

**Provider facts that shape this journey** [Verified-doc, [research: nepal-payments](research/nepal-payments.md), accessed 2026-09-25]:

- Khalti KPG-2: server-side initiate returns `pidx`, `payment_url` and `expires_at`. The return redirect is **unsigned** and must be confirmed with the lookup API; only `Completed` is success. There is no server-to-server webhook. The amount must be above Rs 10. Before KYC, merchants cannot take more than NPR 200 per transaction. The docs contradict themselves on link expiry (60 vs 30 minutes), so `expires_at` from each response is used. <https://docs.khalti.com/khalti-epayment/>, <https://docs.khalti.com/getting-started/>.
- eSewa ePay v2: a signed browser form POST. The success redirect carries a signed Base64 payload. `failure_url` is used for both FAILURE **and PENDING**. The status-check API is the source of truth. There is no server-to-server webhook and no refund API. Payment must be completed within about 5 minutes. <https://developer.esewa.com.np/pages/Epay>.
- The NRB Unified Directive on Payment Systems 2082 caps wallet balances at NPR 50,000, so large carts can fail on wallet balance ([research: nepal-payments](research/nepal-payments.md)).

Design consequence (ADR-0012, [05 §9.4](05-order-payment-and-inventory-lifecycles.md#94-reconciliation-schedule)): the return handler plus a server-to-server lookup is the primary confirmation path. A reconciliation job that polls every non-terminal payment is **required**. Redirect data is never trusted alone. The webhook endpoint exists only for providers that notify server-to-server (for example eSewa Intent) and follows the same verify-by-lookup rule.

#### Main success flow

1. Steps 1–4 of J-05, with payment method `khalti` (or `esewa`). The quote hides Khalti when the total is Rs 10 or less and shows a hint for carts above Rs 50,000.
2. `placeOrder` ⚷ → 201 `{number, status: "awaiting_payment", shop_orders, payment_id, next_action}` ([06 §14.4](06-api-design.md#144-checkout-quotecheckout-then-placeorder)); the order page reads the payment status. In the transaction: shop orders are `awaiting_payment`; reservations are `held` with `expires_at = now() + reservation_ttl_minutes + 10 min` (default 30 + 10, 04a §15.1), later moved to provider session expiry + 10 min when the provider reference is stored ([05 §5.3](05-order-payment-and-inventory-lifecycles.md#53-creating-reservations)), never shortened and never beyond `orders.placed_at + 90 min` across retries [Assumption, 05 §4.8; OD-28]; and one `initiated` payment for the grand total has per-shop `payment_allocations`.
3. After commit, outside the transaction, the server calls the provider. For Khalti: initiate with `purchase_order_id = payment.id`, the amount in paisa, and `return_url = https://<host>/payments/khalti/return?attempt=<payments.id>`; it stores `pidx` and `expires_at`, and the payment becomes `pending`. For eSewa: the server builds and signs the form fields (`transaction_uuid` unique per attempt, HMAC-SHA256 over `total_amount,transaction_uuid,product_code`), and the payment becomes `pending` when the auto-submitting form page is served, with `payments.expires_at = form rendered + reservation_ttl_minutes` because eSewa publishes no session expiry beyond its 5-minute payment window [Assumption; Verify-external VX-06]. `next_action` is `{type: "redirect", url}` or `{type: "form_post", ...}`.
4. The customer pays in the wallet.
5. The browser returns to `GET /payments/{provider}/return?attempt=<payments.id>`. The handler loads the payment by the `attempt` parameter (our `payments.id`) and checks the returned `pidx` or `transaction_uuid` against the one **DripNepal stored**; a mismatch is treated as an unknown status. Only when `attempt` resolves to a gateway payment of that provider does it record a `provider_events` row (`kind = return`, key `return:<attempt key>:<provider status>`, unique on `(provider, provider_event_key)`); an unmatched return stores nothing, changes nothing and leaves one `provider.message_rejected` log line. For a matched return it then calls the provider lookup server-to-server with the stored identifier ([06 §12.2](06-api-design.md#122-return-route-contract-get-paymentsproviderreturn)). It ignores the `status` and `amount` in the URL.
6. Lookup says `Completed` (Khalti) or `COMPLETE` (eSewa) and the amount equals `payments.amount_minor`. In one transaction: the payment becomes `captured`; `captured_minor` and allocations are set; reservations become `committed`; shop orders become `awaiting_acceptance` with `acceptance_due_at`; the parent becomes `placed`; `order_events` are written and emails queued. The browser is redirected to `/checkout/complete/{orderNumber}`.
7. The `payments.verify` job runs the same lookup for every `pending` payment on the [05 §9.4](05-order-payment-and-inventory-lifecycles.md#94-reconciliation-schedule) schedule: every 1 minute for the first 30 minutes after the redirect, every 5 minutes until 2 h, every 30 minutes until 24 h, then `needs_review` with a finance alert. `payments.reconcile_sweeper` (every 5 minutes) re-enqueues lost verify jobs, `inventory.expire_reservations` (every minute) resolves expired holds by the same lookup, and `payments.daily_reconciliation` (06:00 Asia/Kathmandu) compares the previous day's captures with the provider statement. Khalti `Pending` moves the payment to `needs_review` at once and polling continues ([05 §8.5](05-order-payment-and-inventory-lifecycles.md#85-payment-timeout-with-unknown-provider-outcome-r11)).

| Concurrency               | Return handler, page refresh and job racing on one payment: the `provider_events` unique key and the compare-and-set `UPDATE … WHERE status = 'pending'` allow one capture, one ledger-relevant event and one email (T-PAY-005). `startOrderPayment` while an attempt is still `pending` → the server looks it up first; if still pending → `CONFLICT (409)` with the resume URL until `expires_at`. The partial unique index allows only one live gateway attempt per order.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| External-provider failure | **Customer closes the browser mid-payment:** there is no return; the job captures on its next run after the provider completes. **Provider timeout with unknown outcome:** a lookup timeout or 5xx keeps the payment `pending`, increments `verification_attempts` and schedules `next_verification_at`; the customer sees "We're confirming your payment" (the page polls `getMyOrder` every 5 s for 2 minutes, then offers a manual refresh). After 24 h of attempts → `needs_review` plus an alert. While the outcome is unknown the reservations stay `held`, also past `expires_at`, until 24 h after `expires_at` for a payment in `needs_review` (Case C of [05 §5.4](05-order-payment-and-inventory-lifecycles.md#54-expiration-job), reason `needs_review_timeout`); unknown outcomes never cancel a shop order. **Initiate fails** (timeout or 5xx): the order stays `awaiting_payment` with the payment `initiated`; the 201 carries `next_action = retry_payment`; "Try again" calls `startOrderPayment`, which returns `PROVIDER_UNAVAILABLE (503)` while the provider is still down. An attempt whose initiate response never arrived has no `pidx` the customer could pay against, so the retry marks it `cancelled` (superseded) and creates attempt `attempt_no + 1` with a new `payments.id` ([05 §4.8](05-order-payment-and-inventory-lifecycles.md#48-gateway-initiation-after-commit-r11)). **eSewa `failure_url`:** treated as a hint only; the status check decides, and `PENDING` keeps polling. **Signature mismatch:** the eSewa payload is stored with `signature_valid = false` and processed no further; the payment is still resolved by the scheduled status check on the stored `transaction_uuid`. **Amount mismatch** in a lookup: no capture; the payment goes to `needs_review` and finance is alerted.                                                                                                                                                                                                                                                                                            |
| Recovery                  | **Payment captured after reservation expiry (late capture, [05 §8.4](05-order-payment-and-inventory-lifecycles.md#84-payment-success-after-reservation-expiry-r11)):** at `expires_at` the expiry job looks the payment up. A definitive non-success cancels the shop orders with reason `payment_expired` and releases the stock. An unknown outcome keeps the stock `held`; only a payment in `needs_review` loses its hold 24 h after `expires_at` (reason `needs_review_timeout`), while its shop orders stay `awaiting_payment`. If a later lookup says `Completed`, the payment becomes `captured` (provider truth wins) and each shop order re-reserves its lines with the conditional update inside its own savepoint (movement reason `late_capture`). Shop orders that re-reserve fully proceed to `awaiting_acceptance` with a new `acceptance_due_at`. Shop orders that cannot are `cancelled` with reason `stock_unavailable_after_payment`, and a system refund of their allocation is created and auto-approved (J-14). A success found later on an `expired`, `failed` or `cancelled` attempt that had reached the provider, when that attempt was superseded by a newer attempt or its shop orders are terminal, is a superseded late capture: the attempt becomes `captured` with `is_late_capture` (proposed, [04a §12.1](04a-data-dictionary-tables.md#121-payments)), the shop orders and the newer attempt are untouched, and one refund with reason `late_capture` per allocation of that attempt, each for the allocation's captured amount, waits in `requested` for finance approval ([05 §6.4](05-order-payment-and-inventory-lifecycles.md#64-payment-gateway-r11), [§8.4](05-order-payment-and-inventory-lifecycles.md#84-payment-success-after-reservation-expiry-r11)). The latest attempt of an order whose shop orders are still `awaiting_payment` pays the order instead, as described above. Money is never kept silently. The customer can also reopen `/account/orders/{orderNumber}` and use "Pay now" (`startOrderPayment`) while the order is `awaiting_payment` and its reservation is live. |

#### Acceptance criteria

- **AC-J06-01** Given a Khalti return with `status=Completed` whose `attempt` resolves to no gateway payment of that provider, then no payment changes state, no `provider_events` row is stored, and one `provider.message_rejected` log line is written (T-SEC-021; [06 §12.2](06-api-design.md#122-return-route-contract-get-paymentsproviderreturn)). Given a return with `status=Completed` for a stored `pidx` whose lookup says `Pending`, then the payment is not captured, whatever the URL says, and moves to `needs_review` as in AC-J06-16.
- **AC-J06-02** Given the customer paid and closed the browser before the redirect, then the reconciliation job captures the payment within 2 minutes of provider completion during the first 30 minutes, the order becomes `placed`, and the confirmation email is sent once.
- **AC-J06-03** Given the return handler, a page refresh and the job process the same completed payment concurrently, then there is exactly one `pending → captured` transition, one `order.placed` event, one email, and one set of reservation commits (T-PAY-005).
- **AC-J06-04** Given the lookup times out 3 times, then the payment stays `pending` with `verification_attempts = 3` and a later `next_verification_at`, and no shop order or reservation changes. Given the outcome is still unknown 24 h after the redirect (end of the `payments.verify` schedule), then the status is `needs_review`, finance is alerted within 5 minutes, and the customer page says the payment is being confirmed and gives a support-case link.
- **AC-J06-05** Given no capture by the reservation's `expires_at` and a final lookup of `Expired` or `User canceled` (Khalti), or `NOT_FOUND` or `CANCELED` (eSewa), then held reservations are `released` with `release` movements, shop orders are `cancelled` with reason `payment_expired`, the parent is `cancelled`, and the customer gets a "Payment not completed" email.
- **AC-J06-06** Given a lookup returns `Completed` after the reservation was released and one of two shops' variants has since sold out, then the payment is `captured`, the other shop's order proceeds to `awaiting_acceptance` with new `committed` reservations (movement reason `late_capture`), the sold-out shop's order is `cancelled` with reason `stock_unavailable_after_payment`, and one system refund equal to that shop's allocation exists, auto-approved (`approved`, `refunds.execute` queued), with reason `stock_unavailable_after_payment`.
- **AC-J06-07** Given the initiate call fails, then `placeOrder` still returns 201 with `status = awaiting_payment` and `next_action.type = retry_payment`, and `startOrderPayment` returns `PROVIDER_UNAVAILABLE (503)` until the provider responds.
- **AC-J06-08** Given a `pending` attempt, when `startOrderPayment` is called, then it looks up the existing attempt first and returns `CONFLICT (409)` with the resume URL if it is still pending. It creates attempt `attempt_no + 1` with a new provider identifier only after the previous attempt is confirmed not completed.
- **AC-J06-09** Given eSewa redirects to `failure_url` and the status check returns `PENDING`, then the order is not cancelled, stock is not released before `expires_at`, and polling continues.
- **AC-J06-10** Given an eSewa success payload whose signature does not match (constant-time comparison), then no capture happens from that payload, the event is stored with `signature_valid = false`, and the status check by the stored `transaction_uuid` still runs.
- **AC-J06-11** Given a lookup `total_amount` that differs from `amount_minor`, then the payment goes to `needs_review` and is not captured.
- **AC-J06-12** Given a cart total of Rs 10 or less, then Khalti is not offered, and `placeOrder` with `payment_method = khalti` returns `VALIDATION_FAILED (422)`.
- **AC-J06-13** Given a provider that notifies server-to-server (eSewa Intent, if chosen), when `receivePaymentWebhook` is called, then the raw event is stored, 200 is returned after the durable insert, and the state changes only after a lookup in the job. Duplicate deliveries are deduplicated by `(provider, provider_event_key)`.
- **AC-J06-14** Given an order `awaiting_payment` with a `pending` attempt, when the customer tries `cancelMyShopOrder`, then a lookup runs first; unless it shows a definitive non-success, `CONFLICT (409)` "Payment in progress" is returned and nothing changes, as in AC-J07-09 ([05 §6.1](05-order-payment-and-inventory-lifecycles.md#61-shoporder), [06 §13.4](06-api-design.md#134-customer)). Given the attempt is terminal and not captured, or the lookup shows a definitive non-success, then every shop order of the order is cancelled with reason `customer_cancelled`.
- **AC-J06-15** Given any page or log line, then provider secret keys, the eSewa signing secret and full provider payloads with customer mobile numbers never appear in Inertia props or logs (redaction list in docs/07).
- **AC-J06-16** Given a Khalti lookup returns `Pending`, then the payment moves to `needs_review` at once, finance is alerted, the reservations stay `held`, the shop orders stay `awaiting_payment`, and polling continues ([05 §8.5](05-order-payment-and-inventory-lifecycles.md#85-payment-timeout-with-unknown-provider-outcome-r11)).
- **AC-J06-17** Given a payment in `needs_review` whose reservations reached `expires_at + 24 h`, when `inventory.expire_reservations` runs, then the reservations are `released` with reason `needs_review_timeout`, the payment stays `needs_review`, and the shop orders stay `awaiting_payment`.
- **AC-J06-18** Given a payment in `pending` or `needs_review`, then the "Pay again" button is hidden and `startOrderPayment` returns `CONFLICT (409)` with detail "Your previous payment is still being processed", unless its lookup returns a definitive non-success.
- **AC-J06-19** Given reconciliation finds `COMPLETE` for an attempt recorded as `expired` whose shop orders are `cancelled`, then the attempt becomes `captured` with `is_late_capture`, the shop orders stay `cancelled`, and one `late_capture` refund per allocation of that attempt exists, each for the allocation's captured amount, in `requested` waiting for finance approval (T-PAY-004).
- **AC-J06-20** Given retries of `startOrderPayment`, then held reservations are never extended beyond `orders.placed_at + 90 min` [Assumption, 05 §4.8; OD-28]; after that the order expires with `payment_expired` and the customer must check out again.
- **AC-J06-21** Given attempt 1 `expired`, attempt 2 `captured` and the shop orders `awaiting_acceptance`, when a later lookup finds attempt 1 `Completed`, then attempt 1 becomes `captured` with `is_late_capture`, one `late_capture` refund per allocation of attempt 1 waits in `requested` for finance approval, and attempt 2, the shop orders and their reservations are unchanged. Given the same for an attempt recorded as `cancelled` after it reached the provider, then the result is the same ([05 §8.4](05-order-payment-and-inventory-lifecycles.md#84-payment-success-after-reservation-expiry-r11); T-PAY-004).

**Links:** operationIds `placeOrder`, `startOrderPayment`, `getMyOrder`, `cancelMyShopOrder`, `receivePaymentWebhook`; page route `/payments/{provider}/return`. Permissions: customer self; `platform.orders.view` and `platform.refunds.approve` for needs-review handling. Tests: T-PAY-005, T-PAY-004, T-SEC-021, T-CHK-004, T-INV-003; docs/10 test catalogue, area PAY (contract tests against recorded sandbox responses). ADR-0012, ADR-0010. OD-02, OD-03, VX-01, VX-06, VX-07. Milestone M8.

#### Main success flow

1. `/account/orders` lists orders newest first (`listMyOrders`, cursor pagination): number, date (Asia/Kathmandu), derived parent status, grand total and shop count.
2. `/account/orders/{orderNumber}` (`getMyOrder`) shows one card per shop order: shop name snapshot, item snapshots, shop order status, shipment status, courier name, tracking number, a "Track with {courier}" link (https only), expected delivery window, the COD amount to pay, and the customer-visible `order_events` timeline.
3. While a shop order is `awaiting_acceptance`, the card shows "Cancel". The dialog asks for a reason from the AC-FR-ORD-002-2 list (`changed_mind`, `ordered_by_mistake`, `found_cheaper`, `delivery_too_slow`, `other`). Confirm calls `cancelMyShopOrder` ⚷. The shop order becomes `cancelled` (`customer_cancelled`); its reservations are `released` with `release` movements; its COD payment goes from `awaiting_collection` to `cancelled`; the parent status is recomputed in the same transaction. The customer and the shop get emails.
4. After acceptance, "Cancel" is replaced by "Need help with this order?", which opens a support case (J-19). If the vendor accepted a moment before the customer's cancel, the cancel returns `INVALID_STATE_TRANSITION (409)` and the page says "Shop B has already confirmed your order. To cancel now, contact support" with a button that opens a support case ([05 §8.12](05-order-payment-and-inventory-lifecycles.md#812-customer-cancels-while-the-vendor-is-accepting)).
5. **Delivery is late** (AC-FR-ORD-005-4; E-Commerce Act s16(d), s16(g) [Verify-external VX-02]). A shop order is late when it is not `delivered` by `est_max_days_snapshot` days after it entered `awaiting_acceptance` ([05 §6.1](05-order-payment-and-inventory-lifecycles.md#61-shoporder)): that moment is `orders.placed_at` for COD and the capture of the attempt that paid the order for gateway orders, and a same-day promise (`est_max_days_snapshot = 0`) counts as one 24-hour period (AC-FR-ORD-005-4; T-ORD-010). The card then shows "Get help: delivery is late", which calls `openSupportCase` with category `delivery` and the shop order prefilled, and continues in J-19. There is no self-service late-delivery cancel button in R1.
6. **Gateway orders (R1.1)** in `awaiting_payment` can be cancelled only as a whole, because all shop orders share one payment: `cancelMyShopOrder` cancels every shop order of the order with `customer_cancelled` when the payment is `initiated` without a provider reference or a lookup shows a definitive non-success ([05 §6.1](05-order-payment-and-inventory-lifecycles.md#61-shoporder)).

#### Acceptance criteria

- **AC-J07-01** Given customer X, when they call `getMyOrder` for customer Y's order number, then `NOT_FOUND (404)`, and `listMyOrders` never includes Y's orders (T-SEC-002).
- **AC-J07-02** Given a shop order in `accepted`, when `cancelMyShopOrder` is called, then `INVALID_STATE_TRANSITION (409)` and the UI shows the support-case link.
- **AC-J07-03** Given a two-shop order where shop order 1 is cancelled, then shop order 2 is unaffected and the parent stays `placed` or `in_progress`. Given both are cancelled, then the parent is `cancelled`.
- **AC-J07-04** Given a cancelled shop order with 2 units reserved, then `inventory_items.reserved` decreases by 2 and one `release` movement per line references the shop order.
- **AC-J07-05** Given concurrent `cancelMyShopOrder` and `acceptShopOrder` on one shop order, run 50 times, then each run ends with exactly one of `cancelled` or `accepted` and never both side effects.
- **AC-J07-06** Given a shipment with a tracking URL, then the link opens in a new tab with `rel="noopener noreferrer"`, and dates show in Asia/Kathmandu.
- **AC-J07-07** Given a shop order with `est_max_days_snapshot = 5` that entered `awaiting_acceptance` at 2026-10-01T10:00+05:45 and is not `delivered`, when the customer opens the order page after 2026-10-06T10:00+05:45, then the card shows "Get help: delivery is late", and the action opens a support case with category `delivery`, the shop order linked and `due_at = created_at + 15 days`. Before that moment the action is not shown. Given a same-day promise (`est_max_days_snapshot = 0`), then the action appears 24 h after the shop order entered `awaiting_acceptance`, not at once (AC-FR-ORD-005-4; T-ORD-010).
- **AC-J07-08** Given the late-delivery case and a shipment that is not yet `shipped`, when support cancels at the customer's request, then the shop order is `cancelled` with reason `admin_cancelled` (`adminCancelShopOrder`), its reservations are released and the COD payment is `cancelled`. - **AC-J07-09** Given a two-shop gateway order in `awaiting_payment` whose payment is `initiated` without a provider reference, when the customer cancels, then both shop orders are `cancelled` with reason `customer_cancelled` and the payment is `cancelled`. Given the payment is `pending` and the lookup is inconclusive, then `CONFLICT (409)` and nothing changes.

### J-08 Shop application & approval

| Field         | Value                                                                                                                                                                                         |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Actors        | Applicant (an existing customer who becomes the owner); catalog moderator or platform admin; system (emails)                                                                                  |
| Release       | R1 (M2)                                                                                                                                                                                       |
| Related FRs   | FR-SHOP-001, 002, 003, 004, 010, 012, 013, 014                                                                                                                                                |

| Permissions   | Applicant becomes `shops.owner_user_id`. Reviewers need `platform.shops.review` and an MFA-verified session.                                                                                  |

E-Commerce Act 2081 s16 requires each seller to sign a written or electronic contract with the intermediary before selling, and to provide business registration evidence, full name and address, a grievance mechanism, return and refund details, and PAN or VAT details. Section 14 requires the intermediary to have that agreement before listing (<https://giwmscdnone.gov.np/media/files/E-Commerce%20Act%2C%202081_yr7k9o5.pdf>, accessed 2026-09-25; legal confirmation VX-02). This journey captures all of it before the shop can list.

#### Main success flow

1. `/sell` requires sign-in (`/login?return_to=/sell`). Unverified users see the verify prompt. An existing customer applies with their current account; no new user is created (fixes RF-21).
2. **Shop basics:** name (not globally unique), slug (lowercase `a-z0-9` and hyphens, 3–40 characters, not reserved [Assumption; list in docs/07]), description, shop contact email and phone, and 1–3 shop categories [Assumption] from the active list (`shop_category_codes`, a proposed input). The contact can differ from the owner's personal contact and accepts a mobile or a landline normalised to E.164.
3. **Business and tax:** `business_type` (`individual` or `registered_business`); `business_registration_number` and `business_registration_authority` (required for `registered_business`; whether individuals need them is VX-02); `pan_vat_number` and `is_vat_registered` (whether PAN is mandatory for individuals is [Verify-external VX-05]); `grievance_contact_name` and grievance contact phone; `return_policy_text`.
4. **Pickup address:** Province → District → Local level → Ward → Area/tole, stored as `shop_addresses` with `purpose = pickup`.
5. **Agreement:** the page shows the current seller agreement version and text. The version is the effective date of the text, for example `2026-10-01` ([04a §6.4](04a-data-dictionary-tables.md#64-shop_agreements)). An unchecked checkbox "I accept the DripNepal Seller Agreement of {effective date}" must be ticked.
6. Submit calls `applyForShop` with `accepted_agreement_version`. The result is 201: the shop is `pending_review`, and a `shop_agreements` row records the version, `accepted_by_user_id`, `accepted_at` and `ip_hash`.
7. `/account/shops` shows "Under review" and a document checklist. The owner uploads KYC documents (list per OD-16) with `createMediaUpload` (`kind = kyc_document`, private bucket) and `completeMediaUpload`, which is allowed while the shop is `pending_review` or `rejected`. Before review the owner also sets delivery coverage and zone rates on `/seller/{shopSlug}/shipping` (`getShopShipping`, `replaceShopShipping` ⟳; owner only while the shop is `pending_review` or `rejected`, OD-47, decided 2026-10-01), because approval requires them (AC-FR-SHOP-002-2, AC-FR-SHOP-004-3). The owner may also upload the shop logo and banner on `/seller/{shopSlug}/settings` before review: `createMediaUpload` and `completeMediaUpload` with `kind` `shop_logo` or `shop_banner`, under `shop.profile.manage`, and `updateShopProfile` ⟳ attaches them (product owner decision of 2026-10-01; [07 §4.4](07-security-threat-model-and-permissions.md#44-status-gating), [08 §2.5](08-ui-ux-and-design-system.md#25-seller-dashboard-sellershopslug)).
8. A reviewer opens `/admin/shop-applications` (`listShopApplications`, oldest first, flagged "documents missing" where relevant) and checks the s16 fields, the KYC documents, coverage and rates, the slug, and the repeat-seller matches: every shop in any status with the same owner, the same `pan_vat_number`, `business_registration_number`, contact phone or contact email, or the owner's `phone_hash` ([04a §6.1](04a-data-dictionary-tables.md#61-shops), [07 TM-31](07-security-threat-model-and-permissions.md#tm-31-fraudulent-vendor-onboarding-and-counterfeit-listings)). The queue carries KYC metadata only, never a URL: the reviewer opens each document with `viewKycDocument` (proposed, [06 §13.8](06-api-design.md#138-proposed-operations)), which issues one 5-minute link per view and writes one `shop.kyc_view` audit row ([07 TM-16](07-security-threat-model-and-permissions.md#tm-16-unauthorised-access-to-private-media-kyc)). The queue returns each application's `version`, and the decision sends it as `If-Match: "<version>"` (decision of 2026-10-04; [06 §8](06-api-design.md#8-concurrent-edits-etag-and-if-match)). If the owner changed the profile, shipping, logo or banner after the reviewer loaded the application, the decision answers `VERSION_CONFLICT (412)` with `current` and changes nothing; the review page reloads, shows what changed, and the reviewer reviews again. Then either:
   - `approveShopApplication` ⟳ → `active`, `approved_at` and `approved_by` set, a `shop_review_decisions` row (`approved`), audit, and an email. When a repeat-seller match was found, approval needs a written `note`, kept only in the `shop.approve` audit entry and never in the applicant-visible reason (proposed, [06 §13.6](06-api-design.md#136-admin)); or
   - `rejectShopApplication` ⟳ with a reason → `rejected`, a decision row, and an email that includes the reason.
9. If rejected: the owner edits the application on `/account/shops` and calls `resubmitShopApplication` (`rejected → pending_review`). An application rejected more than a year ago has been purged ([04 §19.3](04-domain-model-and-data-dictionary.md#193-retention-schedule), product owner decision of 2026-09-29): resubmitting it returns `INVALID_STATE_TRANSITION (409)`, and the owner applies again with a new shop.
10. If approved: `/seller/{shopSlug}/overview` shows a setup checklist: payout account (`replacePayoutAccount`, owner only, stored masked; finance verifies it later on `/admin/payouts` from M2 with `revealPayoutAccountForVerification` and `verifyPayoutAccount`, both proposed in [06 §13.8](06-api-design.md#138-proposed-operations) (the reveal awaits OD-49), and the verifier is never the person who entered it), and the logo and banner (FR-MED-003) only if they are still missing after step 7. Coverage and rates set in step 7 can be changed at any time with `replaceShopShipping` ⟳; products cannot be submitted or published without them (J-10).

### J-09 Staff invitation

| Field         | Value                                                                                                                                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Actors        | Shop owner; invitee; existing members                                                                                                                                                                  |
| Release       | R1 (M2). Custom roles are R3.                                                                                                                                                                          |
| Related FRs   | FR-SHOP-005, 006                                                                                                                                                                                       |
| Entry points  | `/seller/{shopSlug}/staff`; email link `/invitations/{token}`                                                                                                                                          |
| Preconditions | Shop `active`; while `suspended` (either mode) the owner may only list members, remove members and revoke invitations ([07 §4.4](07-security-threat-model-and-permissions.md#44-status-gating), OD-48) |
| Permissions   | `shop.staff.manage` (owner only; managers do not have it)                                                                                                                                              |

#### Main success flow

1. The owner opens `/seller/{shopSlug}/staff` (`listMembers`): members with role and status, plus pending invitations.
2. "Invite" takes an email and a role (`manager`, `catalog_editor`, `order_fulfiller`, `viewer`) and calls `inviteMember`. The server stores `shop_invitations` with a token hash and `expires_at` 7 days out, and emails the link.
3. The invitee opens `/invitations/{token}`. The page shows the shop, role and inviter. If they are not signed in → `/login` or `/signup` with `return_to` set to the invitation.
4. Signed in and verified, with the account email equal to the invitation email, "Accept" calls `acceptShopInvitation`. This creates a `shop_memberships` row (`active`), or reactivates the row of a removed member (Recovery row), sets `accepted_at`, and redirects to `/seller/{shopSlug}/overview`. The shop appears in the switcher (`listMyShops`).
5. The owner can revoke a pending invitation (`revokeInvitation`), change a role (`changeMemberRole`) or remove a member (`removeMember` → `status = removed`, `removed_at`).

| Class                     | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Success                   | The member has exactly the permissions of their role on the next request.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Empty                     | Only the owner: "Invite people to help run your shop", with role descriptions.                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Validation                | Invalid email, `role = owner` or an unknown role → `VALIDATION_FAILED (422)`.                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Permission                | Manager tries to invite → `FORBIDDEN (403)`. A non-member calls any staff endpoint → `NOT_FOUND (404)` (T-SEC-001). Account email differs from the invitation email → `FORBIDDEN (403)` naming the masked invited address.                                                                                                                                                                                                                                                                                                           |
| Concurrency               | Invitation accepted and revoked at once: compare-and-set on `accepted_at IS NULL AND revoked_at IS NULL`, so one wins. A second accept of the same link, sequential or concurrent → `NOT_FOUND (404)`, and exactly one membership exists. An open invitation accepted by a user who is already an active member of that shop → `CONFLICT (409)` ([07 TM-03](07-security-threat-model-and-permissions.md#tm-03-staff-invitation-abuse); T-SEC-007). Inviting someone who is already an active member or the owner → `CONFLICT (409)`. |
| External-provider failure | Email down: the invitation exists and the email job retries. The raw link is never shown to the owner; "Resend" revokes the old invitation and issues a new token ([07 TM-03](07-security-threat-model-and-permissions.md#tm-03-staff-invitation-abuse)).                                                                                                                                                                                                                                                                            |

#### Acceptance criteria

- **AC-J09-01** Given a manager, when they call `inviteMember`, then `FORBIDDEN (403)`. Given the owner, then an invitation with a hashed token and a 7-day expiry is stored, and the raw token appears only in the email.
- **AC-J09-02** Given an invitation older than 7 days, when accepted, then `NOT_FOUND (404)` and no membership is created.
- **AC-J09-03** Given an invitation for `a@x.com`, when `b@x.com` accepts, then `FORBIDDEN (403)`.
- **AC-J09-04** Given a member whose role changes from `order_fulfiller` to `viewer`, when they next open an order, then the customer phone is masked (last 4 digits) and `acceptShopOrder` returns `FORBIDDEN (403)`.
- **AC-J09-05** Given a member of shops A and B, then the switcher lists both, and each dashboard shows only that shop's data (fixes RF-44).
- **AC-J09-06** Given a removed member with a live session, when they request any `/seller/{shopSlug}` page or API, then `NOT_FOUND (404)` (fixes RF-01). Their customer features keep working.
- **AC-J09-07** Given invite, revoke, role change and removal, then each writes one `audit_logs` row with the owner as actor.

### J-10 Product creation & publication

| Field         | Value                                                                                                                                                                                                                               |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Actors        | Owner, manager, catalog editor; catalog moderator (J-16); system (media worker, listing refresh)                                                                                                                                    |
| Release       | R1 (M3). Bulk CSV import is R3.                                                                                                                                                                                                     |
| Related FRs   | FR-CAT-003, 004, 005, 007, 008, 011, 012; FR-MED-001, 002; FR-PROMO-001                                                                                                                                                             |
| Entry points  | `/seller/{shopSlug}/products` → "Add product" → `/seller/{shopSlug}/products/new`; edit at `/seller/{shopSlug}/products/{productId}`                                                                                                |
| Preconditions | Shop `active` with agreement and s16 fields (J-08); shipping configured before submit or publish; categories and attributes seeded                                                                                                  |
| Permissions   | `shop.products.edit` (create, edit, variants, media, submit for review, archive, restore); `shop.products.publish` (publish, unpublish) ([07 §4.5](07-security-threat-model-and-permissions.md#45-operation--permission-condensed)) |

#### Main success flow

1. `/products/new`: choose a leaf category (`listCategories`). The form shows the category's effective attributes (union over ancestors of `category_attributes`).
2. Enter title, description, brand (select only; missing brands are requested via support, FR-CAT-008), product attributes (audience, material), and the s6 disclosures: `manufacturer_name`, `is_imported` (then `country_of_origin` is required), `warranty_text`, `care_and_precautions`.
3. "Save draft" calls `createProduct` ⚷ → `draft`, with a `public_id` assigned. The editor opens.
4. **Variants:** choose 0–2 option axes (for example `apparel_size`, `color`) and fill the combination grid: price, optional compare-at price, SKU and weight. Save with `replaceProductVariants` ⟳ (`If-Match: "<version>"`, the strong tag of [06 §8](06-api-design.md#8-concurrent-edits-etag-and-if-match); tech lead decision of 2026-10-01).
5. **Media:** `createMediaUpload` returns a presigned PUT URL (JPEG, PNG or WebP; at most 10 MB and 40 megapixels). The browser uploads straight to storage, then calls `completeMediaUpload`. The worker checks magic bytes, strips EXIF and builds WebP derivatives (`processing → ready`). Order, alt text (required) and colour are saved with `replaceProductMedia` ⟳.
6. Stock is entered in J-11. A product may be published with zero stock and then shows "Sold out" ([08 §11.2](08-ui-ux-and-design-system.md#112-product-variant-selection-and-unavailable-combinations)).
7. **Submit.** In `pre` review mode, `submitProductForReview` → `pending_review` (locked for edits). In `post` mode, `publishProduct` → `published`, except for a product whose brand has `requires_moderation`: it goes through `submitProductForReview` → `pending_review` in either mode, and `publishProduct` on such a draft returns `INVALID_STATE_TRANSITION (409)` (AC-FR-CAT-008-3; [04 §3.10](04-domain-model-and-data-dictionary.md#310-brands-are-platform-reference-data-empty-means-own-label), [05 §6.10](05-order-payment-and-inventory-lifecycles.md#610-product-and-shop-lifecycles-summary)). Completeness is checked at submit: at least one active variant, at least one `ready` image with alt text, required category attributes, the s6 disclosures and shop shipping configured.
8. After approval (J-16) the product is `published`, and the listing refresh job adds it to listings within 60 s [Assumption].
9. Later: `unpublishProduct` and `publishProduct` (`published ↔ unpublished`), `archiveProduct`, `restoreProduct` (`archived → draft`).

### J-11 Inventory management

| Field         | Value                                                                                  |
| ------------- | -------------------------------------------------------------------------------------- |
| Actors        | Owner, manager, catalog editor; system (drift detection job)                           |
| Release       | R1 (M3). Low-stock alerts R2; multi-location R3.                                       |
| Related FRs   | FR-INV-001, 002, 003, 005                                                              |
| Entry points  | `/seller/{shopSlug}/inventory`; "Stock" tab on the product editor                      |
| Preconditions | Product has variants. `inventory_items` exists per variant (created with the variant). |
| Permissions   | `shop.inventory.adjust` to change; `shop.products.view` to view                        |

#### Main success flow

1. `listInventory` shows each variant: SKU, option label, `on_hand`, `reserved`, available (`on_hand − reserved`), and last movement.
2. **Adjust:** pick a variant, enter a signed non-zero delta and a reason code (`received_stock`, `damaged`, `lost`, `found`, `sold_offline`, `data_entry_error`, with an optional note; list owned by [05 §5.2](05-order-payment-and-inventory-lifecycles.md#52-movement-kinds)) and call `adjustInventory` ⚷. One conditional update (`WHERE on_hand + delta >= reserved`) changes `inventory_items`, one `adjustment` movement is appended, and an `audit_logs` row `inventory.adjust` is written. `correction` is not a vendor reason: it is the movement kind for platform-admin drift repair only.
3. **Stocktake:** enter the counted quantity; the client sends `{counted_quantity, expected_on_hand}` to `stocktakeInventory` ⚷. If `on_hand` still equals `expected_on_hand`, `on_hand` is set to `counted` and a `stocktake` movement records the delta.
4. The variant's movement history (page props from the inventory module's queries) shows who changed what, why, and with which request ID.
5. The `inventory.drift_check` job (daily 02:30 Asia/Kathmandu, [05 §5.10](05-order-payment-and-inventory-lifecycles.md#510-drift-detection-and-repair)) compares each projection with the sum of its movements and alerts on any mismatch (FR-INV-005; docs/11).

| Class                     | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Success                   | Stock reflects the change; listings update `in_stock` within 60 s.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Empty                     | No variants: "Add variants to this product to track stock".                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Validation                | Delta 0, non-integer, or a missing or unknown reason code (including `correction`) → `VALIDATION_FAILED (422)`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Permission                | Order fulfiller or viewer adjusting → `FORBIDDEN (403)`. Another shop's variant → `NOT_FOUND (404)`. Suspended shop → `SHOP_NOT_ACTIVE (403)`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Concurrency               | An adjustment or stocktake that would make `on_hand < reserved` (for example a checkout reserved the last units a moment ago) → `CONFLICT (409)` with `errors[0].code = below_reserved` and the current `reserved` split in two: `reserved_committed`, with links only to the shop orders the vendor can act on (`awaiting_acceptance`, or `accepted` before shipment), and `reserved_held`, a count only of units held for gateway payments in progress (R1.1), with no order numbers and no release time; nothing is written, and the CHECK constraint is the backstop ([05 §8.13](05-order-payment-and-inventory-lifecycles.md#813-stock-adjusted-below-reserved), AC-FR-INV-003-2). | Recovery                  | Mistakes are corrected with a new `adjustment` with reason `data_entry_error`. Movements are never edited or deleted. Drift found by the job is repaired only by a platform admin with a `correction` movement.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

- **AC-J11-01** Given `on_hand = 5, reserved = 3`, when an adjustment of −3 is sent, then `CONFLICT (409)` with `errors[0].code = below_reserved` and no change. #### Main success flow

1. The dashboard polls the count of `awaiting_acceptance` orders every 60 s [Assumption] (FR-NOT-003) and shows a badge.
2. `/orders` (`listShopOrders`) defaults to `awaiting_acceptance`, sorted by `acceptance_due_at` ascending, with a countdown ("Accept within 7 h").
3. The detail page (`getShopOrder`) shows items, quantities, the COD amount to collect, the customer note, and the recipient name, phone and address when the actor has `shop.customer_contact.view`.
4. **Accept:** `acceptShopOrder` ⚷ → `accepted`, `accepted_at` set, a `shipments` row in `pending`, and the parent moves to `in_progress`. The customer is emailed.
5. **Reject all:** `rejectShopOrder` ⚷ with `scope: "all"` and a `reason` (`out_of_stock`, `cannot_fulfil`, `pricing_error`, `other`; [06 §13.5](06-api-design.md#135-seller); stored in `shop_orders.rejection_reason`, CHECK in [04a §11.2](04a-data-dictionary-tables.md#112-shop_orders), transitions in [05 §6.1](05-order-payment-and-inventory-lifecycles.md#61-shoporder)) → `rejected`. Allowed from `awaiting_acceptance`, and from `accepted` while the shipment is `pending` or `packed` (counted as a late rejection in shop metrics). Reservations are released, the COD payment is `cancelled`, the parent is recomputed and the customer is emailed. For a paid gateway order (R1.1), a system refund of `refundable(so)` is created and auto-approved (J-14): the allocation less the shop order's refunds that are not `cancelled`, such as an earlier item-rejection refund ([05 §3.6](05-order-payment-and-inventory-lifecycles.md#36-partial-cancellation-and-item-level-rejection)).
6. **Reject some items:** `rejectShopOrder` with `scope: "items"` and `items: [{order_item_id, quantity}]` sets `rejected_quantity` on those lines, splits and releases their reservations, and accepts the rest (status `accepted`). The COD `amount_minor` goes down by the allocated amount of the rejected units, `A(k + r) − A(k)` summed over lines, and the shipping fee is unchanged; if the rejection covers every remaining unit the shop order becomes `rejected` and shipping is dropped too ([05 §3.6, §8.7](05-order-payment-and-inventory-lifecycles.md#87-partial-vendor-rejection)). For a gateway order the same amount is refunded by an auto-approved system refund.
7. **Pack (optional):** `recordFulfillmentEvent {event: "packed"}`.
8. **Ship:** `recordFulfillmentEvent {event: "shipped", courier_name, tracking_number?, tracking_url?}` → shipment `shipped`. Reservations go from `committed` to `consumed`, and a `ship` movement lowers both `on_hand` and `reserved`. The customer gets a tracking email.
9. Delivery outcomes continue in J-13.
10. **Acceptance SLA** ([05 §8.11](05-order-payment-and-inventory-lifecycles.md#811-vendor-acceptance-timeout)): `acceptance_due_at` = entry into `awaiting_acceptance` + `vendor_acceptance_sla_hours` (default 48 [Assumption A-07; OD-19]). The delayed job `orders.acceptance_reminder` emails the shop at `acceptance_due_at − least(24 h, vendor_acceptance_sla_hours / 2)`, which is 24 h before the deadline at the 48 h default and never at placement ([05 §4.7](05-order-payment-and-inventory-lifecycles.md#47-what-runs-after-commit), AC-FR-ORD-004-2). The delayed job `orders.acceptance_timeout` fires at `acceptance_due_at`, and a sweeper every 15 minutes catches lost jobs. Either one cancels a shop order still `awaiting_acceptance` with reason `acceptance_timeout`: reservations released, COD `cancelled` or gateway refund created, parent recomputed, both sides emailed, shop timeout metric incremented (FR-ORD-004). A shop with 3 timeouts in 30 days is put on the admin review list [Assumption OD-19]. A last-second acceptance wins, and the job then does nothing.

### J-13 COD delivery outcome & RTO

| Field         | Value                                                                                                                         |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Actors        | Order fulfiller (records what the courier reports); courier (off-platform); customer; system (ledger posting, completion job) |
| Release       | R1 (M6 for outcomes, M7 for ledger). The R1.1 clause of AC-J13-08 is M8.                                                      |
| Related FRs   | FR-FUL-002, 003; FR-PAY-001; FR-LED-001, 002; FR-CHK-007; FR-ORD-006                                                          |
| Entry points  | `/seller/{shopSlug}/orders/{shopOrderNumber}` for a `shipped` shop order                                                      |
| Preconditions | Shipment `shipped`; COD payment `awaiting_collection`                                                                         |
| Permissions   | `shop.orders.process`                                                                                                         |

In R1 the vendor's courier collects the cash, so the platform holds no customer money and the vendor ends up owing commission [Confirmed Q3, Q4, Q5] ([00 §3.3](00-context-assumptions-and-questions.md#33-the-cod-consequence-vendors-hold-the-cash-so-the-ledger-must-go-negative)). E-Commerce Act 2081 s8(1) deems payment to the delivery service provider to be payment received by the business entity; which entity that is for a marketplace is VX-01 and VX-02 ([research: nepal-payments](research/nepal-payments.md), accessed 2026-09-25).

#### Main success flow (delivered and collected)

1. The courier delivers and collects the COD amount. No extra charge at the door is allowed ([05 §3.3](05-order-payment-and-inventory-lifecycles.md#33-shipping-fee-per-shop-order)).
2. The fulfiller records `recordFulfillmentEvent {event: "delivered"}` → shipment `delivered`. The server sets `delivered_at = now()` in that transaction; the client never sends it, so a shop cannot backdate delivery and shorten the return window ([05 §6.3](05-order-payment-and-inventory-lifecycles.md#63-shipment-fulfillment)).
3. The fulfiller records `recordCodCollection {outcome: "collected", amount_minor}` → payment `collected`. The amount must equal the expected COD amount.
4. When both are recorded, the ledger posts in the transaction of whichever comes second ([05 §7.3](05-order-payment-and-inventory-lifecycles.md#73-delivery-posting)). The COD group nets to minus the commission, so under the group rule of [05 §7.2](05-order-payment-and-inventory-lifecycles.md#72-entry-types-and-posting-rules) all four entries are available at once (`available_at` = posting time): debts to the platform are never deferred. Only a group with a positive net (gateway, J-15) waits `ledger_hold_days` (default 7). For shop order `DN-7Q4K2MX-1` (items Rs 2,400, shipping Rs 100, commission at `default_commission_rate_bp` 1000 = 10% of items, shipping commission-free [Open OD-04]):

| Entry type        | Amount      | Meaning                       |
| ----------------- | ----------- | ----------------------------- |
| `sale`            | +Rs 2,400   | Items sold                    |
| `shipping_income` | +Rs 100     | Shipping charged              |
| `commission`      | −Rs 240     | Platform commission           |
| `cod_cash_held`   | −Rs 2,500   | Vendor already holds the cash |
| **Net**           | **−Rs 240** | Vendor owes commission (J-15) |

5. The return window starts at `delivered_at`. The `delivered` transaction stores its end, `shipments.return_window_ends_at = delivered_at + return_window_days` (default 7 [Assumption A-05; OD-06]), so a later change of the setting never moves it ([04a §11.5](04a-data-dictionary-tables.md#115-shipments)). The hourly `orders.auto_complete` job marks the shop order `completed` when `now() ≥ shipments.return_window_ends_at`, no return request is `requested`, `approved`, `in_transit` or `received`, no refund is `requested`, `approved`, `processing`, `failed` or `needs_review`, and the COD payment is `collected` (FR-ORD-006; [05 §6.1](05-order-payment-and-inventory-lifecycles.md#61-shoporder)).

#### Alternate flow (customer refuses or cannot be reached)

1. The fulfiller records `delivery_failed` with a `failure_reason` (`customer_unreachable`, `refused`, `address_problem`, `other`; stored in `shipment_events.reason_code`, CHECK in [04a §11.6](04a-data-dictionary-tables.md#116-shipment_events)) → shipment `delivery_failed`. The customer's order page shows "Delivery attempt failed", and the customer is emailed asking them to contact the shop or support. After the second failure a support case with category `delivery` is opened automatically (J-19).
2. For another attempt: event `reattempt` → shipment back to `shipped` with `attempt_count + 1`, allowed while `attempt_count < 3` [Assumption, 05 §6.3]. There is no separate `reattempt` state.
3. To give up: event `returning` → shipment `returning`. The fulfiller may record `recordCodCollection {outcome: "not_collected"}` now; otherwise the system sets the COD payment to `not_collected` at `returned_to_origin`.
4. When the parcel is back: `returned_to_origin` → shipment `returned_to_origin`. The event marks each returned unit resaleable or damaged (`items[]` with a `restock_quantity` per line, and a `note` with the reason when any unit is not restocked; AC-FR-FUL-003-2). In the same transaction `rto_restock` movements add only the resaleable units back to `on_hand` ([05 §5.8](05-order-payment-and-inventory-lifecycles.md#58-rto-restock)), the COD payment becomes `not_collected` if it is not already, the shop order is `cancelled` with reason `undeliverable`, and the parent is recomputed ([05 §8.9](05-order-payment-and-inventory-lifecycles.md#89-cod-refusal-and-collection-reconciliation)). **No ledger entries** are posted, because nothing was posted before delivery. Who bears the courier's return cost is between the vendor and its courier in R1 (OD-05, OD-07).
5. Damaged units get no stock movement and are written off outside the inventory system, with the reason kept on the `returned_to_origin` event. They are never restocked and then corrected with a `damaged` adjustment, because a checkout could reserve them in between ([05 §5.8](05-order-payment-and-inventory-lifecycles.md#58-rto-restock)).
6. **Repeat-refuser COD limit** ([05 §8.9](05-order-payment-and-inventory-lifecycles.md#89-cod-refusal-and-collection-reconciliation); settings `cod_max_refusals` default 2 and `cod_refusal_window_days` default 90, used only if [Open OD-18] adopts the rule): a refusal is a `delivery_failed` event with `reason_code = refused` on a COD shipment of the customer. When the customer has `cod_max_refusals` or more refusals within the last `cod_refusal_window_days` days, checkout step 7 refuses COD with `COD_LIMIT_EXCEEDED (422)` and detail "Cash on delivery is not available for this account". The window is rolling, so COD comes back without anyone acting once the older refusals fall out of it; R1 has no admin override (T-CHK-007).

- **AC-J13-07** Given a `delivered` shipment, when `not_collected` is recorded, then the COD payment is `not_collected`, a support case with category `order_issue` and `due_at = created_at + 15 days` is opened automatically, no ledger entry is posted, and `orders.auto_complete` leaves the shop order `accepted`. Given support later records `collected` through the admin correction, then the 4 delivery entries are posted exactly once.
- **AC-J13-08** Given OD-18 adopts the rule with `cod_max_refusals = 2` and `cod_refusal_window_days = 90`, and a customer with 2 `delivery_failed` events with `reason_code = refused` on COD shipments in the last 90 days, when they quote a COD checkout, then COD is marked unavailable, `placeOrder` with COD returns `COD_LIMIT_EXCEEDED (422)`, and other methods (R1.1) remain available.
- **AC-J13-09** Given `return_window_days = 7` at delivery, so `shipments.return_window_ends_at = delivered_at + 7 days`, a COD payment `collected` and no open return or refund, when `orders.auto_complete` runs at or after `return_window_ends_at`, then the shop order is `completed` within 1 hour. Given the setting is changed to 10 after delivery, then the stored `return_window_ends_at` is unchanged and still decides completion. Given an open return request (J-20) or a COD payment still `awaiting_collection`, then it stays `accepted`.
- **AC-J13-10** Given the customer's order page, then each failed attempt appears as a customer-visible event with a support link, and the RTO shows as "Returned to seller, order cancelled".
- **AC-J13-11** Given `delivered` with the COD payment still `awaiting_collection`, then exactly one reminder reaches the shop 24 h after delivery, and after 3 days the shop order is listed in the admin "COD outcome missing" queue ([05 §8.9](05-order-payment-and-inventory-lifecycles.md#89-cod-refusal-and-collection-reconciliation), AC-FR-PAY-001-3).
- **AC-J13-12** Given a second `delivery_failed` on the same shipment, then exactly one support case with category `delivery` is opened automatically for the shop order and linked to it.
- **AC-J13-13** Given `returned_to_origin` is recorded while the COD payment is still `awaiting_collection`, then the payment becomes `not_collected` in the same transaction without a separate `recordCodCollection` call.
- **AC-J13-14** Given `collected` with the correct amount recorded while the shipment is `shipped` and before `delivered`, then the payment is `collected`, a receipt email is queued for the customer, and no ledger entry exists until `delivered` is recorded (AC-J13-02). Given `delivered` is still not recorded, then one reminder to record the delivery reaches the shop 24 h after the collection, and after 3 days the shop order is listed in the admin "COD outcome missing" queue ([05 §8.9](05-order-payment-and-inventory-lifecycles.md#89-cod-refusal-and-collection-reconciliation)).
- **AC-J13-15** Given a COD shipment in `shipped` whose payment is `collected`, when `delivery_failed` is recorded, then `INVALID_STATE_TRANSITION (409)` is returned and nothing changes; `returning` and `returned_to_origin` are refused the same way. A collection recorded by mistake is corrected through a support case, as for a mistaken `delivered` ([05 §6.3](05-order-payment-and-inventory-lifecycles.md#63-shipment-fulfillment); T-FUL-004).

### J-14 Refund (admin-initiated)

| Actors        | Support agent (creates); finance officer (approves, records); system (gateway refund job, SLA job); customer                                                                       |
| Release       | R1: manual transfer for COD and bank or wallet (M7). R1.1: gateway refunds with unknown-outcome handling (M8). Self-serve is R2.                                                   |

| Preconditions | Money was collected or captured for the shop order. MFA-verified staff session.                                                                                                    |
| Permissions   | `platform.refunds.create`; `platform.refunds.approve`; approver differs from creator (maker-checker; `single_operator_mode` exception, OD-14)                                      |

Refund methods ([05 §6.7](05-order-payment-and-inventory-lifecycles.md#67-refund)): `manual_transfer` (COD, bank or wallet transfer by finance), `gateway_api` (Khalti refund API), and `gateway_manual` (eSewa has no documented refund API; the operator refunds in the merchant portal or through eSewa support and records the reference). Sources: <https://docs.khalti.com/api/refund/>, <https://developer.esewa.com.np/pages/Epay>, accessed 2026-09-25. The Khalti refund method, auth header and amount unit are unconfirmed (VX-07).

#### Main success flow (COD, manual transfer)

1. The support agent opens the order (`adminGetOrder`) and chooses "Create refund". They pick the shop order, items and quantities (`refund_items`), the reason code (`order_cancelled`, `items_rejected`, `undeliverable`, `return_accepted`, `late_capture`, `stock_unavailable_after_payment`, `goodwill`, `other`; CHECK in [04a §12.4](04a-data-dictionary-tables.md#124-refunds)), an optional internal `note` (at most 2,000 characters, stored in `refunds.note`), method `manual_transfer`, and the recipient's bank or wallet details, which the agent types into `createRefund` (stored encrypted in `recipient_details_enc`). Account numbers are never asked for or pasted in support-case messages, which are plaintext and kept 7 years after the case is resolved; the case composers warn when a message looks like one ([07 TM-19](07-security-threat-model-and-permissions.md#tm-19-refund-abuse-and-double-refunds)). How the customer supplies the details, and what the approver checks them against, is [Open OD-38]. `createRefund` ⚷ → `requested`.
2. The server checks the refundable amount with the allocation and payment rows locked: `refundable = captured or collected − Σ refunds of that shop order in requested, approved, processing, succeeded, needs_review or failed` ([05 §6.7](05-order-payment-and-inventory-lifecycles.md#67-refund)). A `failed` refund still counts until it is cancelled, so a retry and a new refund can never both pay. The payments CHECK `refunded_minor <= captured_minor` is the backstop. `refunds.due_at` is set: the return's `refund_due_at` for a return refund, otherwise creation + 7 days.
3. The finance officer opens `/admin/refunds` and calls `approveRefund` ⚷ → `approved`. In `single_operator_mode` the approver re-enters a TOTP code and the audit row is flagged.
4. Finance makes the transfer outside DripNepal, then records it with `markRefundSucceeded` ⚷ and `paid_reference`. For `manual_transfer` that call moves an `approved` refund through `processing` to `succeeded` in one transaction; the proposed `startRefundTransfer` ([06 §13.8](06-api-design.md#138-proposed-operations)) records `approved → processing` when a transfer is started but not yet confirmed ([05 §6.7](05-order-payment-and-inventory-lifecycles.md#67-refund)).
5. Whether a refund touches the vendor ledger is fixed when it is created: `refunds.affects_vendor_ledger` (proposed) is true only for a `return_accepted`, `goodwill` or `other` refund created after the shop order's delivery posting. Only such a refund posts `refund` and `commission_reversal` in its success transaction, from the amounts stored at creation and deduplicated per refund. `items_rejected`, `order_cancelled`, `undeliverable`, `late_capture` and `stock_unavailable_after_payment` refunds never post, whenever they succeed; a `late_capture` refund never posts even after delivery ([05 §7.4](05-order-payment-and-inventory-lifecycles.md#74-refund-postings-and-commission-reversal)). Example: 1 T-shirt (Rs 1,200) refunded from delivered `DN-7Q4K2MX-1`: `refund` −Rs 1,200 and `commission_reversal` +Rs 120. The platform paid the customer, and the vendor now owes Rs 1,080 more because the vendor kept the cash (J-15) [Assumption OD-07, OD-05].
6. The customer is emailed the amount and reference. The order page shows the refund status.
7. **SLA** (E-Commerce Directive 2082 s9(3); FR-RET-007; [05 §11](05-order-payment-and-inventory-lifecycles.md#11-legal-overlays)): a return refund is due at `return_requests.refund_due_at` = return approval + 7 days; any other refund at `refunds.due_at` = refund creation + 7 days. The Directive does not state when the 7 days start, so the start point is [Assumption; Verify-external VX-02]. `refunds.sla_monitor` (hourly) alerts finance when a refund is not `succeeded` 2 days before its due time and escalates to the platform admin at the due time; the `/admin/refunds` queue is sorted by due time and highlights refunds with 2 days or less left (AC-FR-RET-007-2).
8. **System refunds** created by a rejection, a cancellation or `stock_unavailable_after_payment` of a paid gateway order (R1.1) have an amount fixed by that transition and are auto-approved in the same transaction; a `late_capture` refund waits for finance approval ([05 §6.7](05-order-payment-and-inventory-lifecycles.md#67-refund)).

#### Gateway variant (R1.1)

- `gateway_api` (Khalti): approval queues `refunds.execute`, which commits `processing` before calling the refund API with the refund's `provider_idempotency_key`. At most one Khalti refund per payment is `processing` or `needs_review` at a time; another one waits. Success → `succeeded`. A definitive error → `failed`. `retryRefund` looks the payment up first; then its request transaction moves the refund `failed → processing` with `attempts + 1` and sends `refunds.execute` carrying that attempt number, and the job calls the provider (same `provider_idempotency_key`) only for that attempt (cross-doc check decision, 2026-10-01; [05 §6.7](05-order-payment-and-inventory-lifecycles.md#67-refund), [06 §13.6](06-api-design.md#136-admin)). A timeout or 5xx keeps `processing`, and `refunds.verify` looks the payment up (at 1, 5, 15 and 60 minutes, then hourly). The lookup shows only the payment's status, so it confirms the refund only when it is decisive: no other gateway refund of the payment is `succeeded`, `processing` or `needs_review` and the status matches this refund (partial or full), or this refund completes a full refund of the payment. A decisive lookup → `succeeded`; 5 inconclusive lookups → `needs_review`. A lookup never moves a refund to `failed`. The refund API is never called a second time before a lookup (T-PAY-008; [05 §8.8](05-order-payment-and-inventory-lifecycles.md#88-refund-failure-and-retry-including-esewa-without-a-refund-api)).
- `gateway_manual` (eSewa, no documented refund API): after approval, the operator refunds in the eSewa merchant portal or through eSewa support [Verify-external VX-06] and records eSewa's reference with `markRefundSucceeded`. For this method that call moves the refund to `processing` and stores `paid_reference`; it does not mark success. `refunds.verify` checks the status API daily, and only a decisive check moves the refund to `succeeded`. A second refund on the same payment that does not complete a full refund cannot be told apart by the status, so after 3 daily checks without a decisive result it goes to `needs_review`, and finance resolves it with the merchant-statement line or eSewa's written confirmation (T-RET-003).

#### Acceptance criteria

- **AC-J14-01** Given Rs 2,500 collected and Rs 1,200 already refunded on a shop order, when a refund of Rs 1,400 is created, then `REFUND_EXCEEDS_REFUNDABLE (422)`. A direct SQL update that breaks `refunded_minor <= captured_minor` fails (T-SEC-004).
- **AC-J14-02** Given the creator tries to approve their own refund, then `FORBIDDEN (403)`. Given `single_operator_mode = true`, then approval requires a fresh TOTP code and writes an audit row flagged `single_operator`.
- **AC-J14-03** Given a support agent, when they call `approveRefund`, then `FORBIDDEN (403)`.
- **AC-J14-04** Given `markRefundSucceeded` without `paid_reference`, then `VALIDATION_FAILED (422)`. With it, on a refund with `affects_vendor_ledger`, then the status is `succeeded` and exactly one `refund` and one `commission_reversal` entry exist for the refund.
- **AC-J14-05** Given the example above, then the entries are −120000 (`refund`) and +12000 (`commission_reversal`), and the shop balance falls by 108000.
- **AC-J14-06** Given a Khalti refund call that times out after Khalti processed it, then the refund ends `succeeded` after the lookup, and the refund API was called exactly once (T-PAY-008).
- **AC-J14-07** Given a `failed` gateway refund, when `retryRefund` is called, then a lookup runs first. The API is called again only if the lookup shows no refund, and then only by the `refunds.execute` job for the new attempt number; a job carrying an older attempt number calls nothing.
- **AC-J14-08** Given a return approved at 2026-10-01T10:00+05:45 (so `refund_due_at` = 2026-10-08T10:00+05:45) whose refund is not `succeeded`, then `refunds.sla_monitor` alerts finance within 1 hour after 2026-10-06T10:00+05:45 and escalates to the platform admin within 1 hour after `refund_due_at`. Given a goodwill refund created at the same time, then its `due_at` is 2026-10-08T10:00+05:45 and the same alerts apply (start point [Assumption; Verify-external VX-02]).
- **AC-J14-09** Given two concurrent approvals, then one returns 200 and the other `INVALID_STATE_TRANSITION (409)`.
- **AC-J14-10** Given recipient bank details, then they are stored encrypted and absent from logs and audit `changes`; they are never part of a list or detail response ([04a §12.4](04a-data-dictionary-tables.md#124-refunds)), and the full value is returned only by the audited staff reveal `revealRefundRecipient` (proposed) of [07 §5.5](07-security-threat-model-and-permissions.md#55-encryption), while the refund is `approved` or `processing` (AC-FR-RET-001-3) [Open OD-49].
- **AC-J14-11** Given an open refund on a delivered shop order, then the completion job does not mark it `completed` until the refund is terminal.
- **AC-J14-12** Given create, approve and mark-succeeded, then each writes one audit row with the actor's platform role.
- **AC-J14-13** Given a `failed` refund of Rs 1,200 on a shop order with Rs 2,500 collected, when a second refund of Rs 1,400 is created, then `REFUND_EXCEEDS_REFUNDABLE (422)`. Given the failed refund is first `cancelled`, then the Rs 1,400 refund is accepted.
- **AC-J14-14** Given a refund succeeds on a shop order that was never delivered (for example a rejected gateway shop order), then no `ledger_entries` row is written for it.
- **AC-J14-15** Given a paid gateway shop order (R1.1) with no earlier refund, when the vendor rejects all of it, then a system refund of `refundable(so)`, here equal to its allocation, exists in `approved` (created and approved by the system in the rejection transaction, with no finance approval step) and `refunds.execute` is queued. Given an earlier item-rejection refund on that shop order that is not `cancelled`, then the system refund is the allocation less that refund, never the full allocation ([05 §3.6](05-order-payment-and-inventory-lifecycles.md#36-partial-cancellation-and-item-level-rejection)).
- **AC-J14-16** Given a gateway refund whose `refunds.verify` lookups stay inconclusive 5 times, then the refund is `needs_review`, appears in `/admin/refunds?status=needs_review`, and resolving it requires an evidence reference.
- **AC-J14-17** Given a failed `gateway_api` refund already retried 3 times, when `retryRefund` is called, then `INVALID_STATE_TRANSITION (409)`. Given finance then cancels it and support creates a `manual_transfer` refund naming it as the one replaced, then the new refund keeps the cancelled refund's `due_at` ([05 §6.7](05-order-payment-and-inventory-lifecycles.md#67-refund), [§8.8](05-order-payment-and-inventory-lifecycles.md#88-refund-failure-and-retry-including-esewa-without-a-refund-api); T-RET-004, T-RET-002).
- **AC-J14-18** Given a delivered gateway shop order paid by attempt 2 and a `late_capture` refund for attempt 1 (J-06), when the refund succeeds, then no `ledger_entries` row is written for it ([05 §7.4](05-order-payment-and-inventory-lifecycles.md#74-refund-postings-and-commission-reversal)).
- **AC-J14-19** Given an eSewa payment with one `gateway_manual` refund already `succeeded`, when a second refund on it that does not complete a full refund is recorded with `markRefundSucceeded`, then it stays `processing`, no daily check confirms it, and after 3 checks it is `needs_review` (T-RET-003).

### J-15 Vendor ledger & remittance/payout

| Field         | Value                                                                                                                                                                                  |

| Actors        | Owner and manager (view); finance officer (record, create and approve); system (posting and availability)                                                                              |

#### Main success flow A: COD commission owed and remitted (R1)

1. The owner opens `/seller/{shopSlug}/finance`. `getShopBalance` returns the money objects `balance`, `available`, `payable` (what a payout created now would pay, from R1.1) and `pending` ([05 §7.10](05-order-payment-and-inventory-lifecycles.md#710-balances-availability-and-payable-amount)). A negative `balance` reads "You owe DripNepal Rs 240 in commission on cash-on-delivery orders", with remittance instructions and a reference format agreed under OD-05.
2. `listShopLedgerEntries` (cursor) lists each entry: type, shop order, signed amount and `available_at`. A monthly statement (Asia/Kathmandu calendar month) shows opening balance, entries and closing balance, and can be printed. CSV export is left to R3 bulk export [Assumption].
3. The vendor pays the platform outside DripNepal.
4. The finance officer (`platform.ledger.adjust`) records it in `/admin/ledger`: `recordVendorRemittance` ⚷ with `{shop_id, amount_minor, method, reference, received_at}` → one `vendor_remittances` row and one `vendor_remittance` entry of +amount, available at once, in one transaction with audit `ledger.record_remittance`; the owner is emailed a receipt (AC-FR-LED-004-1). The remittance may not exceed the amount owed (`amount_minor ≤ −balance`), so DripNepal never holds vendor money as a balance ([05 §7.5](05-order-payment-and-inventory-lifecycles.md#75-vendor-remittance-r1); [Verify-external VX-01]). The balance moves to Rs 0.
5. Proposed terms [Assumption; Open OD-05, blocks launch]: a monthly statement, issued after each Gregorian month closes, with payment within 10 days of the statement's issue and a reminder at day 7 after issue ([05 §7.5](05-order-payment-and-inventory-lifecycles.md#75-vendor-remittance-r1)). If the balance stays below −Rs 5,000 for more than 30 days, finance is alerted and suspension with `fulfill_existing` becomes an option (J-17).

#### Main success flow B: payouts after the gateway launch (R1.1)

1. A delivered gateway order posts `sale` +Rs 3,000, `shipping_income` +Rs 100 and `commission` −Rs 300. There is no `cod_cash_held`, because the platform collected the money. The group net is positive, so all three entries get `available_at = delivered_at + ledger_hold_days` (default 7), which covers the return window ([05 §7.2](05-order-payment-and-inventory-lifecycles.md#72-entry-types-and-posting-rules)).
2. Netting: a payout may include exactly the shop's available, unsettled and non-held entries, positive and negative together. An entry is held while its shop order has a return in `requested`, `approved`, `in_transit` or `received`, a refund in `requested`, `approved`, `processing`, `failed` or `needs_review`, or an open `order_issue` support case, and that shop order's available, unsettled entries net > 0. A shop order whose entries net ≤ 0 (a COD delivery posting) is never held, so debts are never deferred and a payout never exceeds the available balance (AC-FR-LED-004-2; [05 §6.8](05-order-payment-and-inventory-lifecycles.md#68-payout-and-settlement-r11), [§7.6](05-order-payment-and-inventory-lifecycles.md#76-payouts-and-netting-r11)). With Rs 240 of COD commission still owed, the payable amount is Rs 2,560. If the payable sum is 0 or less, no payout is created.
3. The finance officer (`platform.payouts.manage`) calls `createPayout` ⚷ (`draft`), which locks the shop row and links the eligible entries in `payout_entries` (each ledger entry at most once); the amount is computed, never typed. The query locks no `ledger_entries` rows, which the application role cannot lock; the shop lock and the unique `payout_entries.ledger_entry_id` keep two drafts apart. The shop needs an active, verified payout account. A `frozen` shop is refused with `CONFLICT (409)` and `errors[0].code = shop_frozen` (proposed) until finance decides how its balance is settled (cross-doc check decision, 2026-10-01; [05 §6.10](05-order-payment-and-inventory-lifecycles.md#610-product-and-shop-lifecycles-summary), [§8.10](05-order-payment-and-inventory-lifecycles.md#810-shop-suspension-while-orders-remain-open), [06 §13.6](06-api-design.md#136-admin)).
4. A second finance officer (`platform.payouts.approve`) calls `approvePayout` ⚷ → `approved`, and the `payout` entry of −amount is posted in the same transaction (05 §6.8). Outside single-operator mode the approver must differ from the draft's creator and from the finance officer who verified the payout account, so with two finance people the verifier of a new account drafts its payouts and the other approves them ([07 §4.7](07-security-threat-model-and-permissions.md#47-maker-checker-and-single-operator-mode)). In the approval transaction `approvePayout` re-runs the eligibility check. If a linked entry's shop order became held, a debt was posted after drafting, or the payout account was replaced, it answers `CONFLICT (409)` with `errors[0].code = payout_stale` (proposed), and finance cancels the draft (`cancelPayout`, proposed) and creates a new one ([05 §7.6](05-order-payment-and-inventory-lifecycles.md#76-payouts-and-netting-r11), [04a §6.7](04a-data-dictionary-tables.md#67-shop_payout_accounts)). A shop frozen after drafting gets `CONFLICT (409)` with `errors[0].code = shop_frozen` (proposed), as in step 3. No payout is approved while [Open OD-27] (1% advance tax, Income Tax Act s95A(6e) [Verify-external VX-05]) is undecided (AC-FR-LED-004-4), and `tax_withholding` stays disabled until then. Approval is also refused while `checkout_enabled = false` [Assumption, AC-FR-ADM-010-2].
5. The bank transfer is made outside DripNepal. `markPayoutPaid` ⚷ with `bank_reference` → `paid`, and the vendor is emailed.
6. If the bank rejects it while the payout is `approved`: `markPayoutFailed` ⚷ with a reason → `failed`, a `payout_reversal` +amount entry is posted, and a new payout is created later. A transfer the bank returns after the payout was recorded `paid` is carried forward by `createLedgerAdjustment` of +amount with `reverses_entry_id` = the payout's `payout` entry and a reason naming the payout and the bank's return reference; the payout stays `paid` ([05 §7.7](05-order-payment-and-inventory-lifecycles.md#77-payout-failure-reversal)).

AC-J17-08 is R1.1 (M8). |
| Related FRs   | FR-IAM-006; FR-ADM-002; FR-SHOP-007; FR-ADM-011 (public grievance contact)                                                                                                                                                                                                                                                                                                                                                                                                                |

| Preconditions | MFA-verified platform admin                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

#### Main success flow: user suspension

1. The admin opens the user (`getUser`) and calls `suspendUser` with a reason of at least 10 characters (AC-FR-IAM-006-1). The status becomes `suspended`, live `user_tokens` are consumed, `security_stamp` rotates, and the `identity.revoke_sessions` job deletes every session tagged with the user ID ([07 §3.3](07-security-threat-model-and-permissions.md#33-the-per-request-account-check-and-the-suspension-decision)). Audit is written.
2. On the user's next request, API calls return `ACCOUNT_SUSPENDED (403)` while the session still exists, or `UNAUTHENTICATED (401)` once the job has revoked it, never a 2xx (AC-J00-03, AC-FR-IAM-006-2). Pages redirect to `/login`, with "Your account is suspended" while the session exists, plus the grievance officer contact from the legal disclosures page (FR-ADM-011).
3. Open orders continue: suspending a user neither cancels their orders nor suspends shops they own (AC-FR-IAM-006-3). Vendors may still process the orders, and support can cancel them (`adminCancelShopOrder`). A suspended shop owner or member loses dashboard access, because every seller request requires an `active` user ([07 §4.4](07-security-threat-model-and-permissions.md#44-status-gating)). The admin user page lists owned shops and open orders so staff can act on them separately.
4. Recovery: the user contacts the grievance officer by email or phone. The admin calls `reinstateUser` → `active`, or `pending_verification` when the email was never verified (AC-FR-IAM-006-4, [07 §3.12](07-security-threat-model-and-permissions.md#312-user-status-transitions)); such a user verifies as a new user does, asking for a new link with `resendEmailVerification`. The user signs in again, because the old sessions are gone.

#### Main success flow: shop suspension

1. The admin calls `suspendShop` with `{suspension_mode, reason}`, the reason of 20 to 2,000 characters. In one transaction the shop becomes `suspended` (audit `shop.suspend`, a `shop_review_decisions` row `suspended`) and the jobs `catalog.refresh_listing` and `orders.handle_shop_suspension` are sent ([05 §8.10](05-order-payment-and-inventory-lifecycles.md#810-shop-suspension-while-orders-remain-open)). Within 60 seconds its products leave listings, `/shops/{shopSlug}` returns 404, and carts flag its lines unavailable; checkout step 4 rejects them with `CART_CHANGED (409)`.
2. **`fulfill_existing`:** members keep `shop.orders.view`, `shop.orders.process`, `shop.customer_contact.view`, `shop.finance.view` and `shop.products.view`. Editing, publishing and inventory changes return `SHOP_NOT_ACTIVE (403)`. Open orders are processed normally, including the acceptance SLA (J-12, J-13); the job only emails the vendor its obligations.
3. **`frozen`:** the dashboard is read-only. The `orders.handle_shop_suspension` job, in batches of 50, cancels every shop order of the shop in `awaiting_acceptance`, or in `accepted` with the shipment `pending` or `packed`, with reason `shop_frozen`: reservations released, COD payments `cancelled`, gateway refunds created, customers emailed. Shop orders in `awaiting_payment` are left alone; if their payment is captured later, the capture transaction cancels the frozen shop's shop orders with `shop_frozen` and refunds their allocation while other shops' parts proceed. Parcels already `shipped`, `delivery_failed` or `returning` are followed by support with the vendor offline, and an admin records their outcome through the proposed `adminRecordFulfillmentEvent` and `adminRecordCodCollection` ([06 §13.8](06-api-design.md#138-proposed-operations), [05 §8.10](05-order-payment-and-inventory-lifecycles.md#810-shop-suspension-while-orders-remain-open)). Until those operations exist, the suspend dialog lists such parcels and recommends `fulfill_existing` until they are delivered or returned (see Consistency notes). Payouts are refused for a frozen shop: `createPayout`, and `approvePayout` for a draft made before the freeze, answer `CONFLICT (409)` with `errors[0].code = shop_frozen` (proposed; R1.1, J-15; [05 §8.10](05-order-payment-and-inventory-lifecycles.md#810-shop-suspension-while-orders-remain-open)).
4. `reinstateShop` → `active`. Products that were `published` return to listings within 60 s. Reinstatement never revives cancelled shop orders.

| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Success                   | Suspension effective on the next request; reinstatement restores access with no data loss.                                                                                                                                                                                                                                                                     |
| Empty                     | A shop with no open orders is frozen with no follow-up list.                                                                                                                                                                                                                                                                                                   |
| Validation                | Missing reason, a `suspendUser` reason under 10 characters, a `suspendShop` reason outside 20 to 2,000 characters ([06 §13.6](06-api-design.md#136-admin); the [04a §6.5](04a-data-dictionary-tables.md#65-shop_review_decisions) `CHECK` holds the same range) or missing `suspension_mode` → `VALIDATION_FAILED (422)`.                                      |

Suspending or reinstating a user who holds an active `platform_staff` row (the admin themselves included) → `CONFLICT (409)`; staff access is removed first with `revokePlatformStaff`, which keeps the last active `platform_admin` ([07 §3.12](07-security-threat-model-and-permissions.md#312-user-status-transitions)). |

### J-18 Password reset

| Field         | Value                                                                                                                                                |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Actors        | Any user (customer, seller, staff); system (email)                                                                                                   |
| Release       | R1 (M1)                                                                                                                                              |

#### Main success flow

1. `/forgot-password`: enter the email and call `requestPasswordReset`. It always returns 202 with "If an account exists, we've sent a link". Limits: 3 per hour per email and 10 per hour per IP.
2. For an existing account in `active` or `pending_verification`, the server invalidates earlier unconsumed reset tokens, stores a new hashed `user_tokens` row (`purpose = password_reset`, expires in 60 minutes [Assumption]) and queues the email. Suspended and anonymized accounts get no email, and the response is identical.
3. The link opens `/reset-password?token=…`. The user enters a new password (10–128 characters) and calls `resetPassword`. The password hash is updated, the token consumed, `security_stamp` rotated and all sessions revoked. A "Your password was changed" email is sent. Because the link proves control of the inbox, a `pending_verification` account is also marked verified [Assumption].
4. The page redirects to `/login` with a success notice. There is no automatic login [Assumption]. Staff still need TOTP.
5. **Change password (signed in):** `/account/security` → `changePassword` with the current and new password. The current session is regenerated and kept; other sessions are revoked. "Sign out of all devices" calls `revokeAllSessions` (FR-IAM-005).

| Class                     | Behaviour                                                                                                                                                                                 |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Success                   | New password works, old sessions end.                                                                                                                                                     |
| Empty                     | Not applicable (single form).                                                                                                                                                             |
| Validation                | Password out of range → `VALIDATION_FAILED (422)`. Wrong current password on change → `VALIDATION_FAILED (422)` on `current_password`.                                                    |
| Permission                | Suspended user: reset gives no email, and login still returns `ACCOUNT_SUSPENDED (403)`.                                                                                                  |
| Concurrency               | Two reset emails requested: only the newest token works. The same token used in two tabs: compare-and-set on `consumed_at IS NULL` lets one succeed; the other shows "link already used". |
| External-provider failure | Email down: job retries, and the page tells the user delivery may take minutes.                                                                                                           |
| Recovery                  | Expired or used token → "This link has expired" with a new request form.                                                                                                                  |

- **AC-J18-01** Given known and unknown emails, then `requestPasswordReset` returns the same status and body. The 4th request per email within an hour returns `RATE_LIMITED (429)`.
- **AC-J18-02** Given a token older than 60 minutes or already consumed, then `resetPassword` fails with `VALIDATION_FAILED (422)` on `token`, and the password is unchanged.
- **AC-J18-03** Given a successful reset, then every session of that user is rejected on its next request and the old password no longer logs in.
- **AC-J18-04** Given two tokens issued in sequence, then only the second works.
- **AC-J18-05** Given `changePassword` from device A while device B is signed in, then A stays signed in (new session ID) and B's next request gets `UNAUTHENTICATED (401)`.
- **AC-J18-06** Given a reset or change, then the "password changed" email is sent, and no token or password appears in logs (redaction, docs/07).

E-Commerce Act 2081 s33 requires complaints to be registered and acknowledged immediately, investigated and decided within 15 days, answered in writing with reasons, and handled through an online mechanism. Directive 2082 s12 lets an unresolved complaint go to the Department (<https://giwmscdnone.gov.np/media/files/E-Commerce%20Act%2C%202081_yr7k9o5.pdf>, <https://giwmscdnone.gov.np/media/pdf_upload/ecommerce-directives_8errkt4.pdf>, accessed 2026-09-25; legal confirmation VX-02).

#### Main success flow

1. The customer opens a case: category (`order_issue`, `return_request`, `refund`, `delivery`, `product_complaint`, `account`, `other`), an optional order or shop order (own only), and a description of up to 5,000 characters [Assumption]. `openSupportCase` → `open`, with `due_at = created_at + 15 days`. There is no subject input: the server derives `support_cases.subject` from the category and the shop order or order number, for example `Delivery – DN-7Q4K2MX-1` ([04a §14.1](04a-data-dictionary-tables.md#141-support_cases); cross-doc check decision, 2026-10-01), as it does for the cases the system opens (step 9).
2. **Acknowledgement:** the response shows the case number and the decision due date (Asia/Kathmandu). In the same transaction a `system` acknowledgement message is written to the case and the acknowledgement email with the same data is queued as a `notifications.dispatch` job (AC-J19-02).
3. The support agent works the register, sorted by `due_at` (`listSupportCases`, `adminGetSupportCase`). They assign it (`updateSupportCase`), write messages (`addSupportCaseMessage`) with `visibility` `customer`, `shop` or `internal`, and set `awaiting_shop` or `awaiting_customer`.
4. The shop sees the case on the shop order (`listShopSupportCases`, `shop.orders.view`) and replies (`replyToShopSupportCase`, `shop.orders.process`). Shop replies are visible to support, and support relays what the customer needs to see [Assumption].
5. The customer replies (`replyToMySupportCase`). A reply to an `awaiting_customer` case moves it back to `open`.
6. **Decision:** the agent records `resolution_summary`, the written decision with reasons, and sets `resolved` (`resolved_at ≤ due_at`). The customer is emailed the decision and how to escalate to the Department if unsatisfied. Follow-up actions run through their own journeys: refund (J-14), return (J-20), cancellation (`adminCancelShopOrder`), and an order note (`addOrderNote`).
7. Staff close a `resolved` case by hand (`updateSupportCase` with `status = closed`). R1 has no job that closes cases (cross-doc check decision, 2026-10-01).
8. **Delivery is late** (AC-FR-ORD-005-4; E-Commerce Act s16(d), s16(g) [Verify-external VX-02]): a case with category `delivery` opened from the late-delivery action (J-07 step 5) names the shop order. Support checks the shipment. If it is not yet `shipped`, support cancels the shop order at the customer's request with `adminCancelShopOrder` (reason `admin_cancelled`) and any captured payment is refunded (J-14). If it is in transit, support tells a COD customer they may refuse the parcel and owe nothing (J-13); a gateway customer (R1.1) is refunded after the parcel returns to origin, or through a return after delivery (J-20). The decision and reasons go into `resolution_summary`.
9. **System-opened cases:** a second `delivery_failed` on a shipment opens a `delivery` case, and `not_collected` recorded on a `delivered` COD shipment opens an `order_issue` case ([05 §6.3, §6.5](05-order-payment-and-inventory-lifecycles.md#65-payment-cod)). Both get `due_at = created_at + 15 days` and follow steps 3–6.
10. **SLA monitoring:** an hourly job flags cases 3 days before `due_at` (amber) and overdue cases (red), and sends a daily digest to platform admins (docs/11). The 15 days are counted as calendar days in Asia/Kathmandu. Pausing the clock while `awaiting_customer` is not allowed without legal confirmation (VX-02).

| Entry points  | A support case with category `return_request` (J-19); the admin order detail                                                                                                                                                                                                                                                                                                                                         |
| Preconditions | Shipment `delivered` and `now() ≤ shipments.return_window_ends_at`, stored at delivery as `delivered_at + return_window_days` (default 7 [Assumption A-05; OD-06]; [04a §11.5](04a-data-dictionary-tables.md#115-shipments)), or an admin override with a written reason for goods that do not conform to the listing (E-Commerce Act s10; AC-FR-RET-006-1); item category not excluded by the return policy (OD-07) |

The Consumer Protection Act 2075 s14 gives a 7-day return right for dissatisfaction, without deductions (secondary source <https://faolex.fao.org/docs/pdf/NEP225788.pdf>, accessed 2026-09-25). E-Commerce Act s10 requires non-conforming goods to be taken back and refunded including taxes. How the two interact, and whether return shipping may be charged, is VX-04 and OD-07.

#### Main success flow

1. The customer opens a `return_request` case naming items and a reason (J-19).
2. The agent checks eligibility: the stored `return_window_ends_at` (or override), excluded categories, and returnable quantity per item: kept (`quantity − rejected − cancelled`) − returned − the line's units on the shop order's `goodwill` or `other` refunds not in `cancelled` − units in open returns ([05 §6.6](05-order-payment-and-inventory-lifecycles.md#66-returnrequest-r1-support-created-r2-self-serve)), so no unit is refunded twice.
3. `createReturnRequest` ⚷ with `{shop_order_number, items: [{order_item_id, quantity}], reason_code, customer_note}` → `requested`, with `created_by_staff_id` and `reason_code` ∈ `not_as_described`, `damaged`, `wrong_item`, `size_issue`, `changed_mind`, `other`. The shop order can no longer auto-complete, and the customer and shop are emailed.
4. `approveReturnRequest` → `approved`, which sets `approved_at` and `refund_due_at = approved_at + 7 days` ([05 §6.6](05-order-payment-and-inventory-lifecycles.md#66-returnrequest-r1-support-created-r2-self-serve); start point [Assumption; Verify-external VX-02]) and emails return instructions. Who pays return shipping follows OD-07. The platform default is that the vendor pays for `not_as_described`, `damaged` and `wrong_item` [Assumption]. Or `rejectReturnRequest` with `resolution_note` (1–2,000 characters, shown to the customer, [06 §13.6](06-api-design.md#136-admin)) → `rejected`, and the case is resolved with reasons.
5. When the customer hands the parcel to a courier, support or the shop records `approved → in_transit` with the courier details. When the customer drops the item at the shop, `in_transit` is set implicitly inside the receive transaction (05 §6.6). The explicit step uses the proposed `adminMarkReturnInTransit` (support) or `markReturnInTransit` (shop) of [06 §13.8](06-api-design.md#138-proposed-operations).
6. The vendor receives the parcel and calls `recordReturnReceived` ⚷ with a condition note per item (`items: [{order_item_id, condition_note}]`; `return_items.condition_note` is written here, once, [04a §11.8](04a-data-dictionary-tables.md#118-return_items)) → `received` (`received_at` set); support is notified to inspect. Support can record receipt instead (`adminRecordReturnReceived`). No stock or money changes at receipt.
7. **Inspection by support** (with the shop's condition notes). Accepted → `received → closed` in one transaction (`closeReturnRequest`, proposed in [06 §13.8](06-api-design.md#138-proposed-operations)): `order_items.returned_quantity += q` per item; a per-item `restock_quantity` (0 to the returned quantity) puts that many resaleable units back with one `return_restock` movement, and the other units are written off with the reason in `return_items.condition_note`; a refund is created in `requested` for the returned items' allocated amount, plus, for `not_as_described`, `damaged` and `wrong_item`, the shipping fee if shipping has not already been refunded on that shop order ([05 §3.3](05-order-payment-and-inventory-lifecycles.md#33-shipping-fee-per-shop-order)) [Assumption; Open OD-07], with the method following the payment method (`manual_transfer` for COD) and `due_at = refund_due_at`. For `manual_transfer` the staff member enters the customer's bank or wallet details in the same step, because the refund cannot be approved without them; where those details come from is [Open OD-38] (J-14 step 1). Not as agreed (used, damaged by the customer, wrong item returned) → `rejected_after_inspection` (`rejectReturnAfterInspection`, proposed in [06 §13.8](06-api-design.md#138-proposed-operations)) with a `resolution_note` that the customer sees (a case note may be written as well) and no quantity, stock or money change; how the item goes back to the customer is agreed in the case.
8. The refund must reach `succeeded` by `refund_due_at` (Directive 2082 s9(3); FR-RET-007), with no restocking fee or other deduction (CPA s14(2) [Verify-external VX-04]). Ledger effects follow J-14: `refund` −vendor share and `commission_reversal` +commission. For COD, that increases what the vendor owes (J-15).
