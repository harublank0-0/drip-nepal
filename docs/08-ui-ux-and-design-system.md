## 1. Design direction

### 1.1 Storefront identity

DripNepal sells three kinds of fashion from many small Nepali shops: streetwear, sneakers and traditional wear. The storefront is **editorial and photo-first**: the product photograph carries the page, and the interface stays quiet around it.

| Principle                         | What it means on screen                                                                                                                                                                                                                                         | Why                                                                                            |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Photo first                       | Product cards are 4:5 portrait images with title, shop name and price below, not on top of the photo. Product detail opens with the gallery. No gradients, glows or text over product photos.                                                                   | Buyers judge colour and fabric from the photo; overlays hide it                                |
| Editorial, not busy               | One serif heading voice (Lora) for page and section titles, a sans body (Noto Sans). Generous white space on listing pages; one accent colour (crimson) used for actions and the brand mark only.                                                               | Three very different styles (sneakers, kurta, hoodie) must look coherent next to each other    |
| Shop visible, marketplace trusted | Every card and product page names the selling shop and links to `/shops/{shopSlug}`. Delivery estimate, return window and COD availability appear before "Add to cart".                                                                                         | A multi-vendor cart splits into shop orders (FR-CHK-004); buyers must know who ships what      |
| Honest commerce                   | No fake countdowns, no invented "only 2 left" counts, no pre-ticked marketing consent. Stock messages come from server data (§4.3 `StockBadge`); listing order has no paid placement (AC-FR-SRCH-001-5).                                                        | FR-IAM-013 consent rule; AC-FR-SRCH-001-5; consumer-protection questions stay with VX-02/VX-04 |
| Fast on a slow phone              | Every decorative effect must justify its bytes against the 250 KB gzip route budget (NFR-PERF-002). The current landing effects (`CursorGlow`, `BackgroundEffects`, `ScrollProgress` under `inertia/pages/landing/components/`) are not used on the storefront. | Most buyers are on mid-range Android phones over mobile data (01 P4, [Assumption])             |

Traditional-wear and sneaker photos are shot on very different backgrounds. Product images therefore always sit on one neutral media surface (`--surface-media`, §5.2) in both themes, so a white studio shot does not glare out of a dark page and a dark street shot does not disappear into it.

### 1.2 Theme policy: light by default, dark supported

**Decision.** The storefront and both dashboards default to the **light** theme. A dark theme is supported and chosen explicitly by the user.

**Why light.** Product photos are colour-critical and most are shot on light backgrounds; a light page shows them as the seller intended. The current code does the opposite: `root_layout.tsx:31` wraps every page in `<ThemeProvider defaultTheme="dark">`, and `theme_provider.tsx` reads `localStorage` and adds the `dark` class inside `useEffect` [Verified-repo]. Because the class is applied only after JavaScript runs, every full page load renders light first and then flips to dark (RF-08, audit A3-09). On a slow phone this flash lasts as long as the JavaScript download. The other half of RF-08 (SSR enabled on the server but not built by Vite, and `createRoot` instead of hydration) is fixed in M0 per [03 §6.1](03-system-architecture.md#61-surfaces-and-rendering-modes); the theme fix below assumes that server HTML is actually rendered and hydrated.

**Mechanism (replaces the `localStorage` theme).**

1. The theme choice (`light`, `dark` or `system`) is stored in a cookie instead of `localStorage`, so the server knows it before rendering. The cookie name and parsing belong to [09](09-code-structure-and-engineering-standards.md) [Assumption].
2. The Edge root template `resources/views/inertia_layout.edge` writes `class="light"` or `class="dark"` and `lang="en"` on `<html>` from that cookie. Today `<html>` has neither [Verified-repo] (RF-25 for `lang`).
3. Only for `system` does the server not know the answer. A three-line inline script in `<head>` reads `matchMedia('(prefers-color-scheme: dark)')` and sets the class before first paint. It carries the per-request CSP nonce (`cspNonce`, [07 §7.3](07-security-threat-model-and-permissions.md#73-csp-and-security-headers)), because `script-src` allows only `'self'` and the nonce. A first-time visitor has no cookie and gets `light`, so the script never runs for them.
4. `ThemeProvider` keeps its React API (`theme`, `setTheme`) but reads its initial value from a page prop and writes the cookie, so the server and client agree and hydration does not mismatch.
5. `sonner`'s `<Toaster>` receives the same theme through its `theme` prop (`'light' | 'dark' | 'system'`, [Verified-repo] `node_modules/sonner/dist/index.d.ts`, sonner 2.0.7).

**Tradeoff.** A cookie is sent with every request (a few bytes) and one tiny inline script is needed for `system`. The cookie holds no personal data and must be readable by client code (so not `HttpOnly`), because `ThemeProvider` writes it [Assumption; 09 sets its attributes]. Rendering the class from a cookie is safe only because anonymous HTML is not edge-cached in R1 ([03 §12.5](03-system-architecture.md#125-caching)); if edge caching of HTML is adopted later, the class must move entirely to the inline script or the cache must vary on the cookie. [07 §5.3](07-security-threat-model-and-permissions.md#53-consent-and-purpose) still lists the theme preference as `localStorage` (Consistency notes item 15). **Verified by:** a browser test that loads a storefront page with JavaScript disabled for each cookie value and checks the `<html>` class (T-UI area, proposed in [10](10-testing-and-quality-gates.md)), and the SSR/hydration check T-ARCH-002 (proposed in [03 §6.1](03-system-architecture.md#61-surfaces-and-rendering-modes)).

### 1.3 The crimson primary and its contrast

`inertia/css/app.css` already defines the brand colour: `--primary: oklch(0.514 0.222 16.935)` in light mode and `oklch(0.455 0.188 13.697)` in dark mode, with `--primary-foreground: oklch(0.969 0.015 12.422)` [Verified-repo]. The contrast ratios below were computed on 2026-09-26 by converting each OKLCH value to sRGB (Björn Ottosson's OKLab matrices) and applying the WCAG 2.x relative-luminance formula. Values are rounded to two decimals; the computation script is not part of the repository, and a token contrast unit test is proposed in §5.10.

| Pair (token on token)                            | sRGB                   | Ratio  | Requirement (WCAG 2.2)           | Result                                                 |
| ------------------------------------------------ | ---------------------- | ------ | -------------------------------- | ------------------------------------------------------ |
| light `--primary` on white `--background`        | `#c70036` on `#ffffff` | 6.06:1 | 4.5:1 text (SC 1.4.3)            | Pass: crimson may be used for text and links           |
| light `--primary-foreground` on `--primary`      | `#fff1f2` on `#c70036` | 5.51:1 | 4.5:1 text                       | Pass: button labels                                    |
| light `--primary` on `--muted`                   | `#c70036` on `#f4f4f5` | 5.50:1 | 4.5:1 text                       | Pass                                                   |
| light `--muted-foreground` on white              | `#71717b` on `#ffffff` | 4.83:1 | 4.5:1 text                       | Pass                                                   |
| light `--muted-foreground` on `--muted`          | `#71717b` on `#f4f4f5` | 4.39:1 | 4.5:1 text                       | **Fail**: secondary text on grey panels                |
| light `--ring` on white                          | `#9f9fa9` on `#ffffff` | 2.63:1 | 3:1 non-text (SC 1.4.11)         | **Fail**, and worse at the `/50` opacity used in `ui/` |
| light `--input` (= `--border`) on white          | `#e4e4e7` on `#ffffff` | 1.27:1 | 3:1 for an input's only boundary | **Fail** for text inputs                               |
| light `--destructive` on white                   | `#e7000b` on `#ffffff` | 4.76:1 | 4.5:1 text                       | Pass                                                   |
| dark `--primary` on dark `--background`          | `#a50036` on `#09090b` | 2.51:1 | 4.5:1 text, 3:1 non-text         | **Fail**: crimson text or icons in dark mode           |
| dark `--primary-foreground` on dark `--primary`  | `#fff1f2` on `#a50036` | 7.20:1 | 4.5:1 text                       | Pass: filled buttons are fine                          |
| dark `--muted-foreground` on dark `--background` | `#9f9fa9` on `#09090b` | 7.56:1 | 4.5:1 text                       | Pass                                                   |

**Consequences** (token changes in §5.2): crimson is safe as the light-mode action and link colour; dark mode needs a separate, lighter crimson for text, links and focus rings; `--muted-foreground` darkens slightly; `--ring` and `--input` get values that reach 3:1. The filled primary button keeps the existing crimson in both themes.

### 1.4 Seller and admin direction: dense, efficient, keyboard-first

The dashboards are tools used many times a day by a few people. They follow the `radix-nova` style as installed, whose visual style is described by shadcn as "reduced padding and margins for compact layouts" [Verified-doc <https://ui.shadcn.com/docs/changelog/2025-12-shadcn-create>].

| Rule                                     | Mechanism                                                                                                                                                                                                                                                                                       |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dense by default                         | Tables with 40 px rows on desktop, filters in one bar above the table, detail views with the action panel on the right (desktop) or at the bottom (phone).                                                                                                                                      |
| Keyboard-first                           | Every action is reachable with Tab and Enter; row actions sit in a menu button, never behind hover; the list's search input is the first focusable element after the page heading. A `Ctrl/⌘ K` command menu (existing `ui/command.tsx`) jumps between pages [Assumption: R1 Should, not Must]. |
| Phone-capable for the vendor's core loop | Accepting, rejecting, marking shipped and recording COD collection work at 360 px width, because many vendors run their shop from a phone [Assumption, 01 §3.1]. Heavy editing (variants, media ordering) is desktop-first but must still work at 360 px.                                       |
| One colour for danger                    | `--destructive` only for irreversible actions (reject, block, suspend, anonymize); state colours come from `StatusBadge` (§4.3), not ad-hoc classes.                                                                                                                                            |
| No decoration                            | No hero images, charts only where FR-ADM-007 asks for numbers; R1 uses stat tiles plus tables and no chart library [Assumption, keeps dashboard JS under the 500 KB gzip budget of NFR-PERF-002].                                                                                               |

## 2. Route map and information architecture

### 2.1 Surfaces at a glance

Routes come from canon §6.4, the additions in [03 §6.1](03-system-architecture.md#61-surfaces-and-rendering-modes) (marked † there) and the page routes proposed in [06 §2.3](06-api-design.md#23-page-routes-this-document-adds). Rendering mode follows [ADR-0003](adr/0003-inertia-ssr-storefront-csr-dashboards.md): SSR with hydration for storefront, auth and payment-return pages; client-side rendering for account, seller and admin pages. Page component names use a surface prefix (`storefront/`, `auth/`, `payments/`, `account/`, `seller/`, `admin/`) because the `ssr.pages` filter sketched in 03 §6.1 selects SSR pages by that prefix.

```mermaid
flowchart TD
  Visitor["Visitor or customer"] --> Store["Storefront (SSR)"]
  Store --> Browse["Home, /men, /women, navigation entries, /c/categorySlug, /search"]
  Store --> PDP["/p/slug-publicId"]
  Store --> ShopPage["/shops/shopSlug"]
  Store --> Cart["/cart"]
  Cart --> Checkout["/checkout (signed in, verified email)"]
  Checkout --> Complete["/checkout/complete/orderNumber"]
  Store --> Legal["/legal, /grievance"]
  Visitor --> Auth["Auth pages (SSR): /login, /signup, /verify-email, /forgot-password, /reset-password"]
  Auth --> Account["Account (CSR): /account/*"]
  Account --> Sell["/sell: apply for a shop"]
  Account --> Seller["Seller dashboard (CSR): /seller/shopSlug/*"]
  Staff["Platform staff"] --> Mfa["/mfa"]
  Mfa --> Admin["Admin (CSR): /admin/*"]
```

Every page link in the header, footer and dashboard navigation is generated from named routes through the typed client ([09](09-code-structure-and-engineering-standards.md)); hard-coded paths such as the current slug-less `/shop/*` sidebar links are what broke navigation in RF-01.

### 2.7 Global navigation and help placement

- **Storefront header** (every page, in this order): brand mark → primary navigation (Men, Women, categories from `navigation.ts`) → search → account → cart with item count. The cart entry is visible at every width, including below 640 px; today the cart and profile buttons are `hidden sm:block` (`inertia/components/navbar/index.tsx:126` and `:144` [Verified-repo]), so phones have no cart entry (RF-28, AC-J00-06).
- **Storefront footer** (every page, same order): help and support (`/account/support`, or `/grievance` for guests), return and refund policy, legal disclosures (`/legal`, AC-FR-ADM-011-1), grievance officer (`/grievance`), terms and privacy. Help is always in the same relative position in the header menu and footer, and on the checkout steps, to meet WCAG 2.2 SC 3.2.6 Consistent Help [Verified-doc <https://www.w3.org/TR/WCAG22/>].
- **Kill-switch banner** (FR-ADM-010): when `checkout_enabled = false`, every storefront page shows the `maintenance_banner` setting text (≤ 280 characters, [04a §15.1](04a-data-dictionary-tables.md#151-platform_settings)) directly below the header within 60 seconds of the change (AC-FR-ADM-010-1, AC-J00-11), and the checkout page shows it instead of the place-order action (AC-FR-CHK-001-4). If the setting is empty, a fixed default message from the message catalog is shown [Assumption]. Component: `SiteBanner`, §4.3.
- **Seller dashboard**: sidebar with Overview, Orders, Products, Inventory, Returns, Support cases, Finance, Shipping, Staff, Settings, filtered by the member's permissions ([07 §4.3](07-security-threat-model-and-permissions.md#43-shop-roles-and-permissions)); shop switcher and account menu in the header; a "Help" link in the same header position on every dashboard page.
- **Admin**: sidebar grouped as Queues (overview, shop applications, moderation, support cases, returns, refunds), Records (orders, users, shops, ledger, payouts, audit logs) and Platform (staff, settings, catalog). Links the staff member's role cannot use are hidden; the server still enforces every permission (UI hides, server decides; §11 when written).

## 5. Design tokens

### 5.1 How tokens are organised

Tokens live in one file, `inertia/css/app.css`, in three layers that already exist in the repo [Verified-repo]:

1. **Values**: OKLCH colours and sizes on `:root, .light` and on `.dark`.
2. **Semantic names**: CSS custom properties such as `--primary` and `--muted-foreground`. Components use only these.
3. **Tailwind utilities**: the `@theme inline` block maps each semantic name to a Tailwind theme variable (`--color-primary: var(--primary)`), which generates `bg-primary`, `text-primary` and so on. `@theme inline` and OKLCH are the shadcn conventions for Tailwind v4 [Verified-doc <https://ui.shadcn.com/docs/tailwind-v4>]; the repo runs Tailwind 4.3.1 [Verified-repo `node_modules/tailwindcss/package.json`].

Dark mode is the `.dark` class through `@custom-variant dark (&:is(.dark *))` [Verified-repo], set on `<html>` by the server as described in §1.2. **Rule:** outside `inertia/components/ui/`, components use semantic utilities only (`bg-background`, `text-muted-foreground`, `bg-success-subtle`), never raw palette classes (`bg-black`, `text-green-600`). The audit counted 403 raw palette classes in 45 files, including a navbar fixed to `bg-black` in both themes (audit A3-19); they are replaced as each screen is rebuilt, and a lint rule in [09](09-code-structure-and-engineering-standards.md) stops new ones.

### 5.7 Motion

- **Durations and easing.** Tailwind's default transition is 150 ms with `--ease-out` for entering and `--ease-in` for leaving [Verified-repo theme.css]. Sheets and dialogs may use up to 200 ms [Assumption]; nothing that blocks input animates longer than 300 ms.
- **Reduced motion.** The app root wraps pages in framer-motion's `<MotionConfig reducedMotion="user">`; the installed framer-motion 12.42.0 types `reducedMotion` as `"always" | "never" | "user"` [Verified-repo `framer-motion/dist/index.d.ts`]. Today only `auth_card.tsx` honours reduced motion (audit A3-13). CSS animations use Tailwind's `motion-safe:` variant; whether the `data-open:` animations from `shadcn/tailwind.css` stop under `prefers-reduced-motion` is checked in M0, and a global reduced-motion rule is added if they do not [Assumption].
- **Not allowed on the storefront:** autoplaying carousels, parallax, cursor effects, scroll-jacking, and entrance animations on product grids (they delay the Largest Contentful Paint element, NFR-PERF-001).
- **Server-rendered styles.** Production CSP allows `style-src 'self' '@nonce'` ([07 §7.3](07-security-threat-model-and-permissions.md#73-csp-and-security-headers)), which is expected to block inline `style="…"` attributes in SSR HTML [Assumption; confirmed by the report-only CSP from M0]. Layout therefore uses classes (for example `aspect-[4/5]`), not inline styles, and motion components must not render meaningful inline styles on the server (Consistency notes item 7). The same directive affects `sonner`: version 2.0.7 inserts its stylesheet at runtime with `document.createElement('style')` and no nonce [Verified-repo `node_modules/sonner/dist/index.mjs`], which an enforced `style-src 'self' '@nonce'` blocks. The M0 `sonner` wrapper (§4.1) therefore also imports the package's exported `sonner/dist/styles.css` into the Vite CSS bundle, so toasts stay styled when the injection is refused [Assumption: the file matches the injected CSS; the report-only CSP from M0 shows the refused injection].

**Verified by:** a browser test with emulated `prefers-reduced-motion: reduce` that asserts no transform animation runs on the product page and checkout (T-UI area, proposed in [10](10-testing-and-quality-gates.md)).

### 5.11 Money and numeral display (VX-12)

This document owns the display decision (risks-and-open-decisions.md VX-12, with [ADR-0007](adr/0007-money-integer-minor-units.md)).

**Recommendation: "Rs" with no period, English UI digits with lakh grouping, for example "Rs 12,34,567.50" and "Rs 7,250".** Reasons: it is exactly what `Intl.NumberFormat('en-IN', { style: 'currency', currency: 'NPR', currencyDisplay: 'narrowSymbol' })` produced on Node 24 with ICU 78.3 [Verified-doc, gt/ui_frontend.md, local run]; it is what 00 A-11, 02 AC-J00-05, 03 §6.2, 04 §18.1, ADR-0007, canon §17.8 and the register's M4 safe default already use; and only canon §6.6 says "Rs." with a period. The IRD invoice formats use "रु." in Nepali [Verified-doc, gt/nepal_regulatory_locale.md], which is a Nepali-UI and invoice question for R2, not this one. The final wording stays **[Verify-external VX-12]** until the product owner confirms it as a brand choice.

**Mechanism, so the choice can change in one place:**

1. One shared formatter module (`formatNPR`, location per [09](09-code-structure-and-engineering-standards.md)) is used by SSR and client code alike; ad-hoc `toLocaleString` calls are removed (today about 20 call sites use `'Rs. ' + value.toLocaleString('ne-NP')`, which prints Devanagari digits after a Latin prefix, and others call `toLocaleString()` with no locale, RF-25).
2. The prefix is one constant (`NPR_DISPLAY_PREFIX = 'Rs'`) joined to the number with a no-break space (U+00A0, the same character ICU puts after "Rs" in the `narrowSymbol` output [Verified-doc: local run, Node 24.21.0, ICU 78.3, 2026-09-26]), so "Rs" never wraps away from the amount. The whole rupees (`(minor - minor % 100) / 100`) are grouped with `Intl.NumberFormat('en-IN')`, and the paisa are appended as a two-digit string, both by integer arithmetic as in [04 §18.1](04-domain-model-and-data-dictionary.md#181-representation). Composing the prefix ourselves, instead of taking ICU's currency symbol, keeps the output identical across Node and browsers whose CLDR data may differ (Firefox and Safari output was not verified, gt/ui_frontend.md) [Assumption: design choice].
3. Paisa are shown only when non-zero (00 A-11): "Rs 7,250" and "Rs 7,250.50".
4. Negative amounts (vendor balance owed) print the minus before the prefix, as `Intl` does ("-Rs 1,000"; the local run above gave "-Rs 1,000.00"), and are always accompanied by a text label such as "You owe", never colour alone.
5. `en-NP` is never used: it is not a CLDR locale and falls back to Western grouping; `ne-NP` gives Devanagari digits and is reserved for the R2 Nepali UI, where the digit choice (`ne-NP-u-nu-latn` or Devanagari) is a separate R2 decision [Verified-doc, gt/ui_frontend.md].

**Verified by:** formatter unit tests for 0, 50 paisa, Rs 7,250, Rs 12,34,567.50 and a negative value, plus an SSR-versus-client snapshot test with identical output (NFR-I18N-002). Localization behaviour beyond money (dates, plurals, catalogs) is §11 (planned).

## 6. Responsive and layout rules

### 6.1 General rules

1. **Mobile-first.** Base styles target a 360 px phone; `md:` and `lg:` add columns. At 360 px every primary action of every journey is reachable without horizontal scrolling (AC-J00-06); at 320 px content reflows without two-dimensional scrolling (SC 1.4.10), except data tables, which may scroll horizontally inside a labelled region.
2. **One column of truth.** The same fields and actions exist at every width; small screens reorder or collapse them (sheet, accordion, card rows) but never drop an action.
3. **No hover-only controls.** Anything revealed on hover is also visible on touch and appears on `:focus-within` (RF-28).
4. **Sticky elements reserve space.** Every sticky header or bottom bar sets matching `scroll-padding-top` or `scroll-padding-bottom` on the scrolling element, so a focused field is never hidden behind it (SC 2.4.11 Focus Not Obscured, technique C43 [Verified-doc <https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html>]; NFR-A11Y-002). Heights come from two CSS variables, `--header-h` and `--bottom-bar-h`, set by the layout.
5. **Safe areas.** Bottom bars add `env(safe-area-inset-bottom)` padding; this needs `viewport-fit=cover` in the viewport meta tag, which `inertia_layout.edge` does not have today (it has `width=device-width, initial-scale=1` [Verified-repo]) [Assumption: added with the first sticky bottom bar in M4].
6. **Media keeps its box.** Every image has a fixed aspect-ratio class (`aspect-[4/5]` for product cards, `aspect-square` for thumbnails) and explicit `width` and `height`, so layout does not shift while images load (CLS ≤ 0.1, NFR-PERF-001). Image strategy is §10.4.

## 7. Interaction patterns

These patterns apply to every surface. They sit on top of the error contract in [06 §5](06-api-design.md#5-error-contract) and the idempotency rules in [06 §7](06-api-design.md#7-idempotency); this section decides only what the user sees and how focus and announcements behave.

### 7.1 Forms

**Stack.** Every form that writes data uses TanStack Form (`@tanstack/react-form` 1.33.0 [Verified-repo `package.json`]) for field state and client validation, and sends the write through the `apiCall()`/`useApiMutation` wrapper of [06 §5.4](06-api-design.md#54-how-inertia-pages-consume-errors) (writes are JSON, reads are props, [ADR-0004](adr/0004-inertia-reads-json-api-writes.md)). Inertia's own `useForm` and `<Form>` are not used for writes, so there is one error path. Kit or registry blocks that bring Zod, Formisch or Valibot forms are rewired to TanStack Form (§4.2).

**Field rules.**

| Rule                  | Mechanism                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Visible label         | Every input is built with the `field` primitive (§4.1): the label's `htmlFor` matches the input `id`, and helper text and the error message are joined in `aria-describedby`. Placeholders never replace labels (fixes the unlabeled inputs of RF-28).                                                                                                                                                                                                                                                                         |
| Required and optional | The label text says "(required)" or, where most fields are required, "(optional)"; never an asterisk alone.                                                                                                                                                                                                                                                                                                                                                                                                                    |
| When to validate      | On blur and on submit. Format hints may update while typing (the shop registration `password_strength.tsx` already uses `aria-live="polite"` [Verified-repo `inertia/pages/shops/register/components/`]; the `inertia/components/auth` copy does not), but an error message never appears while the user is still typing the first time.                                                                                                                                                                                       |
| Client rules mirror   | Client rules copy the server's limits so most errors are caught early: shop slug 3–40 characters with the slug pattern (01 AC-FR-SHOP-001-3, 04a `shops_slug_check`), product title 3–120 characters (01 AC-FR-CAT-003-1), mobile numbers `^9[678]\d{8}$` after removing `+977` (01 AC-FR-IAM-001-5, AC-FR-IAM-012-3; `NepalPhoneInput`, §4.3), except the shop contact phone, which also accepts a landline (AC-FR-SHOP-001-3), and `ward_no` within the local level's `ward_count` (04a). The server is still the authority. |
| Error text            | Says what is wrong and how to fix it ("Enter a 10-digit mobile number starting with 96, 97 or 98"), shown in text with an icon, never by colour alone (SC 1.4.1, 3.3.1, 3.3.3).                                                                                                                                                                                                                                                                                                                                                |
| One submit in flight  | The submit button shows a pending label ("Saving…", "Placing order…") and ignores further presses while the request runs. For ⚷ operations the protection is the `Idempotency-Key` created when the intent starts ([06 §7.1](06-api-design.md#71-the-key)); disabling the button is a courtesy (AC-J00-07).                                                                                                                                                                                                                    |

**Error summary.** When a submit fails with two or more field errors, or with any error on a form longer than one screen at 360 px, the form shows an error summary above the first field: a heading ("There are 3 problems with this form"), then one link per error that moves focus to the field. The summary container has `tabindex="-1"` and receives focus, so screen readers read it and keyboard users start from it (§9.1). A single error on a short form moves focus straight to that field instead. The summary is removed when the errors are fixed, not on the next keystroke.

**Mapping a problem+json response to the form.** The wrapper parses the `Problem` ([06 §5.1](06-api-design.md#51-shape)) and applies these rules:

| Response                                                                                                   | Where it appears                                                                                                                                                                                                           |
| ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `errors[]` item whose `field` matches a registered form field                                              | Under that field. `field` is a dotted path (`variants.2.sku`); TanStack Form paths use brackets for array indexes (`variants[2].sku`) [Verified-repo `form-core` `ArrayAccessor` type], so numeric segments are converted. |
| `errors[]` item with `field: null`, or a path the form does not have                                       | In the error summary as a form-level message                                                                                                                                                                               |
| Several items for one field                                                                                | All shown under the field as a list (06 §5.4 allows several)                                                                                                                                                               |
| No `errors[]` (for example `CONFLICT`, `INVALID_STATE_TRANSITION`)                                         | A form-level alert above the submit button with `detail` and "Reference: `request_id`" (AC-J00-01)                                                                                                                         |
| Codes with their own behaviour (`VERSION_CONFLICT`, `PRICE_CHANGED`, `RATE_LIMITED`, `UNAUTHENTICATED`, …) | §8.3                                                                                                                                                                                                                       |

The message is the catalog text for `errors[].code` when one exists (`resources/lang/en`, NFR-I18N-001), otherwise the server's user-safe `message`; keying on the code keeps the R2 Nepali UI free of API changes.

Server errors go into each field's `errorMap.onServer` slot, which TanStack Form 1.33.0 clears on the field's next change or blur [Verified-repo `form-core/dist/esm/ValidationLogic.js`], so the message disappears as soon as the user edits the field. Sketch (the `setFieldMeta` signature is from the installed `FormApi.d.ts`; `Problem`, `toFormPath` and `messageFor` are DripNepal code, 09 places them):

```ts
import type { AnyFormApi } from '@tanstack/react-form'

// 'variants.2.sku' -> 'variants[2].sku'
const toFormPath = (field: string) => field.replace(/\.(\d+)(?=\.|$)/g, '[$1]')

export function applyServerErrors(form: AnyFormApi, problem: Problem, known: Set<string>) {
  const formLevel: string[] = []
  for (const item of problem.errors ?? []) {
    const path = item.field === null ? null : toFormPath(item.field)
    if (path === null || !known.has(path)) {
      formLevel.push(messageFor(item)) // catalog text by item.code, else item.message
      continue
    }
    form.setFieldMeta(path, (prev) => ({
      ...prev,
      errorMap: { ...prev.errorMap, onServer: messageFor(item) },
    }))
  }
  return formLevel // rendered in the error summary
}
```

`AnyFormApi` is re-exported from `@tanstack/form-core` by `@tanstack/react-form` 1.33.0 [Verified-repo `dist/esm/index.d.ts`, `FormApi.d.ts`]. **Verified by:** a component test that submits a product form, receives a 422 with `variants.2.sku` and `field: null` items, and asserts the SKU message under the third variant, the other message in the summary, focus on the summary, and that typing in the SKU field clears its message (T-UI area, proposed in [10](10-testing-and-quality-gates.md)).

**Preserving input across failures.**

- **Any error response or timeout:** the form stays mounted with every value; a failed submit never clears a field.
- **Session expiry (401 `UNAUTHENTICATED`):** before the redirect to `/login?return_to=…`, the checkout, product edit and support case forms save a draft to `sessionStorage` and restore it after login (AC-J00-02). Drafts never contain passwords, TOTP codes, payout account numbers or KYC files; those fields are excluded by name in each form's draft config. Drafts are keyed by form and user ID and cleared on successful submit and by the `logOut` success handler before it navigates away ([07 §3.11](07-security-threat-model-and-permissions.md#311-logout-and-inertia-history)). Tradeoff: an address draft stays in the tab's `sessionStorage` until then, the same exposure as the open tab on a shared phone.
- **Inertia history:** filter drawers and other unsent UI state may use `useRemember`; sensitive fields are never remembered (gt/ui_frontend.md, Inertia "Remembering State" docs).

**Concurrent edits (`VERSION_CONFLICT`, 412).** Editors keep the user's values and list the fields that changed in `current` ([06 §8](06-api-design.md#8-concurrent-edits-etag-and-if-match)), with "Keep my changes" (resubmit on the new version) or "Discard mine and reload". Nothing is overwritten silently.

### 7.2 Tables and lists

Every seller and admin list is a `DataTable` (§4.3) over a cursor-paginated operation ([06 §6.2](06-api-design.md#62-cursors-everything-else)); the storefront listing uses page numbers and is specified in §11 (planned).

**URL is the state.** Filters, sort and the cursor live in the query string, using exactly the parameter names of the operation's allowlist ([06 §6.3](06-api-design.md#63-filter-and-sort-allowlists)), for example `/seller/{shopSlug}/orders?status=awaiting_acceptance&late=true`. A refresh, a shared link and the Back button all restore the same view. The page controller validates the query with the same allowlist; an unknown or malformed parameter redirects to the URL without it instead of showing an error page (the page equivalent of 400 `INVALID_QUERY_PARAMETER`).

| User action             | Inertia visit                                                                                                                                                            | History                                                               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| Change a filter or sort | `router.get(url, query, { preserveState: true, preserveScroll: true, replace: true, only: ['rows', 'meta'] })`; the cursor is dropped                                    | Replace, so Back leaves the list instead of undoing each filter click |
| Type in the search box  | Same, debounced 300 ms [Assumption], and only when the input has 0 or at least 2 characters (the 2–100 bound that 07 TM-24 proposes [Assumption]; 06 §6.3 sets none yet) | Replace                                                               |
| "Next page"             | Same visit with `cursor=<next_cursor>`, `replace: false`, `preserveScroll: false`                                                                                        | Push, so Back returns to the previous page                            |
| "Back to first page"    | Visit without `cursor`                                                                                                                                                   | Push                                                                  |
| Phones: "Load more"     | Appends the next page; on `@adonisjs/inertia` 4.2.0 this needs `merge()` props and a `reset` on filter change [Verified-doc gt/ui_frontend.md]                           | Replace                                                               |

The visit options are the `Visit` fields of the installed `@inertiajs/core` 2.3.27 types (`preserveState`, `preserveScroll`, `replace`, `only`, `reset`) [Verified-repo]; `rows` and `meta` are DripNepal prop names (09). Cursors only go forward, so the table offers "Next page" and "Back to first page" and relies on browser Back for the previous page; there is no page count. Only the public catalog has totals (06 §6.1); when its `total_is_capped` is true, the storefront count reads "10,000+ results".

**Table markup and keyboard.** A `<table>` with a `<caption>`, `scope="col"` headers, sort buttons inside `<th>` with `aria-sort`, one row-action menu button named with the row ("Actions for order DN-7Q4K2MX-1"), and the row identifier as the only link (no row click handler). A filter change announces the new count politely ("25 orders shown", §7.4). Phones get cards (§6.3). No bulk actions in R1 [Assumption: no R1 FR needs one].

**Verified by:** a browser test that applies two filters on `/seller/{shopSlug}/orders`, pages forward, presses Back twice, and asserts the URL, the rows and the focused element at each step (T-UI area, proposed); axe on each list page (T-A11Y-001).

### 7.3 Dialogs and destructive confirmations

Actions are sorted into three tiers. The tier decides the confirmation, not the colour of the button.

| Tier                                   | Examples                                                                                                                                                                                                                                                 | Confirmation                                                                                                                                                                                                                                                                                                                      |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0: reversible                          | Save a draft, unpublish and republish a product, change a filter, remove a cart line                                                                                                                                                                     | None. A toast confirms (§7.4)                                                                                                                                                                                                                                                                                                     |
| 1: consequential                       | Accept or reject a shop order, cancel my order, mark shipped or delivered, record COD outcome, remove a staff member, approve or reject a product or shop, suspend a shop with `fulfill_existing`, approve a refund or payout, change `checkout_enabled` | `ConfirmDialog` that states the consequence in one sentence ("The customer is told and the stock is released"), shows the amounts for money actions, and names the confirm button with the verb ("Reject order", never "OK")                                                                                                      |
| 2: irreversible or platform-wide admin | Anonymize a user, block a product, suspend a shop with `frozen` (cancels its open orders, [05 §8.10](05-order-payment-and-inventory-lifecycles.md#810-shop-suspension-while-orders-remain-open)), mark a payout paid                                     | Tier 1 plus **type-to-confirm**: the confirm button stays disabled until the user types the target's identifier shown in the dialog: the shop slug (suspend, and mark payout paid, since `payouts` has no human number in [04a](04a-data-dictionary-tables.md)), the product `public_id`, or the last 8 characters of the user ID |

Rules for every dialog:

1. `ConfirmDialog` is the `alert-dialog` primitive (§4.1). In the installed `@radix-ui/react-alert-dialog` 1.1.17 the content traps focus, ignores outside clicks (Escape still closes), and returns focus to the trigger on close [Verified-repo `dist/index.mjs`]. If the trigger no longer exists (the row left the filtered list), focus goes to the list heading.
2. On open, the same primitive focuses its Cancel button by default [Verified-repo], which is the tier 1 behaviour. Tier 2 passes an `onOpenAutoFocus` handler that calls `event.preventDefault()` and focuses the type-to-confirm input; the primitive skips its own focus when the event is already prevented.
3. Reasons that the server requires (reject reason, suspension note) are form fields inside the dialog and follow §7.1; a server error keeps the dialog open with the typed reason.
4. A ⚷ action creates its `Idempotency-Key` when the dialog opens and reuses it for retries from the same dialog ([06 §7.1](06-api-design.md#71-the-key)).
5. Step-up ([07 §3.10](07-security-threat-model-and-permissions.md#310-step-up-for-money-staff-and-sensitive-settings)): when an action answers 401 `MFA_REQUIRED` with `mfa: "verification_required"`, the same dialog swaps in a TOTP field (`autocomplete="one-time-code"`, paste allowed, SC 3.3.8), calls `verifyMfaChallenge`, and retries with the same `Idempotency-Key`; where 06 defines a `totp_code` body field (self-approval in `single_operator_mode`, `updatePlatformSetting` for `checkout_enabled` and `single_operator_mode`), the field is shown up front. Dialogs are never stacked. Turning `checkout_enabled` off asks for no code under 07, while 06 §13.6 asks for one in both directions; the dialog follows 07 (Consistency notes item 29).
6. Type-to-confirm compares after trimming and ignores case; it is friction, not security. The server decides and audits every action regardless (AC-J00-09).

**Verified by:** component tests per tier (focus on open, focus return, disabled confirm until the identifier matches, error keeps typed reason) (T-UI area, proposed); axe with each dialog open (T-A11Y-001).

### 7.4 Toasts and live announcements

**Toasts.** One `Toaster` from the `sonner` wrapper lives in the root layout (§4.1). In the installed `sonner` 2.0.7 the toaster region is a `section` with `aria-live="polite"`, `aria-relevant="additions text"` and `aria-atomic="false"`, labelled "Notifications" plus the hotkey, which defaults to Alt+T; toasts last 4,000 ms by default, and its stylesheet disables transitions under `prefers-reduced-motion` [Verified-repo `node_modules/sonner/dist/index.mjs`].

| Use a toast for                                                                     | Do not use a toast for                                                                                                                                                              |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Confirming the user's own successful action ("Added to cart", "Order accepted")     | Errors the user must act on: they go inline or in the form alert (§7.1, §8.3)                                                                                                       |
| Server flash messages after a redirect (shown once, keyed by flash ID, audit A3-11) | The only record of something: every toast's content is also visible on the page (the order status changed, the row moved)                                                           |
| Non-blocking background results in dashboards ("Image processed")                   | Storefront toasts with action buttons: the toast's action button is 24 px high in `sonner`'s CSS [Verified-repo], below the 44 px storefront target (§6.4); dashboards may use them |

Toasts with an action stay 8 s [Assumption]. Because every toast repeats something visible on the page, its timeout removes no information.

**Live announcements that are not toasts.** The root layout renders two visually hidden live regions in the server HTML, one `aria-live="polite"` and one `aria-live="assertive"`, so they exist before any text is written into them [Assumption: screen readers miss regions inserted together with their text]. A small `announce(message, politeness)` helper writes into them.

| Event                                                                                                         | Politeness                                             |
| ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Cart count or totals change, quantity changed, filter result count, variant price and stock after a selection | Polite                                                 |
| Cart revalidation notices (price changed, line unavailable; §11)                                              | Polite, plus the visible notice at the top of the cart |
| Checkout 409 or 422 on "Place order" (AC-J05-15)                                                              | Polite, with focus moved to the first affected group   |
| Session expired before a redirect, submit blocked by `RATE_LIMITED` with the wait time                        | Assertive                                              |
| Form error summary                                                                                            | No announcement: it receives focus (§7.1)              |

Assertive is reserved for these interruptions, because it cuts off whatever the screen reader is saying.

## 8. States

Every screen in §3 designs for the states below in addition to its own. The screen tables name only the states that are specific to a screen.

### 8.1 Loading

**Full page visits.** Storefront pages are server-rendered, so the first view has its content and needs no skeleton. For client-side visits, Inertia's progress bar is kept: in the installed `@inertiajs/core` 2.3.27 it appears only after a 250 ms delay by default and takes `color`, `includeCSS` and `showSpinner` options; with `includeCSS: true` it injects a `<style>` element at runtime without a nonce [Verified-repo `@inertiajs/core/dist/index.esm.js`, `setupProgress`]. That injection meets the same CSP problem as `sonner` (§5.7), so the app sets `includeCSS: false` and ships the bar's CSS in `app.css`, coloured with `--primary` (today the bar is `#4B5563` grey, set in `inertia/app.tsx` [Verified-repo]). The bar is decorative; for visits that take longer than 1 s the target region gets `aria-busy="true"` until the new page renders [Assumption].

**Skeletons** appear only where content arrives after the first render: deferred and `WhenVisible` sections (§10.3), the cart drawer and dashboard stat tiles. A skeleton has the same box as its content (§6.1 rule 6), so the swap causes no layout shift; the region has `aria-busy="true"` and one visually hidden text ("Loading reviews"). The existing `cart_skeleton.tsx`, `checkout_skeleton.tsx` and `product_skeleton.tsx` [Verified-repo] stand in for content that becomes server-rendered with RF-27, so they are deleted unless that content is deferred.

**Buttons in flight** keep their width, show a spinner plus a text label change ("Saving…"), and are marked busy (§7.1). No spinner replaces a whole page.

### 8.2 Empty states

`EmptyState` (§4.3) always says why the view is empty and offers the next action. Three kinds:

| Kind                | Example                                                   | Copy and action                                                                                                   |
| ------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| First use           | New shop's product list, a customer with no orders        | "You have no products yet" + "Add a product"; "No orders yet" + "Start shopping"                                  |

### 8.4 Offline and slow network

Many customers and vendors are on congested mobile data (01 §2.2, NFR-NET-001 to NFR-NET-003). The UI assumes requests can be slow, fail without an answer, or succeed without the answer arriving.

**Detection.** Three signals: the browser's `offline` and `online` events (`navigator.onLine` is only a hint), Inertia's `exception` event for visits that fail without a response (named `networkError` in Inertia v3, gt/ui_frontend.md; the v2 event names are in the installed `GlobalEventsMap` [Verified-repo]), and a client timeout in the `apiCall()` wrapper: 15 s for reads and 30 s for writes [Assumption; `placeOrder` p95 is 800 ms under NFR-PERF-004, so 30 s means the network, not the server, is the problem].

**`OfflineBanner`** (§4.3) appears below the header, not over content (SC 2.4.11), with a polite announcement: "You're offline. We'll keep what you've entered." or, after a timeout, "This is taking longer than usual." It has a "Try again" button (44 px on phones) and disappears on the next successful request.

**Rules.**

1. **Form state is kept** in memory through any failure (§7.1). A retry resends the same body.
2. **Writes are never retried automatically** except `IDEMPOTENCY_IN_PROGRESS` (§8.3). The user presses "Try again", and a ⚷ retry reuses the intent's `Idempotency-Key`, so a request that did succeed on the server is replayed, not repeated ([06 §7.4](06-api-design.md#74-outcomes); T-CHK-004).
3. **Reads retry once** automatically after the `online` event (partial reload with `only`), then wait for the user.
4. **Checkout recovery** after a timeout on "Place order" shows "Checking your order…" and looks for the order before offering a retry; the full behaviour, including the `sessionStorage` key, is §11 (planned) and follows AC-J05-12 and the recovery row of J-05.

**Verified by:** browser tests with the network set offline during a product save and during "Place order": the form values survive, the banner appears, the retry sends the same `Idempotency-Key`, and exactly one order exists (T-CHK-004 plus a T-UI test, proposed).

### 8.5 Permission denied: 404 versus 403

The policy is [07 §1.5](07-security-threat-model-and-permissions.md#15-design-rules-that-every-section-relies-on) rule 2 and AC-J00-08: another tenant's or another customer's resource is **404**, byte-identical to a missing one; **403** is used only when the caller already knows the resource exists. The UI follows it exactly and never adds wording that would reveal existence.

| Situation                                                               | Response                                                                                        | UI                                                                                                                                                                                                                                       |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Other shop's slug or nested ID; other customer's order, address or case | 404                                                                                             | `errors/not_found`, same copy as any missing page                                                                                                                                                                                        |
| Non-staff user on any `/admin` page                                     | 404 ([07 §4.5](07-security-threat-model-and-permissions.md#45-operation--permission-condensed)) | `errors/not_found`; the admin surface is never linked for them                                                                                                                                                                           |
| Shop member lacking a permission (an `order_fulfiller` opening Finance) | 403 `FORBIDDEN`                                                                                 | `PermissionDenied` inside the seller layout: "Your role (Order fulfiller) can't view Finance. Ask the shop owner to change your role." No retry button                                                                                   |
| Shop not active (`SHOP_NOT_ACTIVE`)                                     | 403 with `shop_status`, `suspension_mode`                                                       | A status banner on every seller page ("This shop is suspended. You can still fulfil existing orders.") and the blocked actions shown disabled with that reason ([07 §4.4](07-security-threat-model-and-permissions.md#44-status-gating)) |
| Unverified email at checkout or shop application (`EMAIL_NOT_VERIFIED`) | 403                                                                                             | Inline prompt "Verify your email to place an order" with "Resend email" (`resendEmailVerification`)                                                                                                                                      |
| Staff without the permission for an admin action                        | 403 `FORBIDDEN`                                                                                 | `PermissionDenied` in the admin layout                                                                                                                                                                                                   |

**UI hides, server decides.** Navigation and action buttons are filtered with the current user's permissions for the current shop or platform role, so members rarely meet a 403. Seller pages receive that permission list as a page prop computed on the server from the role maps in [07 §4.3](07-security-threat-model-and-permissions.md#43-shop-roles-and-permissions) (prop name per 09, proposed); the client never derives authority from anything else. Hiding is a convenience: every page and API route still checks the permission and the status gate (T-SEC-001, T-SEC-002), and a hidden action reached by URL gets the responses above.

The current weight is unknown until the first M0 run; the heavy candidates are the ones below.

**How the storefront stays under budget.**

- **No devtools in production (RF-30).** Today `inertia/app.tsx` imports `TanStackDevtools` and `formDevtoolsPlugin` statically and hides them with `<Show when={isDevMode && isBrowser}>`, so the code ships in the production bundle even though it never renders [Verified-repo]. The fix loads them through a dynamic import inside a branch that Vite removes from production builds:

  ```tsx
  // inertia/app.tsx (sketch). import.meta.env.DEV is replaced by false in `vite build`,
  // so the dynamic import below is never emitted into the production bundle.
  import { lazy, Suspense } from 'react'
  const Devtools = import.meta.env.DEV ? lazy(() => import('./dev/devtools')) : null
  // …inside setup(): {Devtools && <Suspense fallback={null}><Devtools /></Suspense>}
  ```

  `./dev/devtools.tsx` is a new DEV-only module that renders `TanStackDevtools`. **Verified by:** the CI bundle check also fails if the production output contains the strings `TanStackDevtools` or `react-form-devtools` (T-UI area, proposed).

- **Motion:** storefront pages use CSS transitions (§5.7); `framer-motion` is not imported by storefront page chunks or the storefront layout [Assumption: its size is measured in the first budget run; if it fits, the rule can relax].
- **Icons** are imported one by one from `lucide-react`; `radix-ui` imports may switch to subpath imports (`radix-ui/popover`) if the bundle report shows unused primitives [Verified-doc gt/ui_frontend.md].
- **No third-party scripts** (analytics, chat, ads) on the storefront in R1; any later addition needs consent (07 §5.8) and a budget review.
- **Dead UI removed:** the unrouted `landing` page and design-system pages (RF-40, RF-47) leave the page glob, so they are not built at all.

### 10.2 Prefetch policy

Inertia 2.3.27 `Link` accepts `prefetch` as `true`, `'hover'`, `'click'`, `'mount'` or a list, with `cacheFor` and `cacheTags`; the app config has `prefetch.hoverDelay` and `prefetch.cacheFor` [Verified-repo `@inertiajs/core` types]. The documented defaults are a 75 ms hover delay and 30 s cache (gt/ui_frontend.md).

| Where                                         | Policy                                                                                                                                                                                                                                                                                                                                        |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Storefront, fine pointer with hover (desktop) | `prefetch="hover"` on product cards and category links; default 30 s cache. "Continue to checkout" is not prefetched (row "Pages with personal data" below)                                                                                                                                                                                   |
| Storefront, touch devices                     | **No prefetch.** Phones have no hover, and `mount` prefetch would spend the user's data on pages they may never open. The client decides after hydration with `matchMedia('(hover: hover) and (pointer: fine)')`; the SSR markup is the same either way [Assumption: the `prefetch` prop changes only event handlers, not the rendered `<a>`] |
| Save-Data                                     | No prefetch on any device when `navigator.connection.saveData` is true [Assumption: the API is missing in some browsers, where the rule simply does not apply]                                                                                                                                                                                |
| Seller and admin dashboards                   | `prefetch="hover"` on row links and sidebar links (desktop only, same rule)                                                                                                                                                                                                                                                                   |
| Pages with personal data or side effects      | Never prefetched: `/checkout`, `/account/*` detail pages, payment return, logout. Prefetch is for GET pages whose props are safe to cache for 30 s                                                                                                                                                                                            |
| After a cart write                            | Prefetching links to pages that show the cart (the header count) carry `cacheTags: 'cart'`, and the add-to-cart success handler calls `router.flushByCacheTags('cart')` [Verified-repo `router.d.ts`], because cart writes go through the JSON API, not an Inertia visit                                                                      |

### 10.3 Deferred props and below-the-fold loading

`@adonisjs/inertia` 4.2.0 provides `inertia.defer(fn, group?)` and the client has `<Deferred data fallback>` and `<WhenVisible data buffer fallback>` [Verified-repo `props.d.ts`, `inertia.d.ts`, `WhenVisible.d.ts`]. Deferred props load in one extra request after the first render (parallel requests per group), and `WhenVisible` loads them when the section nears the viewport (gt/ui_frontend.md).

| Page                      | In the SSR HTML (never deferred)                                                                              | Deferred or loaded when visible                                                                       |
| ------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Product                   | Title, shop, price, variants with availability, first gallery image, delivery and return summary, disclosures | Related products and "More from this shop" (`WhenVisible`, buffer 400 px [Assumption]); reviews in R2 |
| Listing                   | First page of products, facets with counts, applied filters                                                   | Nothing in R1; next pages load on demand (§7.2, §11)                                                  |
| Home                      | Hero and the first product rail                                                                               | Further rails (`WhenVisible`)                                                                         |
| Cart, checkout, orders    | Everything (they are small and must be correct at first paint)                                                | Nothing                                                                                               |
| Seller and admin overview | Page frame and navigation                                                                                     | Stat tiles as one deferred group, queue counts as another (AC-FR-ADM-001-2 read target)               |

SEO-relevant and decision-relevant data (price, stock, title, images) is never deferred, so it is in the server HTML for crawlers and for users whose JavaScript has not loaded yet (NFR-NET-001). Fallbacks are the skeletons of §8.1.

### 10.4 Images

**Decision (R1): pre-generated WebP derivatives, served from our own media domain.** This follows [ADR-0013](adr/0013-media-direct-upload-async-processing.md) and [03 §3.5](03-system-architecture.md#35-object-storage-layout):

- Originals stay in the **private** bucket; vendors upload them directly with a presigned URL (10 minutes in 03 and ADR-0013; 01 AC-FR-MED-001-1 says 15, Consistency notes item 5).
- The worker writes WebP derivatives at **320, 640, 1024 and 1600 px** wide (01 AC-FR-MED-001-2 [Assumption]) to the public bucket under content-addressed keys, served from `media.<domain>` behind Cloudflare with `Cache-Control: public, max-age=31536000, immutable`. These widths replace the 320/640/960/1440 set in this document's brief (Consistency notes item 6).
- Cloudflare Images transformations are **not** used in R1. The free plan allows 5,000 unique transformations a month; once exceeded, cached transformations keep serving but new ones fail with error 9422 [Verified-doc <https://developers.cloudflare.com/images/pricing/>, accessed 2026-09-25]. With a growing catalogue and several widths per image, that ceiling would break new product images without warning; ADR-0013 keeps edge transformation as a revisit option (R-20).

**Markup rules.** Every product image is an `<img>` with `src` set to the 640 px derivative, a `srcset` of all four derivatives with `w` descriptors, a `sizes` value per context, explicit `width` and `height` from `media_assets.width` and `height` ([04a §7.13](04a-data-dictionary-tables.md#713-media_assets)), `decoding="async"`, and the vendor's alt text (FR-MED-002).

| Context                                    | `sizes` [Assumption: from the §6.2 grids and `max-w-7xl`]  | Loading                                                                                    |
| ------------------------------------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Listing card (2 / 3 / 4 columns)           | `(min-width: 1024px) 300px, (min-width: 768px) 33vw, 50vw` | `loading="eager"` for the first row (2 cards on phones, 4 on desktop), `lazy` for the rest |
| Product gallery main image                 | `(min-width: 768px) 50vw, 100vw`                           | First image `loading="eager"` and `fetchpriority="high"` (the LCP element); others `lazy`  |
| Gallery thumbnails, cart and order lines   | `80px`                                                     | `lazy`; the browser picks the 320 px file                                                  |
| Home hero (editorial image, not a product) | `100vw`                                                    | `eager`, `fetchpriority="high"`; exactly one image per page gets high priority             |

A 360 px phone at device pixel ratio 3 renders a two-column card at about 180 CSS px, which selects the 640 px file; the 1600 px file is used only by large desktop galleries.

**Layout stability.** Images sit in the aspect-ratio boxes of §6.1 rule 6 (`aspect-[4/5]` cards, `aspect-square` thumbnails) on the `--surface-media` background (§5.2) with `object-contain`, so photos of any shape keep their box and nothing shifts while they load (CLS ≤ 0.1) [Assumption: `object-contain` rather than cropping, to show the whole garment; revisited after the visual review of §5.2].

**Placeholders (LQIP and dominant colour).** R1 uses the neutral `--surface-media` background as the only placeholder: it costs no bytes and needs no inline style, which matters because the production CSP is expected to block inline `style` attributes in server HTML (§5.7). Per-image placeholders are an R2 option with two variants, both requiring a new column that 04a does not have (proposed; Consistency notes):

| Option                    | How                                                                                                                                                                                                           | Cost                                                                                         |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Dominant colour           | The worker computes it during processing (pseudocode; sharp is not installed yet [Verified-repo]) and stores it; the UI maps it to one of about 12 preset tone classes, so no inline style is needed          | A few bytes per image; approximate colour                                                    |
| Tiny blurred image (LQIP) | A 16 px WebP stored as a `data:` URI and rendered as a second `<img>` behind the real one; allowed by `img-src … data:` in [07 §7.3](07-security-threat-model-and-permissions.md#73-csp-and-security-headers) | About 200–400 bytes per image in the page props, which counts against the 100 KB prop budget |

**Vendor uploads on slow links.** `ImageUploader` shows each file's size and progress, uploads one file at a time on phones, and keeps the queue with "Retry" after a failure (§8.4) [Assumption].

### 10.5 Fonts

- **Self-hosted, no font CDN:** Fontsource packages bundled by Vite, matching `font-src 'self'` ([07 §7.3](07-security-threat-model-and-permissions.md#73-csp-and-security-headers)).
- **`font-display: swap`** is already declared by Fontsource [Verified-repo `@fontsource-variable/noto-sans/index.css`], so text is never invisible while a font loads.
- **Subsets load on demand.** Each subset is its own `@font-face` with a `unicode-range`, and the browser downloads only the subsets whose characters appear on the page. Installed file sizes [Verified-repo `node_modules/@fontsource-variable/*/files`]: Noto Sans latin 35.8 KB, latin-ext 168.0 KB, Devanagari 99.2 KB; Lora latin 37.8 KB, latin-ext 20.1 KB. An English page therefore loads about 74 KB of fonts (Noto Sans latin and Lora latin). The "Rs" prefix of §5.11 is plain ASCII, so prices never pull in another subset, whereas "₨" (U+20A8) sits in the latin-ext and Devanagari ranges [Verified-repo `unicode-range`]. Nepali product text pulls in the 99 KB Devanagari file once, which is expected (NFR-I18N-004).
- **Geist is dropped** and the duplicate CSS imports removed in M0 (§5.3, RF-30).
- **Preload one file.** Storefront pages preload the Noto Sans latin file (`<link rel="preload" as="font" type="font/woff2" crossorigin>`), because body text and prices are the LCP content; Lora is not preloaded, since headings can swap in. The hashed file URL comes from the Vite manifest in the Edge layout (pseudocode until M4; `@adonisjs/vite` 5.1.1 helpers for this are not verified here).
- **Fallback metrics.** A local fallback `@font-face` with `size-adjust` close to Noto Sans reduces layout shift when the font swaps [Assumption: values tuned in M4 with Lighthouse CLS].

### 10.6 Production hygiene

- No devtools (§10.1) and no page props written to the console or SSR logs (RF-26, AC-J00-10; lint rule `no-console` in `inertia/**` per [09](09-code-structure-and-engineering-standards.md)).
- Source maps are uploaded to the error tracker and not served publicly [Assumption; 11 decides].
- Debug, mock and design-system pages are unrouted in production (RF-40). The Tuyau client registry still ships every route pattern to the browser; [07 §1.1](07-security-threat-model-and-permissions.md#11-scope-and-method) accepts that because no control depends on hidden routes (audit A5-17), so here it counts only as bundle weight, measured by the §10.1 check.
